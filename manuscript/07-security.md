# 第7章　攻撃の手口を知り、守りを固める

ネットショッピングでカード番号を入力するとき、私たちは大切な情報をインターネットに送り出しています。第6章で見たように、データはいくつものルーターを中継して届きます。途中には、自分では管理できない機器がたくさんあります。それなのに、なぜパスワードやカード番号は盗み見られないのでしょうか。

この章では、まず情報セキュリティの考え方と身近な脅威を整理します。そのうえで、暗号、デジタル署名と電子証明書、認証という守りのしくみを順に見て、最後にシステムを作る側の備えを紹介します。読み終えるころには、鍵マークの意味や、パスワードを使い回してはいけない理由を、自分の言葉で説明できるはずです。

## 7-1　情報セキュリティとは何か

「セキュリティ」と聞くと、ウイルス対策ソフトや複雑なパスワードを思い浮かべるかもしれません。しかし、それらは手段の一部です。まずは「何を守るのか」から考えましょう。

私たちが家に鍵をかけるのは、中にある財産や暮らしを守るためで、鍵そのものが目的ではありません。情報の世界でも、守る対象は情報と、それを扱うシステムです。これを**情報資産**と呼びます。顧客の名簿、写真、プログラムのソースコード、サーバーなどが情報資産にあたります。

### 機密性・完全性・可用性

では、情報が「守られている」とは、どういう状態でしょうか。**情報セキュリティ**では、次の3つの性質を保つことだと考えます。

1つ目は**機密性**（Confidentiality）です。見てよい人だけが情報を見られる状態を指します。SNSで「友達のみに公開」にした写真を、他人が見られないことです。

2つ目は**完全性**（Integrity）です。情報が正しく、勝手に書き換えられていない状態を指します。投稿した文章が、知らないうちに別の内容に変わっていないことです。

3つ目は**可用性**（Availability）です。使いたいときに、きちんと使える状態を指します。見たいときにSNSが開けることです。

3つの英語の頭文字をとって、**CIA**と呼ぶこともあります（表7-1）。国際規格のISO/IEC 27000シリーズでも、情報セキュリティはこの3つを維持することだと定義されています。日本ではJIS Q 27000などがこれにあたります。この定義の注記では、さらに4つの性質を加えることもあるとしています。利用者や情報が名乗るとおりの本物であること（**真正性**）。誰がいつ何をしたかを後からたどれること（**責任追跡性**）。行った操作を後から否定できないようにすること（**否認防止**）。システムが意図したとおりに動くこと（**信頼性**）。7-4のデジタル署名は真正性と否認防止を、7-6のログは責任追跡性を支えます。

表7-1　情報セキュリティの3要素

| 要素 | 意味 | SNSでの例 | 損なわれた例 |
| --- | --- | --- | --- |
| 機密性（C） | 許可された人だけが見られる | 非公開の写真は本人と友達だけが見られる | 不正ログインで非公開のメッセージを読まれる |
| 完全性（I） | 正確で、改ざんされていない | 投稿した文章がそのまま表示される | 乗っ取られたアカウントで勝手に投稿される |
| 可用性（A） | 必要なときに使える | いつでも投稿や閲覧ができる | 攻撃でサーバーが止まり、つながらない |

3つの性質は、ときにぶつかり合います。データを金庫にしまって誰にも触らせなければ、機密性は高まりますが、すぐ取り出せないので可用性は下がります。序論で、何かを得ると別の何かを手放すことになる関係を、トレードオフと呼びました。安全性と使い勝手は、その代表です。

### 脅威・脆弱性・リスク

**脅威**（threat）は、情報資産に損害を与えるおそれのある原因です。攻撃者やマルウェアのほか、地震や火災、操作ミスも含まれます。**脆弱性**（vulnerability）は、脅威につけこまれる弱点です。ソフトウェアの欠陥、推測しやすいパスワード、鍵のかけ忘れなどが該当します。**リスク**（risk）は、脅威が脆弱性をついて、実際に損害が生まれる可能性のことです。

家の防犯でいえば、空き巣が脅威、窓の鍵のかけ忘れが脆弱性です。空き巣がいても戸締まりが完璧なら、また鍵をかけ忘れても空き巣がいない場所なら、被害は起きにくいでしょう。リスクは、脅威と脆弱性がそろったときに大きくなります。

リスクの大きさは、起こりやすさと、起きたときの影響の大きさの2つの面から見積もります。めったに起きなくても、起きれば会社が傾くような事態は、大きなリスクとして扱います。

### 技術・人・組織で守る

対策は、大きく3つに分けて考えると整理しやすくなります。

- **技術的対策**：暗号化、ウイルス対策ソフト、ファイアウォール、アクセス制御など、技術で守るもの
- **人的対策**：社員への教育や訓練、守秘義務の取り決めなど、人の行動で守るもの
- **組織的対策**：セキュリティの方針やルールづくり、責任者の任命、事故が起きたときの対応手順の整備など、組織のしくみで守るもの

サーバー室への入室制限のような、物理的な対策を別に分けることもあります。どれか1つだけでは不十分です。最新の暗号技術を使っていても、社員がパスワードを付箋に書いて画面に貼っていれば、そこから破られます。「鎖の強さは最も弱い輪で決まる」といわれるように、セキュリティの強さは一番弱いところで決まるのです。

### リスクを「ゼロ」にはできない

セキュリティを考えるうえで最も大切なのは、リスクをゼロにすることはできない、という考え方です。インターネットから切り離し、誰にも使わせなければ、攻撃される心配はほとんどなくなりますが、それでは誰の役にも立ちません。対策を増やすほど費用がかかり、使い勝手も悪くなります。

そこで実際には、リスクを洗い出して大きさを見積もり、許容できる水準まで下げることを目指します。リスクへの向き合い方には、次の4つがあります。

- 対策をしてリスクを小さくする（低減）
- 危険な業務やデータの保有そのものをやめる（回避）
- 保険や外部への委託で、損害を他者と分け合う（移転）
- 小さなリスクは承知のうえで受け入れる（受容）

どれを選ぶかは、守るものの価値と、対策にかかる費用とのつり合いで決めます。対策をしたあとにも残るリスクを**残留リスク**と呼びます。残留リスクは、責任者が中身を把握したうえで受け入れます。

営業担当者が、顧客名簿の入ったノートパソコンを持ち歩く会社を例にしましょう。パソコンの中身を暗号化して、置き忘れても読めないようにするのが「低減」です。名簿を社外へ持ち出さないと決めるのが「回避」、漏えいに備えて保険に入るのが「移転」です。そして、パソコンに入れるのが公開済みの製品カタログだけなら、なくしても影響は小さいと事前に判断し、追加の対策はしないと決めておくのが「受容」です。

### 方針を決めて、回し続ける

こうした判断を担当者任せにすると、守り方が人によってばらつきます。そこで組織は、何をどの水準で守るのかを文書にまとめます。これを**情報セキュリティポリシー**と呼びます。経営者が示す基本方針と、それを具体化した対策の基準や手順書に分けて作るのが一般的です。

方針は、作って終わりではありません。脅威も業務も変わるからです。リスクを見積もり、対策を実施し、点検して見直す。この循環を続ける管理のしくみを**ISMS**（情報セキュリティマネジメントシステム）と呼びます。求められる事項は国際規格ISO/IEC 27001（日本ではJIS Q 27001）に定められ、第三者の審査を受けて認証を取得する組織もあります。

エンジニアには、「この機能にはどんな脅威があり、どこまで守ればよいか」を、作り始める前から考えることが求められます。セキュリティは、完成したあとに貼りつけるものではなく、設計の段階から組み込むものなのです。

## 7-2　身近にある脅威

「宅配便の不在通知です。こちらから再配達の手続きをしてください」。こんなメッセージがスマホに届いたことはないでしょうか。これは、よくある攻撃の入り口です。守りの第一歩として、相手の手口を知りましょう。

### マルウェア ― 悪意のあるプログラム

**マルウェア**（malware）は、悪意をもって作られたソフトウェアの総称です。命令の中身が悪意あるものでも、コンピューターは指示どおりに実行してしまいます。マルウェアは、広がり方やふるまいによって、次のように分けられます。

表7-2　代表的なマルウェア

| 種類 | 特徴 |
| --- | --- |
| ウイルス | 他のプログラムやファイルに入り込み、それが実行されると活動して広がる |
| ワーム | 単独で動き、ネットワークを通じて自分の複製を次々に送り込む |
| トロイの木馬 | 便利なソフトなどに見せかけて入り込み、裏で不正な動作をする |
| ランサムウェア | ファイルを勝手に暗号化して使えなくし、元に戻す代わりに身代金を要求する |

**ウイルス**は他のファイルにとりついて増え、**ワーム**は単独でネットワークを伝って広がります。**トロイの木馬**の名前は、ギリシャ神話の木馬の計略に由来します。無料のゲームや便利ツールのふりをして、利用者自身にインストールさせるのが典型的な手口です。

なかでも大きな被害を出しているのが**ランサムウェア**です。会社のサーバーのファイルが一斉に暗号化され、業務が何日も止まった例が国内外で報告されています。情報を守るための暗号（7-3）が、攻撃にも使われているのです。最近は、暗号化する前にデータを盗み出しておき、「払わなければ公開する」とも脅す**二重脅迫**が広がっています。暗号化はせず、盗んだデータを公開すると脅すだけの**ノーウェアランサム**もあります。IPA（情報処理推進機構）が毎年発表する「情報セキュリティ10大脅威」の組織向けの順位では、2021年版から2026年版まで6年続けて、この種の攻撃が1位でした。2026年版での名前は「ランサム攻撃による被害」で、ノーウェアランサムも含めています。

基本的な対策は3つです。まず、OSやアプリを最新の状態に保ち、ウイルス対策ソフトを使うこと。名前は「ウイルス」ですが、現在の製品はマルウェア全般を対象にしています。次に、出どころの分からないソフトやメールの添付ファイルを開かないこと。そして、バックアップです。データの複製が別の場所に残っていれば、身代金を払わずに元へ戻せる可能性が高まります（7-6）。

### フィッシング ― 本物そっくりの偽物

**フィッシング**（phishing）は、偽のメールやWebサイトで、パスワードやカード番号をだまし取る手口です。冒頭の宅配便の通知は、その典型例です。銀行やショッピングサイトを名乗って「アカウントが停止されます」などと不安をあおり、本物そっくりの偽サイトへ誘導します。SMSを使うものは**スミッシング**とも呼ばれます。

フィッシングは、技術の弱点ではなく人の心理をつきます。「急がないと損をする」と思わされると、人は確認を省きがちです。

対策は、メールやSMSのリンクから直接ログインせず、公式アプリや、ブックマークしておいた正しいURLからアクセスすることです。アドレスバーでドメイン名を確かめる習慣も役立ちます。ただし、偽サイトは見た目では見分けにくく、鍵マークがあるから本物とも限りません（7-4）。そこで、多要素認証やパスキー（7-5）のように、だまされても被害が出にくいしくみが重要になります。

### 不正アクセス ― 他人の鍵で入り込む

**不正アクセス**は、使う権限のない人が、他人のアカウントやシステムに入り込むことです。ここではパスワードを狙う手口を紹介します。

1つは、考えられる文字の組み合わせを片っ端から試す**総当たり攻撃**（ブルートフォース攻撃）です。よく使われる単語やパスワードを順に試す**辞書攻撃**もあります。長く推測されにくいパスワードが有効で、サービス側も、何度も失敗したらログインを一時的に止めるなどして防ぎます。

もう1つが、**パスワードリスト攻撃**です。どこかのサービスから流出したIDとパスワードの組を、別のサービスでそのまま試します。同じパスワードを使い回す人が多いので、よく成功します。使い回しがなぜ危険なのかは、7-5で見ます。

### ソーシャルエンジニアリング ― 人をだます

**ソーシャルエンジニアリング**は、技術ではなく人の心理や不注意につけこんで情報を盗む手口の総称です。たとえば、社内の情報システム部門を名乗って電話をかけ、「システム点検のためにパスワードを教えてください」と頼みます。パスワードを入力する手元を後ろからのぞき見る**ショルダーハッキング**や、捨てられた書類から情報を拾い集める手口も含まれます。取引先や経営者になりすまして偽の振込先を伝える**ビジネスメール詐欺**も、この仲間です。

どれほど強固なシステムでも、人がパスワードを教えてしまえば役に立ちません。「最も弱い輪」は、人であることも多いのです。対策としては、「正規の担当者がパスワードを聞くことはない」といったルールを決めて周知します。電話やメールで重要な依頼を受けたら、別の連絡手段で本人に確かめることも大切です。

### DoS攻撃・DDoS攻撃 ― 使えなくする

ここまでの脅威は、主に機密性や完全性を狙うものでした。これに対して可用性を狙うのが**DoS攻撃**（Denial of Service attack：サービス妨害攻撃）です。サーバーに処理しきれないほど大量の通信を送りつけ、本来の利用者がサービスを使えない状態にします。

攻撃元が1台なら、その送信元からの通信を遮断するのが基本の対処です。ただし、送信元のIPアドレスは偽ることができるので、遮断だけで防ぎきれるとは限りません。大量の通信ではなく、脆弱性を突く細工をした通信でサーバーを止めるDoS攻撃もあります。さらに攻撃者は、マルウェアに感染させた多数の機器から一斉に通信を送ります。これを**DDoS攻撃**（Distributed Denial of Service attack：分散型サービス妨害攻撃）といい、攻撃者に操られる機器の集まりを**ボットネット**と呼びます。パスワードが初期設定のまま放置された防犯カメラやルーターなどのIoT機器（インターネットにつながる家電やセンサーなど）も悪用されています。第6章で触れた2016年のDNS事業者への攻撃でも、マルウェアに感染した多数のIoT機器が使われました。

送信元が世界中に散らばるため、DDoS攻撃を1つの組織だけで防ぐのは困難です。通信事業者やクラウド事業者の対策サービスを使い、異常な通信を手前でふるい落とすのが一般的です。利用者も、自宅のルーターやカメラの初期パスワードを変え、ファームウェアを更新しておけば、自分の機器が攻撃の踏み台になるのを防げます。

### 標的型攻撃とサプライチェーン攻撃 ― 狙いを定め、回り道をする

ここまでの手口の多くは、不特定多数に仕掛けるものでした。これに対して、特定の組織に狙いを定め、機密情報を盗むことなどを目的にした攻撃を**標的型攻撃**と呼びます。攻撃者は相手の業務や取引先を調べ、実在の担当者を装ったメールでマルウェアを送り込みます。気づかれないまま、長いあいだ内部を探ることもあります。見破りにくいので、「開かせない」対策だけでは足りません。侵入されても被害が広がりにくくする最小権限や、異常に気づくためのログの監視（どちらも7-6）と組み合わせます。

守りの固い組織を直接は狙わず、つながりのある弱いところから入り込むのが**サプライチェーン攻撃**です。サプライチェーンは、製品やサービスが届くまでの取引のつながりを指します。手口は大きく2つあります。1つは、対策が手薄な取引先や委託先に先に侵入し、そこを足がかりにする方法です。もう1つは、多くの組織が使うソフトウェアやその更新プログラムに、開発や配布の段階でマルウェアを混ぜる方法です。後者では、正規の更新を入れただけで被害にあいます。7-1の「最も弱い輪」は、自分の組織の外にもあるわけです。委託先に求める対策を契約で決めて確認することや、自分のシステムが使っている部品（ライブラリなど）を把握しておくことが対策になります。10大脅威2026の組織向けでは、サプライチェーンや委託先を狙った攻撃が2位でした。

### そのほかの攻撃

このほかにも、名前としくみを知っておきたい攻撃があります（表7-3）。Webアプリケーションを狙う攻撃は、7-6で詳しく見ます。

表7-3　そのほかの代表的な攻撃

| 攻撃 | しくみ | 主な対策 |
| --- | --- | --- |
| DNSキャッシュポイズニング | フルサービスリゾルバーのキャッシュ（6-5）に偽の対応を覚えさせ、正しいドメイン名で偽サイトへ導く | 応答を署名で検証するしくみ（DNSSEC）など |
| バッファオーバーフロー | 用意されたメモリの領域より長いデータを送り込み、隣の領域を書き換えて、誤動作や不正な命令の実行を引き起こす | 入力の長さの検査、メモリを安全に扱う言語 |
| ディレクトリトラバーサル | ファイル名の入力に「`../`」（1つ上のディレクトリ）などを混ぜ、非公開のファイルを読み出す | 入力からファイルの場所を直接組み立てない |
| ブルートフォース攻撃 | パスワードや鍵の候補をすべて試す（総当たり攻撃） | 長いパスワード、試行回数の制限、多要素認証 |
| ゼロデイ攻撃 | 修正プログラムが提供される前の脆弱性を突く（7-6） | 1つの守りに頼らず、対策を重ねて監視する |

次の節からは、これらの脅威に立ち向かう技術を見ていきます。

## 7-3　盗み見を防ぐ ― 暗号のしくみ

カフェの無料Wi-Fiでネットショッピングをしている場面を想像してください。同じWi-Fiには見知らぬ人もつながっていますし、パケットはいくつものルーターを経由します。途中の誰かが中身をのぞくことを、完全に防ぐのは困難です。そこで、見られても意味が分からないようにしておけばよいのです。これが**暗号**の考え方です。

### 平文・暗号文・鍵

元の読めるデータを**平文**（ひらぶん）、読めないように変換したデータを**暗号文**と呼びます。平文を暗号文に変えることを暗号化、暗号文を平文に戻すことを**復号**といいます。

古くからある単純な例が、文字をずらすシーザー暗号です。アルファベットを3文字後ろにずらすと決めれば、「CAT」は「FDW」になります。受け取った人は、3文字前に戻して読みます。

ずらすという手順を**暗号アルゴリズム**、「3文字」という具体的な値を**鍵**と呼びます。現代の暗号では、アルゴリズムは公開し、鍵だけを秘密にします。世界中の専門家に調べてもらい、弱点が見つからなかったものだけを使うほうが、隠すよりも信頼できるからです。

シーザー暗号の鍵は25通りしかないので、すべて試せばすぐに解けます。現代の暗号は、鍵の候補が天文学的な数になるように作られています。第2章で見たとおりnビットなら2のn乗通りなので、128ビットの鍵は2の128乗、およそ3.4×10の38乗通りです。現在のコンピューターで総当たりしても、現実的な時間では試しきれません。

### 共通鍵暗号 ― 同じ鍵で閉めて開ける

暗号化と復号に同じ鍵を使う方式を**共通鍵暗号**といいます。現在よく使われているのは、**AES**（Advanced Encryption Standard）です。2001年に米国の標準として定められ、Wi-Fiの暗号化、スマホの中のデータの保護、Webの通信など、身の回りの多くの場面で働いています。

共通鍵暗号の長所は、写真や動画のような大きなデータでも速く処理できることです。ところが、大きな弱点があります。暗号文を受け取る相手にも、同じ鍵を渡さなければならないことです。鍵をそのままインターネットで送れば、途中で盗まれるかもしれません。鍵を安全に送る手段があるなら、そもそも暗号は要らないはずです。この矛盾を**鍵配送問題**と呼びます。

さらに、相手ごとに別の鍵が必要です。10人が互いに秘密のやりとりをするには45個、100人なら4,950個の鍵が要ります。インターネットで出会う無数の相手と、事前に鍵を分け合っておくことは不可能です。

### 公開鍵暗号 ― 誰でも閉められる南京錠

この難問を解決したのが、1970年代に登場した**公開鍵暗号**です。この方式では、暗号化と復号に別々の鍵を使います。一方の鍵は、広く公開します。これを**公開鍵**と呼びます。もう一方は、持ち主だけが厳重に保管します。これを**秘密鍵**と呼びます。送り手は受け手の公開鍵で暗号化し、受け手は対になる秘密鍵で復号します。

南京錠にたとえましょう。あなたは、開いた状態の南京錠をたくさん用意して、誰にでも配ります。これが公開鍵です。南京錠は押せば誰でも閉められますが、開ける鍵はあなただけが持っています。これが秘密鍵です。誰かがあなたに秘密の手紙を送りたいときは、手紙を箱に入れて、あなたの南京錠で閉めて送ればよいのです。途中で誰かが箱を手に入れても、開けることはできません（図7-1）。

![図7-1　共通鍵暗号と公開鍵暗号の違い](../figures/fig-7-1.svg)

共通鍵暗号は同じ鍵で閉めて開けるのに対し、公開鍵暗号は受け手の公開鍵で閉めて、受け手の秘密鍵で開けます。

この方式なら、事前に鍵をこっそり受け渡す必要がありません。公開鍵から秘密鍵を割り出すことは、現実的な時間ではできないように作られています。代表例は、RSAを使う暗号化方式の**RSA-OAEP**です。

ただし、公開鍵暗号にも弱点があります。複雑な計算を行うため、共通鍵暗号に比べて処理がずっと遅いのです。大量のデータをすべて公開鍵暗号で暗号化するのは、効率がよくありません。鍵の受け渡しやすさと処理の速さの、トレードオフです。

表7-4　共通鍵暗号と公開鍵暗号の比較

| 項目 | 共通鍵暗号 | 公開鍵暗号 |
| --- | --- | --- |
| 使う鍵 | 暗号化と復号に同じ鍵 | 暗号化に公開鍵、復号に秘密鍵 |
| 処理の速さ | 速い | 遅い |
| 鍵の受け渡し | 相手に秘密のまま渡す必要がある | 公開鍵は誰に知られてもよい |
| 必要な鍵の数 | 相手ごとに1つずつ | 1人につき1組 |
| 代表例 | AES | RSA-OAEP |

### いいとこ取りのハイブリッド方式

そこで実際の通信では、両方の長所を組み合わせます。データ本体は速い共通鍵暗号で暗号化し、その共通鍵を相手と共有する部分にだけ、公開鍵暗号の技術を使います。これを**ハイブリッド暗号方式**と呼びます。

基本的な流れはこうです。送り手は使い捨ての共通鍵を作り、相手の公開鍵で暗号化して送ります。相手は自分の秘密鍵で復号し、共通鍵を取り出します。あとは、2人だけが持つ共通鍵でやりとりできます。重い荷物そのものではなく、「荷物の鍵」だけを南京錠つきの小箱で送るイメージです。実際のHTTPSでは、さらに工夫された**鍵交換**という方法で共通鍵を共有しています（7-4）。

### ハッシュ関数 ― データの指紋

暗号と並ぶ重要な道具が、第4章のハッシュテーブルで登場したハッシュ関数です。ハッシュ関数は、どんな長さのデータからでも、決まった長さの短い値を作り出します。セキュリティで使うのは、後で見る特別な性質を持たせたもので、暗号学的ハッシュ関数とも呼ばれます。作り出される値を**ハッシュ値**と呼びます。よく使われるSHA-256では、ハッシュ値は常に256ビットです。

Pythonの標準ライブラリhashlibで、「Hello」と「hello」のSHA-256のハッシュ値を計算してみましょう。ハッシュ関数が受け取るのはバイトの並びなので、第2章で見たencodeでUTF-8のバイト列に直してから渡します。hexdigest()は、ハッシュ値を16進数の文字列で返します。

```python
import hashlib

for text in ["Hello", "hello"]:
    data = text.encode("utf-8")
    print(text, hashlib.sha256(data).hexdigest())
```

```text
Hello 185f8db32271fe25f561a6fc938b2e264306ec304eda518007d1764826381969
hello 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824
```

16進数の1桁は4ビットなので、256ビットは64桁です。大文字と小文字が1文字違うだけで、ハッシュ値はまったく別物になりました。入力をどれだけ長くしても、結果は64桁のままです。暗号に使うハッシュ関数には、次のような性質があります。

- 同じデータからは、必ず同じハッシュ値ができる
- 少しでも違うデータからは、まったく違うハッシュ値ができる
- ハッシュ値から元のデータを求めることは、事実上できない（一方向性）
- 同じハッシュ値になる別々のデータを見つけることは、事実上できない

4つ目には補足が必要です。第4章では、ハッシュテーブルの衝突は起きるものだと説明しました。入力は無数にあり、ハッシュ値は有限なので、SHA-256でも衝突する組は必ず存在します。違いは、見つけられるかどうかです。棚の数が少ないハッシュテーブルと違い、SHA-256のハッシュ値は2の256乗通りもあり、衝突を見つける現実的な方法は知られていません。衝突は存在するが、見つけられない。これが暗号に使うハッシュ関数の条件です。

ハッシュ値は、データの「指紋」のようなものです。指紋から本人の顔は再現できませんが、本人かどうかは照合できます。

この性質は、**改ざん**の検知に役立ちます。配布ファイルを受け取ったら、自分で計算したハッシュ値を、開発元から信頼できる経路で得た値と照合します。ただし、ファイルと掲示された値の両方を書き換えられると、照合は通ってしまいます。配布元も確かめたいときは、次の節のデジタル署名を使います。

ハッシュ関数は、暗号化とは別物です。暗号文は鍵があれば平文に戻せますが、ハッシュ値は元に戻せません。この性質が、7-5で見るパスワードの保存にも生かされています。なお、MD5やSHA-1は、弱点が見つかったため、安全性が求められる用途では使われなくなっています。

エンジニアにとって大切なのは、暗号を自分で発明しないことです。自作の暗号は、たいてい思わぬ弱点を抱えます。実務では、専門家が長年検証してきたAESやSHA-256のような標準的な方式を、信頼できるライブラリを通じて使います。

## 7-4　相手を確かめ、改ざんを見抜く ― デジタル署名と電子証明書

暗号を使えば、通信の途中で中身を盗み見られるリスクは大きく下がります。しかし、まだ大きな問題が残っています。暗号化して送った相手が、そもそも本物のショッピングサイトなのか、という問題です。

7-3のハイブリッド方式を思い出してください。あなたのブラウザーは、ショッピングサイトから届いた南京錠（公開鍵）で、共通鍵を入れた小箱を閉めて送ります。ところが、その南京錠が途中ですり替えられていたらどうでしょう。攻撃者が自分の南京錠を「ショッピングサイトの南京錠です」と偽って渡していたら、小箱は攻撃者に開けられ、そのあとに送るカード番号も読まれてしまいます。暗号化は完璧でも、相手を取り違えれば意味がありません。このように、他人のふりをすることを**なりすまし**といいます。また、通信の間に割り込んで双方になりすます攻撃は、**中間者攻撃**と呼ばれます。

なお、現在のHTTPS（TLS 1.3）は、サイトの公開鍵で共通鍵を閉めて送る方式を使わず、公開鍵を署名の確認にだけ使います。それでも、「受け取った公開鍵は本当に相手のものか」という問題は共通です。これを確かめる技術が、デジタル署名と電子証明書です。

### デジタル署名 ― 本人にしか作れない印

紙の書類では、手書きのサインや印鑑で「本人が書いた」ことを示します。これをデジタルの世界で実現するのが**デジタル署名**です。7-3では、公開鍵で閉じて、秘密鍵で開けました。デジタル署名では、秘密鍵で署名を作り、公開鍵で署名を確かめます。署名を作れるのは秘密鍵の持ち主だけです。一方、公開鍵は誰でも手に入るので、署名が本物かどうかは誰でも確かめられます。

文書のハッシュ値を使う方式では、次のように進みます（細部は方式によって異なります）。

1. 送り手は、送りたい文書のハッシュ値を計算する
2. 送り手は、そのハッシュ値と自分の秘密鍵から、署名を作る
3. 送り手は、文書と署名をいっしょに送る
4. 受け手は、届いた文書のハッシュ値を自分でも計算する
5. 受け手は、送り手の公開鍵を使って署名を検証し、手順4のハッシュ値と対応しているかを確かめる

検証に成功すれば、その文書に対して、公開鍵と対になる秘密鍵で署名が作られたと確認できます。文書が書き換えられていれば、検証は通りません。ただし、署名を特定の人や組織に結び付けるには、その公開鍵が誰のものかを確かめる必要があります。

文書をハッシュ値にまとめるのは、効率のためです。公開鍵暗号の重い計算を、短いハッシュ値に対してだけ行えば済みます。

デジタル署名は、身近なところで使われています。スマホのOSやアプリの更新プログラムには開発元の署名が付いており、端末はそれを確かめてからインストールします。途中で差し替えられていれば、署名の検証で見抜けるわけです。

### 電子証明書と認証局

しかし、署名を確かめるための公開鍵が本物かどうかは、どうやって確かめればよいのでしょうか。ここで登場するのが、信頼できる第三者です。現実の世界では、市区町村が発行する印鑑登録証明書が、印鑑が本人のものだと保証してくれます。インターネットで同じ役割を果たすのが、**認証局**（CA：Certificate Authority）です。

認証局は、申請者がそのドメイン名を管理していることを確かめたうえで、**電子証明書**を発行します。証明書の種類によっては、申請した組織が実在することも確かめます。電子証明書は「この公開鍵は、このドメイン名（またはこの組織）のものです」と証明するデジタルの書類です。持ち主のドメイン名と公開鍵、有効期限、発行した認証局の名前などが書かれ、認証局のデジタル署名が付いています。この署名があるので、内容が改ざんされていないことと、確かに認証局が発行したことを確かめられます。

### 信頼の連鎖

では、認証局の公開鍵が本物だと、どうして分かるのでしょうか。実際のしくみでは、認証局は階層構造になっています。Webサイトの証明書には、中間の認証局が署名しています。中間の認証局の証明書には、さらに上位の認証局が署名しています。そして最上位にあるのが、**ルート認証局**です。こうして証明書を順にたどって確かめていくしくみを、**信頼の連鎖**（チェーン・オブ・トラスト）と呼びます。

連鎖の出発点となるルート認証局の証明書は、OSやブラウザーにあらかじめ組み込まれています。OSやブラウザーの開発元が審査した認証局だけが登録されています。私たちは端末を手にした時点で、信頼の出発点を受け取っているのです。

### HTTPS（TLS）の接続で起きていること

ここまでの道具を組み合わせると、冒頭の疑問に答えられます。第6章で見たHTTPSは、HTTPの通信をTLSで守ったものです。**TLS**（Transport Layer Security）は、通信の暗号化と相手の確認を行うプロトコルです。前身がSSLと呼ばれていたため、今でも「SSL/TLS」と呼ばれることがあります。

ブラウザーがHTTPSのサイトにつなぐとき、本題のやりとりの前に、次のような準備が行われます（図7-2）。最新のTLS 1.3を例に、流れを単純化して説明します。

1. ブラウザーが、自分が使える暗号の方式と、鍵交換のための材料を送る
2. サーバーが、使う方式を決めて、自分側の鍵交換の材料を返す
3. 双方が、交換した材料から、それぞれ同じ共通鍵を計算する。これ以降のやりとりは暗号化される
4. サーバーが、自分の電子証明書を送る
5. サーバーが、ここまでのやりとり全体に対する署名を送る。署名の対象には、手順1と2の鍵交換の材料も含まれる。署名は、証明書の公開鍵と対になる秘密鍵で作る
6. サーバーが、やりとりの完了を確かめるための値（Finished）を送る
7. ブラウザーが、証明書と署名とFinishedを検証し、自分のFinishedを返す。証明書については、認証局の署名をルート証明書までたどり、ドメイン名が接続先と一致するか、有効期限内かなどを確かめる。署名は、証明書の公開鍵で検証する
8. 確認がすべて済んだら、HTTPのやりとりを共通鍵暗号で暗号化して始める

手順3がポイントです。共通鍵そのものはネットワークに流れません。双方が、交換した材料と、手元に残した秘密の値から、数学的なしくみで同じ鍵を導き出します。これが7-3で触れた鍵交換です。送るのは見られてもよい材料だけなので、途中で盗み見ても共通鍵は計算できません。

しかも、材料と秘密の値は接続のたびに新しく作り、鍵を計算したら捨てます。共通鍵はこの使い捨ての値から計算し、証明書の秘密鍵は手順5の署名にしか使いません。そのため、将来サーバーの証明書の秘密鍵が漏れても、過去の接続の共通鍵は計算できません。通信を記録しておいた攻撃者にも、過去の内容は解読できないのです。この性質を**前方秘匿性**と呼びます。7-3で説明した、共通鍵を相手の公開鍵で閉めて送る方式では、こうはいきません。共通鍵が毎回使い捨てでも、秘密鍵が漏れれば、記録しておいた小箱を開けて過去の共通鍵を取り出せるからです。TLS 1.3では、この方式は廃止されました。

手順5の署名は、中間者攻撃を防ぐ要です。証明書は公開されている情報なので、攻撃者でもコピーして送れます。しかし、対応する秘密鍵がなければ署名は作れません。では、攻撃者が間に割り込み、鍵交換の材料を自分のものにすり替えたらどうなるでしょうか。署名の対象には鍵交換の材料が含まれるので、ブラウザーが受け取ったやりとりと、サーバーが署名したやりとりが食い違い、検証は失敗します。本物の署名を別の接続から写してきても使えません。材料は接続ごとに違い、署名の対象も毎回変わるからです。こうしてブラウザーは、「いま鍵を共有した相手は、証明書の秘密鍵の持ち主だ」と判断できます。

手順6と7のFinishedは、共通鍵をもとに作る確認の値です。双方が同じ鍵を計算できたことと、やりとりが途中で書き換えられていないことを確かめ合います。検証のどこかで失敗すれば、ブラウザーは警告を表示して接続を止めます。なお、実際には手順2から6までをサーバーがまとめて送り、往復の回数を減らしています。

![図7-2　HTTPS接続で証明書を確かめて暗号化通信を始めるまで](../figures/fig-7-2.svg)

共通鍵は交換した材料から双方で計算され、ブラウザーが証明書と署名、Finishedを確かめたあとで、本題のHTTPのやりとりが始まります。

暗号化された通信では、データが途中で書き換えられていないかも確かめられます。HTTPSは、機密性と完全性を守り、相手が本物であることまで確かめるしくみなのです。

### 鍵マークの意味と限界

ブラウザーのアドレスバーの鍵マークは、2つのことを示しています。通信が暗号化されていること。そして、表示中のドメイン名について、正しい証明書が確認できたことです。

鍵マークは「このサイトは安全で信頼できる」という意味ではありません。ドメイン名の管理者であることだけを確認して発行される証明書があるので、攻撃者が自分で取得したドメイン名で偽サイトを作り、正規の証明書を取ることもできます。実際、フィッシングサイトの多くもHTTPSを使っています。

本物のドメイン名に1文字だけ違う文字を混ぜた偽サイトでも、鍵マークは表示されます。そのドメイン名が本当に目的の相手かは、利用者が確かめるしかありません。こうした誤解を避けるため、Chromeは、2023年に公開したバージョン117から、鍵マークを、設定を表す別のアイコンに置き換えました。

エンジニアにとっての教訓は2つあります。1つは、自分が作るサービスは必ずHTTPSで提供することです。もう1つは、証明書の期限切れに注意することです。更新を忘れるとサイトに警告が出て、利用者がアクセスできなくなります。しかも、有効期間の上限は年々短くなっています。認証局とブラウザーの開発元でつくる団体（CA/Browser Forum）の取り決めで、新しく発行する証明書の最長の有効期間は、2026年3月15日から200日になりました。2027年3月15日からは100日、2029年3月15日からは47日に縮まる予定です。期間が短いほど、秘密鍵が漏れたときなどの影響は小さくなりますが、人手での更新は追いつかなくなります。そこで、更新の自動化が前提になっています。

## 7-5　本人であることを確かめる ― 認証のしくみ

7-4では、通信相手のサーバーが本物かを確かめるしくみを見ました。この節では逆に、サービスが利用者を確かめるしくみを見ていきます。画面の向こうにいるのが本当にあなたなのかを、サービスはどうやって判断しているのでしょうか。

### 認証と認可

**認証**（authentication）は、相手が名乗ったとおりの本人かを確かめることです。IDとパスワードでログインするのが、その代表です。**認可**（authorization）は、確かめた相手に、何をしてよいかの権限を与えることです。

会社のビルでいえば、入口で社員証を見せて本人だと確かめてもらうのが認証、入れるフロアが部署ごとに決まっているのが認可です。SNSなら、ログインが認証です。自分の投稿は削除できても、他人の投稿は削除できない。これが認可です。

エンジニアは「ログインしているか」だけでなく、「この人にこの操作を許してよいか」も、操作のたびに確かめる必要があります。確認が漏れると、ログインした利用者が他人のデータを見られてしまいます。

### 認証の3要素

本人を確かめる手がかりは、大きく3種類に分けられます。

表7-5　認証の3要素

| 要素 | 内容 | 例 |
| --- | --- | --- |
| 知識情報 | 本人だけが知っていること | パスワード、暗証番号、秘密の質問 |
| 所有情報 | 本人だけが持っているもの | スマホ、ICカード、ハードウェアのセキュリティキー |
| 生体情報 | 本人の身体的な特徴 | 指紋、顔、静脈、虹彩 |

それぞれに弱点があります。知識情報は、推測されたり、だまし取られたりします。所有情報は、紛失や盗難のおそれがあります。生体情報は忘れたりなくしたりしませんが、もし偽造されても、パスワードのように変更できません。

### サービスはパスワードをどう保存しているか

ログインのとき、サービスは入力されたパスワードを、登録されたものと照らし合わせます。では、登録されたパスワードは、データベースにそのまま保存されているのでしょうか。もしそうなら、データベースが流出した瞬間に、全員のパスワードが知られてしまいます。サービスの管理者が利用者のパスワードを見られるのも問題です。

そこで使われるのがハッシュ関数です。サービスはパスワードそのものではなく、そのハッシュ値を保存します。ログインのときは、入力されたパスワードのハッシュ値を計算し、保存してある値と一致するかを確かめます。ハッシュ値から元のパスワードは求められないので、データベースが流出しても、パスワードをすぐには知られずにすみます。

ただし、これだけでは不十分です。よく使われるパスワードについては、ハッシュ値をあらかじめ計算した一覧表を用意できます。流出したハッシュ値をその表と突き合わせれば、元のパスワードが分かります。また、同じパスワードの人は同じハッシュ値になるので、1人分が分かれば、まとめて分かってしまいます。

この対策が**ソルト**です。ソルトは、利用者ごとに作るランダムな値です。パスワードとソルトをつなげてからハッシュ値を計算し、ソルトとハッシュ値をいっしょに保存します。同じパスワードでもソルトが違えばハッシュ値はまったく別物になります。

次の例で確かめましょう。ソルトをパスワードの前につなげて、SHA-256で計算します。これはしくみを見るための実演で、実際の保存方法ではありません（理由はこのあと説明します）。ソルトは本来、登録のたびに乱数で作りますが、ここでは決まった値を書いています。

```python
import hashlib

def demo_hash(password, salt):
    text = salt + password    # ソルトを前につなげる
    return hashlib.sha256(text.encode("utf-8")).hexdigest()

password = "sakura2024"
print(demo_hash(password, ""))
print(demo_hash(password, "3b9f61c27ad04e85b1f0c6d2957e4a18"))
print(demo_hash(password, "e07a54d19c3b4f6a82d5b3f9160c7e2d"))
```

```text
e062713d6cf2e88246be0319adf817c07a2baef1639a1ef6b9d9b2a021abdef5
4eb6d45b505d24c84212443bf504cda2c2c28ec682be430292ea639fc06ded96
4a2b022f4594e8752f6168102485812bda758102a5195f7e146c511d90ea3454
```

1行目はソルトなし、2行目と3行目は、別々の利用者のソルトを付けた結果です。同じパスワードなのに、ハッシュ値に共通点はありません。これで、あらかじめ用意した一覧表は役に立たなくなります。攻撃者は、利用者1人ずつ、ソルトごとに計算し直さなければなりません。ソルトは秘密にする値ではなく、ハッシュ値と並べて保存します。例のソルトは、16バイト（128ビット）を16進数32桁で書いたものです。米国の標準技術研究所（NIST）の指針SP 800-63B-4は32ビット以上を求めており、実務では16バイト程度がよく使われます。

さらに実務では、SHA-256のような汎用のハッシュ関数をそのままパスワードの保存には使いません。速く計算できるように作られているので、攻撃者も候補を高速に試せてしまうからです。代わりに、わざと時間がかかるように作られた、パスワード保存専用の関数を使います。**bcrypt**、scrypt、**Argon2**などが代表例です。基本の考え方は、ハッシュ値の計算を何万回もくり返すことです。次の例は、その考え方だけを取り出した実演です。digest()はハッシュ値をバイト列で返し、hex()はそれを16進数の文字列に直します。

```python
import hashlib

salt = "3b9f61c27ad04e85b1f0c6d2957e4a18"
value = (salt + "sakura2024").encode("utf-8")
for i in range(100000):
    value = hashlib.sha256(value).digest()
print(value.hex())
```

```text
fdbff0bfac49df554ea9b60b6b69ff4edf5612a95a6bc86cf492586ceb8b97af
```

10万回くり返しても、1回のログインなら一瞬です。一方、攻撃者は候補を1つ試すたびに10万回の計算が必要になり、同じ時間で試せる候補は10万分の1に減ります。ここにもトレードオフがあります。遅くするほど安全ですが、ログインのたびにサーバーの計算も増えます。そこで、利用者が待たされたと感じない範囲で、できるだけ遅く設定します。実際の専用関数は、大量のメモリも使わせるなど、さらに工夫をしています。自分で組み立てず、信頼できるライブラリのものを使ってください。

エンジニアにとっての鉄則は明らかです。パスワードは平文でも暗号化でもなく、ソルトを付けて、専用の関数でハッシュ値にして保存します。「パスワードを忘れた」利用者に元のパスワードを送ってくるサービスがあれば、平文か、元に戻せる形で保存している証拠です。

### パスワードを使い回すと危険な理由

ここまで来ると、7-2で見たパスワードリスト攻撃が、なぜ脅威なのかがはっきりします。どれほど推測しにくいパスワードを作っても、それを保存するのはサービスの側です。どこかのサービスが、平文や、ソルトなしの速いハッシュ関数で保存していて、それが流出すれば、パスワードは攻撃者の手に渡ります。使い回しをすると、あなたの安全は、使っている中で最も守りの弱いサービスに左右されるのです。

対策は、サービスごとに異なるパスワードを使うことです。数十ものパスワードは覚えられないので、**パスワードマネージャー**を使います。サービスごとに長くランダムなパスワードを作り、安全に保管してくれます。正しいサイトでだけ自動入力されるので、フィッシングサイトに気づくきっかけにもなります。

### 強いパスワードの条件 ― 長さと、いまの指針

では、総当たり攻撃に強いのは、どんなパスワードでしょうか。候補の数を計算してみましょう。使える文字がk種類で、長さがn文字なら、候補はkのn乗通りです。英小文字だけなら26種類、英大文字、英小文字、数字、記号をすべて使うと、キーボードで打てる文字は94種類あります。Pythonでは、べき乗を「`**`」で書きます。

```python
for length in [8, 12, 16]:
    print(length, 26 ** length, 94 ** length)
```

```text
8 208827064576 6095689385410816
12 95428956661682176 475920314814253376475136
16 43608742899428874059776 37157429083410091685945089785856
```

左から、長さ、英小文字だけの場合、94種類を使う場合の候補の数です。英小文字だけの16文字（約4.4×10の22乗通り）は、94種類を使った8文字（約6.1×10の15乗通り）の約700万倍あります。文字の種類を増やすより、長くするほうがずっとよく効くのです。仮に、流出したハッシュ値を手元で調べる攻撃者が、1秒に100億個の候補を試せるとしましょう。94種類の8文字は約7日で試し尽くせますが、英小文字だけの16文字は約14万年かかります。ただし、これは文字をでたらめに選んだ場合の話です。単語や誕生日をもとにしたパスワードは、辞書攻撃で先に試されます。

こうした事情から、パスワードの指針は以前と変わりました。NISTのSP 800-63B-4は、サービス側に次のことを求めています。

- パスワードだけで認証する場合は15文字以上を求める（多要素認証と組み合わせる場合でも8文字以上）。64文字以上の長いパスワードも受け付ける
- 「大文字と記号を必ず混ぜる」といった文字の種類の強制をしない
- 定期的な変更を強制しない。流出した証拠があるときには変更させる
- 登録や変更のとき、よく使われるパスワードや流出したパスワードの一覧と照合し、当てはまれば受け付けない
- パスワードマネージャーの自動入力や、貼り付けでの入力を妨げない

以前の常識と逆に見える項目には、理由があります。文字の種類を強制されると、多くの人は「`Password1!`」のような予想しやすい形で条件を満たします。定期的な変更を強制されると、末尾の数字を1つ増やすような変え方や、使い回しが増えます。手間のわりに、推測しやすいパスワードが増えてしまうのです。日本でも、総務省の「国民のためのサイバーセキュリティサイト」が、流出した事実がなければ定期的な変更は不要で、使い回しのない固有のパスワードにすることが大切だと案内し、パスワード管理ツールの利用も勧めています。なお、NISTが禁じているのはサービスによる強制で、利用者が自分で文字の種類を混ぜるのは差し支えありません。

利用者は、パスワードを長くし、サービスごとに別のものにして、パスワードマネージャーに覚えさせます。どうしても覚える必要があるものは、無関係な単語をいくつもつなげた長いものにします。

### 多要素認証

パスワードを使い回さなくても、フィッシングでだまし取られる可能性は残ります。そこで、認証の3要素のうち異なる2つ以上を組み合わせます。これを**多要素認証**（MFA：Multi-Factor Authentication）といいます。2つの要素を使う場合は、**二要素認証**とも呼びます。

身近な例は、パスワードを入力したあと、スマホのアプリに表示される6桁の数字を入力する方式です。この数字は30秒ほどで変わる使い捨てのもので、**ワンタイムパスワード**と呼ばれます。パスワード（知識）と、スマホ（所有）の2つを確かめているわけです。

多要素認証の強みは、1つの要素が破られても、それだけでは突破されないことです。パスワードが流出しても、攻撃者があなたのスマホを持っていなければ、ログインできません。確認が増えるぶん手間も増える、安全性と使い勝手のトレードオフですが、得られる安全のほうがずっと大きいので、重要なサービスでは設定しておきましょう。

「多段階」と「多要素」は違います。パスワードの入力後に秘密の質問に答える方式は、確認が2段階あっても、どちらも知識情報なので多要素認証ではありません。同じ種類の要素は、同じ方法でまとめて盗まれるおそれがあるからです。

ただし、多要素認証も万能ではありません。偽サイトが、入力されたパスワードとワンタイムパスワードを、その場で本物のサイトに転送する手口も知られています。

数字を入力する代わりに、スマホに届く「ログインを許可しますか」という通知で承認を押すだけの方式もあります。手軽ですが、パスワードを手に入れた攻撃者がログインを何度もくり返して通知を大量に届け、根負けや押し間違いによる承認を待つ手口があります（多要素認証疲労攻撃）。身に覚えのない通知は、決して承認してはいけません。パスワードが漏れている合図でもあるので、パスワードを変更します。

### パスキー ― パスワードのいらない認証

パスワードの弱点を根本から解決しようとするのが、**パスキー**です。FIDOアライアンスとW3Cが中心になって標準化を進めてきた技術で、主要なOSやブラウザーが対応しています。

パスキーのしくみは、公開鍵暗号の応用です。利用者がサービスにパスキーを登録すると、端末の中で鍵の組が作られます。秘密鍵は端末の中に厳重に保管され、公開鍵だけがサービスに送られます。秘密鍵は、同じ利用者の端末どうしで暗号化したまま同期されることはあっても、サービスに送られることはありません。

ログインのときは、サービスが毎回違うランダムなデータを送ってきます。端末は、指紋や顔、画面ロックの暗証番号で本人を確かめてから、秘密鍵でそのデータに署名して返し、サービスは登録された公開鍵で検証します。デジタル署名で本人を確かめているのです。

この方式には、大きな利点があります。

- サービス側には公開鍵しか保存されないので、流出しても悪用できない
- 秘密鍵はサービスに送られないので、通信を盗み見られても問題ない
- パスキーは登録したサービスのドメインに結びついているので、偽サイトではそもそも使えない
- 利用者は、複雑なパスワードを覚える必要がない

特に3つ目が重要です。どんなに精巧な偽サイトでも、ドメイン名が違えば、端末はパスキーを使いません。人の注意力に頼らずに、フィッシングを防げるのです。ただし、パスキーを登録しても、パスワードでのログインが残っているサービスは少なくありません。その場合、偽サイトにパスワードを入力してしまう危険は残るので、パスワードの側にも多要素認証を設定しておきます。端末（所有）と指紋や暗証番号（生体・知識）を組み合わせるので、パスキーは多要素認証の性質も備えています。

サービスを作るときは、パスワードを正しく保存したうえで、多要素認証やパスキーを選べるようにすることが、利用者を守ることにつながります。

## 7-6　システムとデータを守るために

最後に、立場を変えてみましょう。あなたがエンジニアとして、SNSのようなサービスを作り、運用する側になったとします。7-1で見たように、守りは1つでは足りません。いくつもの対策を重ねて、どれか1つが破られても全体は守られるようにします。これを**多層防御**と呼びます。

### ファイアウォール ― 入口で通信をふるい分ける

最初の守りは、ネットワークの入口です。**ファイアウォール**は、ネットワークの境目に置き、そこを流れる通信を調べて、許可されたものだけを通すしくみです。

ファイアウォールは、建物の受付にいる警備員にたとえられます。警備員は、荷物の宛先と差出人の住所（IPアドレス）、届け先の部屋番号（ポート番号）を見て、通すかどうかを決めます。たとえばWebサーバーなら、HTTPSの443番の窓口あての通信だけを通します。管理用の窓口あての通信は、社内のネットワークからに限ります。このように、必要な通信以外はすべて止めておくのが基本です。

ただし、ファイアウォールは主に宛先や送信元を見て判断するので、中身までは十分に調べられません。正規の窓口に届いた通信に攻撃が紛れていると、素通りさせてしまいます。そこで、**WAF**（Web Application Firewall）なども組み合わせて使います。WAFは、Webアプリケーションへの通信の中身を調べて、攻撃らしいものを止めるしくみです。

### ネットワークを区切り、見張る ― DMZ・IDS・IPS・VPN

公開するサーバーを社内のネットワークと同じ場所に置くと、そのサーバーが乗っ取られたときに、社内まで一気に入り込まれます。そこで、外部に公開するWebサーバーなどは、インターネットとも社内とも区切った中間の区画に置きます。この区画を**DMZ**（DeMilitarized Zone：非武装地帯）と呼びます。ファイアウォールで、インターネットからDMZへは必要な通信だけを通し、DMZから社内へは、さらに限られた通信だけを通します。顧客情報を持つデータベースサーバーは社内側に置きます。

通したあとの通信を見張るしくみもあります。**IDS**（Intrusion Detection System：侵入検知システム）は、通信やサーバーの動きを監視し、攻撃の特徴に合うものや、ふだんと違う動きを見つけて管理者に知らせます。**IPS**（Intrusion Prevention System：侵入防止システム）は、その通信を遮断するところまで行います。自動で止めるIPSは対応が速い反面、正常な通信を誤って止めるおそれがあります。IDSは業務を妨げませんが、人が対応するまで攻撃は続きます。ここにもトレードオフがあります。

社外から社内のシステムを使うときは、第6章で見たVPNで、インターネットの上に暗号化された通り道を作ります。ただし、VPNの入口になる機器は、インターネットのどこからでも届く場所にあります。その脆弱性や弱いパスワードが侵入口になりやすいので、次に見るアップデートと、多要素認証が欠かせません。

### 脆弱性とアップデート

ソフトウェアは人が作るものなので、脆弱性をゼロにすることはできません。脆弱性が見つかると、開発元は修正プログラムを配布します。これを**パッチ**、または**セキュリティアップデート**と呼びます。ところが、修正が公開されると、攻撃者もその内容を調べて攻撃に使います。そのため、パッチを適用せずに放置したシステムは、格好の標的になります。修正が提供される前の脆弱性をつく攻撃もあり、**ゼロデイ攻撃**と呼ばれます。

エンジニアは、自分のシステムがどのソフトウェアのどのバージョンを使っているかを把握しておく必要があります。日本では、JVN（Japan Vulnerability Notes）というポータルサイトで、脆弱性と対策の情報が公開されています。こうした情報を確認し、計画的にアップデートを適用する運用が欠かせません。

### Webアプリケーションの代表的な脆弱性

作る側として注意すべき脆弱性もあります。ここでは、Webアプリケーションの代表的な3つを紹介します。はじめの2つは、利用者が入力したデータを、プログラムが命令や画面の一部として扱ってしまうことが原因です。3つ目は、ブラウザーがCookieを自動で送るしくみを突くものです。

1つ目は**SQLインジェクション**です。アプリケーションは、SQL（第5章）でデータベースに命令を送ります。ログイン画面に入力された名前でデータベースを検索するとき、入力された文字列をSQL文にそのままつなげて組み立てると、危険が生まれます。

```text
（危険な例）入力された文字列を、そのままSQL文の中に貼り込んで組み立てる
"SELECT * FROM users WHERE name = '" + 入力された名前 + "'"
```

たとえば「'」（シングルクォーテーション）は、SQLでは文字列の区切りを表します。この記号を含む細工された入力によって、検索の条件が書き換えられてしまうのです。その結果、本来見えないはずのデータが表示されたり、データが消されたりします。データとして渡したはずの入力が、命令の一部として実行されてしまうわけです。

対策の基本は、**プレースホルダー**を使うことです。SQL文の中で、値が入る場所をあらかじめ記号で示しておきます。そして、値はSQL文とは別に、データベースへ渡します。

```sql norun
-- 安全な例：値の入る場所を「?」で示しておく（プレースホルダー）
SELECT * FROM users WHERE name = ?;
-- 入力された名前は、命令とは別に「値」として渡される
```

こうすれば、データベースは先に命令の形を確定させます。そのあとで受け取った入力は、どんな記号を含んでいても、ただの値として扱われます。命令とデータを混ぜないことが、根本的な対策になるのです（図7-3）。

![図7-3　SQLインジェクションとプレースホルダーによる対策（概念図）](../figures/fig-7-3.svg)

入力をそのままつなげると命令とデータが混ざりますが、プレースホルダーでは命令と値が別々に届くため、入力が命令として実行されません。

2つ目は**クロスサイトスクリプティング**（XSS：Cross-Site Scripting）です。掲示板やSNSのように、利用者の入力をWebページに表示するアプリケーションで起こります。入力された文字列をそのままHTMLに埋め込むと、その中のタグ（HTMLで見出しやリンクなどを指定する記号）やスクリプト（JavaScriptなどで書かれた短いプログラム）を、ブラウザーがページの一部として解釈してしまいます。悪意ある人がスクリプトを仕込めば、ページを見た他の利用者のブラウザーで、それが実行されます。ログイン状態を乗っ取られたり（第6章で見たCookieの悪用など）、偽の入力画面を表示されたりする被害につながります。

対策の原則は、入力が命令として解釈されない形にしてから出すことです。必要な処理は、出力する場所によって違います。

基本になるのは、HTMLの中に文字として表示する場合です。このときは**エスケープ**を行います。HTMLで特別な意味を持つ文字を、画面にその文字として表示するための別の表記に置き換えてから出力します。

```text
エスケープの例（左の文字を、右の表記に置き換えて出力する）
<  →  &lt;
>  →  &gt;
&  →  &amp;
"  →  &quot;
'  →  &#39;
```

「`<`」と「`>`」はタグの始まりと終わりを、「`&`」は上のような別の表記の始まりを表します。「`"`」と「`'`」は、タグの中に書く設定値（属性値）を囲む文字です。リンクを表すタグ `<a href="…">` の「…」に入力を入れる場合、入力に「`"`」があると、そこで値が終わったことになり、続きがタグの一部として解釈されます。5つの文字をすべて置き換えておけば、本文でも、引用符で囲んだ属性値でも、入力はただの文字として表示されます。データを命令として解釈させないという考え方は、SQLインジェクションの対策と同じです。

ほかの場所では、この置き換えだけでは足りません。JavaScriptで画面に文字を差し込むときは、文字列をHTMLとして解釈させず、文字のまま置く方法（textContentというしくみ）を使います。リンク先のURLを入力から作るときは、httpsなど、許可する方式で始まっているかを検査します。「javascript:」で始まるURLは、クリックするとスクリプトとして実行されるので、5つの文字を置き換えても危険だからです。スクリプトの中や、クリックしたときの動作を書く属性（イベント属性）に、入力を直接埋め込むことは避けます。

Webアプリケーションのフレームワーク（開発によく使う機能をまとめた、土台となるソフトウェア）の多くは、標準でエスケープを行います。それでも、しくみを理解していないと、うっかり外してしまう事故が起こります。

3つ目は**クロスサイトリクエストフォージェリ**（CSRF：Cross-Site Request Forgery）です。forgeryは偽造という意味で、利用者のブラウザーから、本人が意図しないリクエストを送らせる攻撃を指します。第6章で見たように、ログインした状態はCookieで保たれ、ブラウザーはそのサイトあてのリクエストにCookieを自動で付けます。CSRFは、ここにつけこみます。

利用者がショッピングサイトにログインしたまま、攻撃者が用意した別のページ（罠サイト）を開いたとします。罠サイトには、ショッピングサイトへ「届け先の住所を変更する」というリクエストを送らせるしかけがあります。ブラウザーはこのリクエストにもショッピングサイトのCookieを付けるので、サーバーからは本人の操作に見えます（図7-4）。攻撃者は、Cookieを盗んではいません。自動で付くしくみを利用しただけです。XSSは利用者のブラウザーで攻撃者のスクリプトを動かす攻撃、CSRFは利用者のブラウザーから攻撃者の望むリクエストを送らせる攻撃です。

![図7-4　CSRFのしくみとCSRFトークンによる対策（概念図）](../figures/fig-7-4.svg)

罠サイトをきっかけにしたリクエストにもCookieは付きますが、トークンは罠サイトには分からないので、サーバーは偽のリクエストを見分けられます。

対策は、リクエストが自分のサイトの画面から送られたものかを、サーバーが確かめることです。代表的な方法では、サーバーが画面を返すときに、推測できないランダムな値（**CSRFトークン**）を埋め込み、変更の操作を受け取るときに、その値が添えられているかを照合します。罠サイトはこの値を知らないので、正しいリクエストを作れません。もう1つの方法は、CookieにSameSiteという属性を付け、別のサイトをきっかけにしたリクエストにはCookieを付けないようブラウザーに指示することです。多くのフレームワークがこれらのしくみを備えているので、無効にせずに使います。なお、XSSの脆弱性があると、攻撃者のスクリプトが画面からトークンを読み取れるので、CSRFの対策も破られます。

#### 修正問題　エスケープしたら「&」が増えた

XSSの対策として、HTMLに表示する文字をエスケープする関数を作りました。replaceは、文字列の中の指定した部分を、別の文字列にすべて置き換えるメソッドです。実行すると「`&amp;lt;`」のような余計な表記ができてしまいます。置き換えの順番をたどり、目標の出力になるように直しましょう。

ヒント：最初の置き換えで「`<`」は「`&lt;`」になります。その中の「`&`」は、3つ目の置き換えでどうなるでしょうか。

```python exercise=html-escape
def escape_html(text):
    text = text.replace("<", "&lt;")
    text = text.replace(">", "&gt;")
    text = text.replace("&", "&amp;")
    return text

print(escape_html("<b>Tom & Jerry</b>"))
```

目標の出力（修正後）

```text
&lt;b&gt;Tom &amp; Jerry&lt;/b&gt;
```

### バックアップ ― 最後の砦

ランサムウェアの被害や機器の故障、操作ミスが起きたときの最後の砦がバックアップです。**3-2-1ルール**という考え方があります。

- データのコピーを3つ持つ（元のデータを含む）
- 2種類の異なる媒体に保存する
- そのうち1つは、離れた場所に保管する

同じ建物にすべてのコピーがあれば、火災や地震で一度に失われます。ネットワークにつながったままのバックアップは、ランサムウェアにまとめて暗号化されるおそれもあるので、切り離した場所や、書き換えのできない形でも保管します。第5章でも触れたとおり、実際に元に戻せるかを定期的に試しておきましょう。

### 最小権限の原則

**最小権限の原則**は、利用者やプログラムには、仕事に必要な最小限の権限だけを与えるという考え方です。たとえば、Webアプリケーションがデータベースに接続するときのアカウントです。商品を表示するだけの機能なら、データを読む権限があれば十分で、テーブルを削除する権限は要りません。権限を絞っておけば、万一SQLインジェクションを突かれても、被害を小さく抑えられます。退職者や異動者の権限を速やかに外すことも、大切な対策です。

### ログと監視

ここでいうログは、誰が、いつ、どこから、何をしたかを、時刻とともに記録したものです（5-5で見たデータベースの変更のログとは、目的が異なります）。ログを監視していれば、深夜に大量のログイン失敗が続くといった異常に、早く気づけます。被害が起きたあとで、原因や範囲を調べる手がかりにもなります。

### 事故が起きたとき ― 最初の対応とCSIRT

どれだけ備えても、事故は起こりえます。セキュリティ上の事故や、その疑いのある出来事を**インシデント**と呼びます。これに対応する専門のチームが**CSIRT**（Computer Security Incident Response Team：シーサート）です。組織の窓口として報告を受け、調査、復旧、再発の防止、関係者への連絡を取りまとめます。

「パソコンがマルウェアに感染したかもしれない」と気づいたとき、最初の行動で被害の大きさが変わります。基本は3つです。まず、広がりを止めます。LANケーブルを抜く、Wi-Fiを切るなどして、機器をネットワークから切り離します。次に、記録を残します。あわてて初期化したりファイルを消したりすると、ログなどの痕跡が失われ、原因も被害の範囲も調べられなくなります。画面の表示や気づいた時刻も控えます。そして、すぐに報告します。自分だけで直そうとしたり、叱られるのを恐れて黙っていたりすると、そのあいだに被害が広がります。早く報告した人を責めないことも、組織的対策の1つです。

外部への報告が法律で義務づけられている場合もあります。**個人情報保護法**は、個人データの漏えいなどが起き、個人の権利や利益を害するおそれが大きい場合に、個人情報保護委員会への報告と本人への通知を、事業者に義務づけています。不正アクセスなど不正の目的による漏えいや、1,000人を超える漏えいなどが対象で、最初の報告は速やかに（おおむね3〜5日以内に）行うこととされています。

### エンジニアに求められる姿勢

セキュリティの知識は、守るためにも攻めるためにも使えます。だからこそ、法律と倫理を守ることが欠かせません。

日本には**不正アクセス禁止法**（不正アクセス行為の禁止等に関する法律）があります。他人のIDとパスワードを無断で使ってログインすることは、この法律で禁じられています。脆弱性を突いてアクセス制御をくぐり抜けることも同様です。たとえ興味本位でも、「ちょっと試しただけ」でも、犯罪になりえます。禁じられているのは、侵入そのものだけではありません。不正アクセスに使う目的で他人のIDやパスワードを手に入れること、そうして不正に手に入れられたものを保管すること、正当な理由なく他人のIDやパスワードを第三者に教えることも対象です。7-2で見たフィッシングも同じです。本物の運営者を装ってIDやパスワードを入力させる偽サイトを公開することや、そうした入力を求めるメールを送ることは、だまし取った情報を悪用する前の段階で、この法律により禁じられています。

また、刑法には「不正指令電磁的記録に関する罪」があります。正当な理由がないのに、他人のコンピューターで実行させる目的でマルウェアを作ること、人に提供すること、他人のコンピューターで実行される状態に置くことは、処罰の対象です。同じ目的で取得することや保管することも罰せられます。学習のために手口を調べるときも、試してよいのは、自分が管理する機器や、許可を得た環境の中だけです。

もし他人のサービスに脆弱性を見つけたら、自分で試したりせず、運営者や公的な窓口に知らせましょう。日本ではIPAが、ソフトウェアやWebサイトの脆弱性の届け出を受け付けています。セキュリティは、作る人、使う人、守る人が協力して支えるものです。

## コラム　AIとセキュリティ ― 攻撃にも防御にも使われる技術

生成AIの登場は、セキュリティの世界で、攻める側と守る側の両方に変化をもたらしています。

攻撃の側では、まずフィッシングメールが変わりました。不自然な日本語は、もう偽物を見分ける手がかりになりません。本人そっくりの声や映像を作る**ディープフェイク**も悪用され始めました。2024年には香港で、ビデオ会議に映った最高財務責任者（CFO）や同僚が実は偽物で、社員が約2億香港ドル（日本円で約38億円）を送金してしまった事件が報じられました。

一方、守る側もAIを活用しています。迷惑メールの判別には、以前から機械学習（大量のデータから規則性をコンピューターに学ばせる技術）が使われてきました。最近では、膨大なログから攻撃の兆しを見つけたり、ソースコードから脆弱性を探したりする用途にも広がっています。

AIそのものを狙う新しい脅威もあります。その1つが**プロンプトインジェクション**です。AIに読ませる文書やWebページの中に、命令に見える文章を紛れ込ませ、AIに本来とは違う動作をさせます。たとえば、メールを要約するAIが、メールの中に仕込まれた文章を自分への指示と取り違えます。データが命令として扱われる構造は、SQLインジェクションとよく似ています。ただし、AIは自然な言葉を柔軟に解釈するため、データと命令をはっきり分けることが難しいのです。そのため、AIに与える権限を必要な範囲に絞る、重要な操作の前には人が確認する、といった対策が重視されています。社外のAIサービスに機密情報をうっかり入力してしまうことも、情報漏えいの原因になりえます。

AIは新しい道具ですが、守りの考え方は変わっていません。送金の依頼は別の手段で本人に確かめる。多要素認証やパスキーを使う。AIにもシステムにも、必要以上の権限を与えない。本章で学んだ基本は、新しい技術が登場しても、そのまま足場として使えるのです。

## 修正問題の解答

### ログインできないのはなぜ？

check関数が、ソルトを付けずにハッシュ値を計算していました。保存してあるのは「ソルト＋パスワード」のハッシュ値なので、パスワードだけのハッシュ値とは、正しいパスワードでも一致しません。保存のときと同じmake_hashを、保存してあるソルトと一緒に使います。

```python answer=salt-login
import hashlib

def make_hash(password, salt):
    text = salt + password
    return hashlib.sha256(text.encode("utf-8")).hexdigest()

# 登録のときにサービスが保存した値
saved_salt = "7c1d0e9a4b6f43d2a85e3f1b9c0d2e64"
saved_hash = make_hash("tsubame-kaze-2031", saved_salt)

def check(password):
    hashed = make_hash(password, saved_salt)
    return hashed == saved_hash

print(check("tsubame-kaze-2031"))
print(check("tsubame-kaze-2032"))
```

実行結果は次のとおりです。

```text
True
False
```

サービスがソルトをハッシュ値と並べて保存しておくのは、照合のときに同じ計算をやり直すためです。

### 暗証番号は何通り？

「`length ** kinds`」を「`kinds ** length`」に直します。候補の数は、文字の種類（10）を、長さの回数だけ掛け合わせたものです。元のコードは左右が逆で、4の10乗と6の10乗を計算していました。

```python answer=pin-count
kinds = 10
for length in [4, 6]:
    print(length, kinds ** length)
```

実行結果は次のとおりです。

```text
4 10000
6 1000000
```

4桁の暗証番号は1万通りしかなく、総当たりには弱いといえます。それでもATMで使えるのは、キャッシュカードという所有情報と組み合わせた多要素認証であり、数回まちがえると使えなくなるからです。

### エスケープしたら「&」が増えた

「`&`」の置き換えを、最初に行うように順番を変えます。元のコードでは、先に「`<`」を「`&lt;`」に置き換え、そのあとで「`&`」を置き換えたので、「`&lt;`」の中の「`&`」まで「`&amp;`」に変わっていました。

```python answer=html-escape
def escape_html(text):
    text = text.replace("&", "&amp;")
    text = text.replace("<", "&lt;")
    text = text.replace(">", "&gt;")
    return text

print(escape_html("<b>Tom & Jerry</b>"))
```

実行結果は次のとおりです。

```text
&lt;b&gt;Tom &amp; Jerry&lt;/b&gt;
```

この関数は「`"`」と「`'`」を置き換えていないので、属性値の中に出力するには不十分です。実際の開発では自分で書かず、言語やフレームワークが用意している機能（Pythonなら標準ライブラリのhtml.escape）を使います。

## 第7章のまとめ

- 情報セキュリティとは、機密性・完全性・可用性（CIA）を保つことです。リスクはゼロにできないため、許容できる水準まで下げることを目指します。安全性と使い勝手はトレードオフの関係にあります。
- 身近な脅威には、マルウェア、フィッシング、不正アクセスがあります。ソーシャルエンジニアリング、DoS攻撃・DDoS攻撃、標的型攻撃、サプライチェーン攻撃もあります。
- 共通鍵暗号は速いものの、鍵を安全に渡すのが難しく、公開鍵暗号はその逆です。実際の通信では両者を組み合わせます。
- ハッシュ関数は、元に戻せない「データの指紋」を作り、改ざんの検知やパスワードの保存に使われます。
- デジタル署名と電子証明書によって、相手が本物であることを確かめられます。HTTPSは、暗号化と相手の確認を組み合わせた通信で、共通鍵は接続ごとの使い捨ての値から計算します。鍵マークは、サイトが信頼できることまでは保証しません。
- 認証は本人であることを、認可は何をしてよいかを確かめます。サービスは、パスワードにソルトを付け、わざと遅くした専用の関数で保存します。利用者は、長いパスワードをサービスごとに変え、多要素認証やパスキーを使います。
- システムを守る側は、いくつもの対策を重ねます。ファイアウォールとDMZ、アップデート、SQLインジェクション・XSS・CSRFへの対策、バックアップ、最小権限、ログの監視などです。事故が起きたら、切り離し、記録を残し、すぐに報告します。法律と倫理を守ることも欠かせません。

これで、本書で学ぶしくみはすべて出そろいました。最後に、ここまでの道のりを振り返ってみましょう。
