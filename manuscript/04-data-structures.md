## 4-1　変数とデータ型

### データに名前をつけて覚える

料理を作るとき、料理人は材料を作業台に並べます。「これは砂糖、これは塩」と分かるように、容器にラベルを貼っておくこともあるでしょう。プログラムも同じで、扱うデータをメインメモリという作業台に置き、名前をつけて管理します。

この「名前のついたデータの置き場所」が、第3章でも登場した変数（variable）です。変数に値を入れることを**代入**（assignment）といいます。Pythonでは次のように書きます。

```python
age = 20          # 変数 age に 20 を代入する
name = "さくら"    # 変数 name に文字列を代入する
print(name, age)  # 2つの変数の中身を表示する
```

```
さくら 20
```

ここで使っている「=」は、数学の等号とは意味が違います。「右側の値を、左側の名前の場所に入れる」という命令です。ですから、次のような書き方もできます。

```python
age = 20
age = age + 1     # 今の age に 1 を足して、結果を age に入れ直す
print(age)
```

```
21
```

数学なら「age = age + 1」は成り立ちません。プログラムでは、右側を先に計算し、その結果で左側を上書きする、と読みます。変数の中身は後から何度でも変えられます。これが「変わる数」と書いて変数と呼ぶ理由です。

### 変数の正体はメモリ上の場所

変数の実体は、メインメモリ上のある場所です。第1章で見たように、メモリには、場所を区別するための通し番号である番地（アドレス）が振られています。けれども、人間が「1,048,576番地に年齢を入れる」と番地で考えるのは大変です。そこでプログラミング言語は、番地の代わりに age のような名前で場所を指せるようにしてくれます。

名前と番地の対応づけは、コンパイラーやインタープリター、実行時のしくみが裏で引き受けます。プログラマーは名前だけを気にすればよいのです。これは、作業台のマス目の番号を覚える代わりに、容器に貼った「砂糖」「塩」のラベルで呼ぶのに似ています。なお、Pythonの変数は、この見方をもう一歩進めたしくみになっています。それは章末のコラム「値と参照」で見ます。

ここから、エンジニアにとって大事な教訓が1つ導かれます。それは、変数名はプログラムを読む人のためにある、ということです。コンピューターにとって名前は単なる目印にすぎません。しかし、x や a ばかりのプログラムは、半年後の自分にも読めなくなります。age や user_name のように、中身が分かる名前をつけることが、読みやすいプログラムへの第一歩です。

### 変えないと決めた値：定数

反対に、一度決めたら変えない値もあります。消費税率や、1回の投稿に添付できる写真の上限枚数などです。こうした値を**定数**（constant）と呼びます。多くの言語には、定数を書き換えようとするとエラーにするしくみがあります。Pythonにはそのしくみがありません。代わりに、MAX_PHOTOS のように全部大文字で名前を書き、「これは変えない値です」と示す習慣があります。

プログラムの中に「10」という数字がいきなり出てくると、読む人には何の10なのか分かりません。MAX_PHOTOS という名前の定数にしておけば意味が伝わります。上限を変えたくなったときも、1か所を直すだけで済みます。

### データ型：そのデータは何として扱うのか

変数に入れるデータには種類があります。この種類を**データ型**（data type）、または単に型と呼びます。よく使う基本的な型は次の4つです。

表4-1　基本的なデータ型

| 型の名前 | Pythonでの名前 | 例 | 主な用途 |
| --- | --- | --- | --- |
| 整数 | int | 20、-3、0 | 個数、年齢、「いいね」の数 |
| 浮動小数点数 | float | 170.5、0.1 | 身長、気温、割合 |
| 文字列 | str | "さくら"、"海の写真" | 名前、文章、タグ |
| 真偽値 | bool | True、False | 公開／非公開、ログイン済みかどうか |

Pythonでは、type という関数で値の型を確かめられます。

```python
print(type(20))        # 整数
print(type(170.5))     # 浮動小数点数
print(type("さくら"))   # 文字列
print(type(True))      # 真偽値
```

```
<class 'int'>
<class 'float'>
<class 'str'>
<class 'bool'>
```

真偽値は、「はい」か「いいえ」の2つの状態だけを持つ型です。投稿が公開されているかどうか、といった判断に使います。次の節で見るように、第3章の条件分岐（if文）で活躍します。

### なぜ型が必要なのか

第2章で見たとおり、コンピューターの中では、どんなデータもビットの並びです。第2章の例では、「01000001」という8ビットが、整数として読めば65、文字コードとして読めば「A」になりました。同じビット列でも、どう解釈するかで意味がまったく変わるのです。

型は、この「解釈のしかた」をプログラムに教える情報です。型が分かっていれば、コンピューターは次のことを正しく判断できます。

- メモリ上で何バイト分の場所を使うか
- そのビット列をどう読むか
- どんな操作ができるか（足し算ができるのか、文字をつなげるのか）

型がなければ、身長の数値を文字として表示したり、名前どうしを数として足したりする混乱が起きます。型は、データにつけた取扱説明書のようなものだといえます。

型は、扱える値の範囲も決めます。たとえばJavaのint型は32ビットの整数で、扱えるのはおよそプラスマイナス21億までです。それを超える計算をすると、第2章で見たオーバーフローが起き、値が反対側の端に回り込みます。一方、これも第2章で触れたとおり、Pythonの整数は必要に応じて使うメモリを増やすため、とても大きな数も扱えます。どこまでの値を入れる可能性があるのかを考えて型を選ぶことも、エンジニアの仕事の一部です。

### 静的型付けと動的型付け

型の扱い方は、プログラミング言語によって大きく2つに分かれます。

1つは**静的型付け**（static typing）です。プログラムを実行する前に、変数の型を決めておく方式です。Java、C、Goなどがこの方式をとります。Javaでは「int age = 20;」のように、変数を用意するときに型も書きます。間違った型の値を入れようとすると、実行前の段階でコンパイラーが誤りを指摘してくれます。

もう1つは**動的型付け**（dynamic typing）です。実行しながら、その時点で入っている値に応じて型が決まる方式です。PythonやJavaScript、Rubyがこの方式です。先ほどの例でも、age に型を書いていませんでした。代入された20を見て、実行時に整数だと判断されています。

2つの方式には、それぞれ長所と短所があります。

表4-2　静的型付けと動的型付けの比較

| 観点 | 静的型付け | 動的型付け |
| --- | --- | --- |
| 型の決まるタイミング | 実行前 | 実行中 |
| 書く手間 | 型を書く分だけ多い | 少なく、すぐに試せる |
| 誤りに気づくタイミング | 実行前に見つかりやすい | 実行して初めて分かることがある |
| 向いている場面 | 大人数・長期間の開発 | 小さな道具、試作、学習 |

どちらが優れているというものではありません。手軽さと安全性のどちらを重く見るか、という設計上の選択です。最近は、動的型付けの言語にも型を書き添えるしくみが広まっています。Pythonの型ヒントや、JavaScriptに型を加えたTypeScriptがその例です。手軽さを残しつつ、誤りを早く見つけたいという要望の表れです。

エンジニアとして新しい言語に触れるときは、まず「この言語は静的か、動的か」を確かめてみてください。エラーがいつ、どのように現れるのかが見通せるようになります。

## 4-2　データを計算し、判断する ― 演算と式

### 計算の基本：算術演算

データを覚えたら、次はそれを使って計算します。プログラムの中で値を組み合わせて新しい値を作るものを**演算子**（operator）と呼びます。演算子と値を組み合わせた「1 + 2」のような計算のまとまりは**式**（expression）といいます。

足し算や掛け算のような計算を**算術演算**といいます。Pythonの主な算術演算子は次のとおりです。掛け算は「×」ではなく「`*`」、割り算は「÷」ではなく「/」を使います。キーボードで打ちやすい記号が選ばれているのです。

表4-3　Pythonの主な算術演算子

| 演算子 | 意味 | 例 | 結果 |
| --- | --- | --- | --- |
| `+` | 足し算 | `7 + 2` | 9 |
| `-` | 引き算 | `7 - 2` | 5 |
| `*` | 掛け算 | `7 * 2` | 14 |
| `/` | 割り算 | `7 / 2` | 3.5 |
| `//` | 整数の割り算（商） | `7 // 2` | 3 |
| `%` | 割り算の余り | `7 % 2` | 1 |

### 割り算には3種類ある

表の中で、割り算だけが3つもあることに気づいたでしょうか。小学校で習った「7÷2＝3あまり1」を思い出してください。答えの表し方には「3.5」と「3あまり1」の2通りがあります。プログラムでは、どちらが欲しいのかを演算子で選び分けます。

たとえば、3,000円のお菓子代を7人で分ける場面を考えてみましょう。

```python
total = 3000
people = 7
print(total / people)   # 小数まで含めた割り算
print(total // people)  # 1人あたりの金額（整数部分だけ）
print(total % people)   # 配りきれずに余る金額
```

```
428.57142857142856
428
4
```

1円未満のお金は配れませんから、実際には「1人428円で、4円余る」が欲しい答えです。このように、整数の割り算と余りは、現実の問題でよく使います。

余りの計算は、意外なほど用途の広い道具です。偶数か奇数かは、2で割った余りが0かどうかで判定できます。表の行を1行おきに色分けするときにも使います。秒数を「何分何秒」に直すときは、60で割った商と余りを求めます。

なお、最初の結果の末尾が「…856」となっているのは、浮動小数点数で表しているためです。浮動小数点数は、多くの小数を近い値でしか表せません。このしくみは第2章で説明したとおりです。お金のように誤差が許されない計算では、浮動小数点数を避け、円単位の整数で扱うのが定石です。

演算の結果にも型があります。「/」による割り算は、割り切れる場合でも結果が浮動小数点数になります。6 / 2 の結果は、整数の3ではなく3.0です。一方、「//」は整数どうしなら結果も整数です。割り算の結果をリストの番号などに使いたいときは、「//」を選ぶ必要があります。どの演算が、どの型の値を返すのか。それを意識しておくと、思わぬ誤りを防げます。

プログラムでは、変数の値を少し増やして入れ直す操作がとても多く現れます。そのため、「likes = likes + 1」を「likes += 1」と短く書ける**複合代入演算子**も用意されています。「いいね」ボタンが押されるたびに数を1つ増やす、といった場面でよく使います。

### 計算の順番：演算子の優先順位

「`1 + 2 * 3`」の答えは、いくつになるでしょうか。左から順に計算すれば9ですが、Pythonの答えは7です。算数と同じく、掛け算や割り算を足し算や引き算より先に計算するからです。このような計算の順番の決まりを、演算子の**優先順位**（precedence）といいます。

```python
print(1 + 2 * 3)     # 掛け算が先
print((1 + 2) * 3)   # 括弧の中が先
```

```
7
9
```

優先順位は言語ごとに細かく決められています。しかし、すべてを覚える必要はありません。迷ったら括弧で囲めばよいのです。括弧を付けておけば、計算の意図が読む人にもはっきり伝わります。プログラムは、書く時間より読まれる時間のほうがずっと長いものです。少し冗長に見えても、誤解の余地がない書き方を選ぶのがよい習慣です。

### 比べて判断する：比較演算

2つの値を比べる演算を**比較演算**といいます。結果は必ず真偽値、つまり True（正しい）か False（正しくない）のどちらかになります。

```python
likes = 120
print(likes >= 100)   # 100以上か
print(likes == 50)    # 50と等しいか
print(likes != 50)    # 50と等しくないか
```

```
True
False
True
```

注意したいのは、「等しいか」を調べるときは「==」と、イコールを2つ並べることです。1つだけの「=」は、前の節で見たとおり代入を意味します。この2つを取り違えるのは、初心者が最もよくつまずく点の1つです。

### 条件を組み合わせる：論理演算

「ログインしていて、かつ、投稿が公開されている」のように、条件を組み合わせたい場面もよくあります。このときに使うのが**論理演算**です。Pythonでは and、or、not という英単語で書きます。

表4-4　論理演算

| 演算 | 意味 | 結果が True になるとき |
| --- | --- | --- |
| A and B | AかつB（論理積：AND） | AとBの両方がTrueのとき |
| A or B | AまたはB（論理和：OR） | AとBの少なくとも一方がTrueのとき |
| not A | Aではない（否定：NOT） | AがFalseのとき |

この3つは、第2章で見たブール代数の「かつ」「または」「でない」そのものです。CPUの中の電子回路も、AND・OR・NOTの組み合わせで足し算や比較を行っています。電気信号を扱う回路と、プログラムの中の条件判断は、同じ論理の上に成り立っているのです。

論理演算には、もう1つ大切な性質があります。and は左側が False なら、右側を調べずに結果を False と決めます。or は左側が True なら、右側を調べずに True と決めます。答えがもう決まっているのに、残りを計算するのは無駄だからです。これを**短絡評価**（short-circuit evaluation）と呼びます。

短絡評価は、速さのためだけの工夫ではありません。たとえば「投稿が存在し、かつ、その投稿が公開されている」という条件を考えてみてください。投稿が存在しないのに中身を調べようとすると、エラーになってしまいます。and の左側に「存在するか」を置いておけば、存在しないときには右側の確認が行われません。条件を書く順番で、安全に確認する手順を表現できるのです。

### 型が違うと結果も違う：型変換

ここで、前の節で見た型が効いてくる例を紹介しましょう。

```python id=str-int
a = "10"   # 引用符で囲んだので文字列
b = 10     # 引用符なしなので整数
print(a + a)   # 文字列どうしの「+」
print(b + b)   # 整数どうしの「+」
```

```
1010
20
```

同じ「+」なのに、文字列では2つをつなげ、整数では足し算をしています。演算子の意味が、データの型によって変わるのです。では、文字列と整数を足そうとするとどうなるでしょうか。

```python uses=str-int raises=TypeError
print(a + b)
```

```
TypeError: can only concatenate str (not "int") to str
```

「文字列には文字列しかつなげられません」というエラーになりました。型の違う値を混ぜたいときは、どちらかの型に合わせる**型変換**（type conversion）を行います。

```python uses=str-int
print(int(a) + b)   # 文字列 "10" を整数 10 に変換してから足す
print(a + str(b))   # 整数 10 を文字列 "10" に変換してからつなげる
```

```
20
1010
```

この話は、机の上の練習問題ではありません。キーボードからの入力や、Webのフォームに書き込まれた値は、たとえ数字であっても文字列として届くのが普通です。年齢欄に「20」と書かれても、受け取った直後は「"20"」という文字列なのです。計算に使う前に、必ず数値へ変換する必要があります。

ただし、変換にも失敗はあります。「abc」のように数字でない文字列を int で整数にしようとすると、エラーになります。ユーザーは想定外の値を入力するものです。入力を変換する前に中身を確かめるのは、エンジニアの基本的な心構えです。

### 判断の材料としての式

比較演算や論理演算の結果は、第3章で学んだ条件分岐の「条件」として使われます。

```python
is_logged_in = True
is_public = False
if is_logged_in and not is_public:   # ログイン済み、かつ、非公開なら
    print("この投稿は自分だけに表示されます")
```

```
この投稿は自分だけに表示されます
```

if の後ろに書く条件は、最終的に True か False に決まる式です。どんなに複雑な判断も、比較と論理演算を組み合わせ、1つの真偽値にまとめて表します。プログラムが「判断している」ように見えるとき、その中身は真偽値の計算なのです。

エンジニアがバグを調べるとき、条件式を1つずつ分解して、それぞれが True か False かを確かめることがよくあります。思いどおりに動かない条件分岐の多くは、型の取り違えか、条件の組み合わせ方の誤りが原因です。演算と式を正確に読めることは、プログラムを書く力と同じくらい、直す力の土台になります。

## 4-3　たくさんのデータをまとめる ― 配列と連想配列

### 変数を100個用意するのか

スマートフォンのアルバムには、何百枚、何千枚もの写真が入っています。これを1枚ずつ別々の変数で扱おうとしたらどうなるでしょうか。photo1、photo2、photo3……と名前をつけていくのは、すぐに限界がきます。写真が1枚増えるたびに、プログラムを書き直す必要も出てきます。

そこで、同じ種類のデータを1つの名前でまとめて扱うしくみが用意されています。それが**配列**（array）です。配列は、データを一列に並べ、それぞれに番号をつけて管理します。この番号を**インデックス**（index）または添字と呼びます。

Pythonでは、配列にあたるものを**リスト**（list）と呼びます。角括弧で囲み、要素をカンマで区切って書きます。

```python id=photos
photos = ["海.jpg", "空.jpg", "猫.jpg"]   # 3つの要素をもつリスト
print(photos[0])     # 先頭の要素
print(photos[2])     # 3番目の要素
print(len(photos))   # 要素の数
photos.append("花.jpg")   # 末尾に1つ追加する
print(photos)
```

```
海.jpg
猫.jpg
3
['海.jpg', '空.jpg', '猫.jpg', '花.jpg']
```

配列と、第3章で学んだ繰り返しは、とても相性のよい組み合わせです。「すべての写真にフィルターをかける」という処理も、繰り返しを使えば、写真が3枚でも3,000枚でも同じ数行で書けます。

### なぜ0から数えるのか

先頭の要素を取り出すのに、photos\[1\] ではなく photos\[0\] と書きました。多くのプログラミング言語では、インデックスを0から数えます。人間の感覚では1から数えるほうが自然なのに、なぜでしょうか。

理由は、配列がメモリ上でどう置かれているかにあります。配列の要素は、メモリ上に隙間なく、連続して並べられます（図4-1）。インデックスは「先頭から数えて何番目か」ではなく、「先頭から何個分ずれた位置か」を表しているのです。先頭の要素は、先頭からのずれが0個です。だからインデックスは0になります。

![図4-1　配列のメモリ配置とインデックス](../figures/fig-4-1.svg)

CPythonのリストで連続して並ぶのは、各文字列への**参照**です。文字列の中身は別の場所に置かれます。インデックスから参照を格納した場所を計算し、その参照をたどって値を読みます。

この考え方を使うと、要素の場所が簡単な計算で分かります。仮に、配列の先頭が1,000番地で、要素1つが8バイトだとしましょう。

- インデックス0の要素：1,000 + 0 × 8 = 1,000番地
- インデックス1の要素：1,000 + 1 × 8 = 1,008番地
- インデックス3の要素：1,000 + 3 × 8 = 1,024番地

「先頭の番地 ＋ インデックス × 要素の大きさ」という1回の計算で、どの要素の場所も求まります。1から数えると、毎回「インデックスから1を引く」余計な計算が必要になります。0から数えるのは、コンピューターの都合に合わせた合理的な選択なのです。

### 連続して並んでいることの利点と弱点

要素の場所が1回の計算で分かるということは、何番目の要素でも同じ速さで取り出せるということです。100万個の要素がある配列でも、50万番目の要素を取り出すのに、先頭から順にたどる必要はありません。この性質は**ランダムアクセス**と呼ばれ、配列の最大の長所です。

一方で、弱点もあります。配列の途中に要素を挿入したいとき、それより後ろの要素をすべて1つずつ後ろへずらさなければなりません。映画館で座席を詰めて座っている列に、途中から1人を入れるようなものです。後ろの人全員が1席ずつ動く必要があります。削除の場合も同様に、後ろの要素を前へ詰める必要があります。

「取り出しは速いが、途中への挿入や削除は遅い」。この特徴は、次の節でほかのデータ構造と比べるときの基準になります。

配列の大きさにも注意が必要です。C言語の配列は、作るときに要素の数を決め、後から増やせません。Pythonのリストは、要素を足すと自動的に大きくなります。裏では、あらかじめ少し広めの場所を確保しておき、足りなくなったら、より広い場所へ全体を引っ越させています。場所を移すときは各要素への参照をコピーします。文字列の中身まで1つずつ複製する必要はありません。

### 範囲の外を指したらどうなるか

先ほどのリストは、「花.jpg」を追加して要素が4つになりました。ここで、インデックス4を指定するとどうなるでしょうか。

```python uses=photos raises=IndexError
print(photos[4])   # 要素は photos[0] から photos[3] まで
```

```
IndexError: list index out of range
```

Pythonは「インデックスが範囲外です」というエラーを出して、処理を止めてくれます。要素が4つなら、使えるインデックスは0から3までです。「最後の要素は、要素の数から1を引いた番号」という関係は、0から数える方式ならではの注意点です。

一方、C言語は範囲外かどうかを確かめません。計算した番地をそのまま読み書きしてしまいます。その結果、配列の外にある無関係なデータを書き換えてしまうことがあります。この種の誤りは、攻撃者にプログラムを乗っ取られる深刻な弱点の原因にもなってきました。範囲の確認は、エンジニアが常に意識すべき習慣です。

### 名前で引ける配列：連想配列

配列は番号でデータを引きます。しかし、番号ではなく名前で引きたいことも多いものです。たとえば、ユーザーの情報を扱う場面を考えてみましょう。

```python
user = {"name": "さくら", "age": 20, "city": "東京"}   # キーと値の組
print(user["name"])    # キー "name" で値を取り出す
user["age"] = 21       # 値を書き換える
user["job"] = "学生"   # 新しい組を追加する
print(user)
```

```
さくら
{'name': 'さくら', 'age': 21, 'city': '東京', 'job': '学生'}
```

このように、**キー**（key）と**値**（value）の組でデータを管理するしくみを**連想配列**（associative array）といいます。Pythonでは**辞書**（dict）と呼びます。言語によっては、マップ（map）やハッシュ（hash）とも呼ばれます。国語辞典で、見出し語から意味を引くのと同じ使い方ができるのです。

### ハッシュテーブル：名前から置き場所を計算する

連想配列で驚くべきなのは、データが何百万件あっても、キーからほぼ一瞬で値を取り出せることです。その秘密が**ハッシュテーブル**（hash table）というしくみです。

ハッシュテーブルでは、キーを**ハッシュ関数**（hash function）という計算にかけて、1つの数値に変換します。その数値を、配列のインデックスとして使うのです。図書館で「書名から棚番号を計算する決まり」があると想像してください。本を探すときは、書名から棚番号を計算して、その棚だけを見ればよいわけです。なお、ハッシュ関数は、第7章で見るようにセキュリティの分野でも重要な役割を果たします。

ただし、別々のキーから同じ棚番号が計算されてしまうこともあります。これを**衝突**（collision）と呼びます。衝突が起きたら、近くの空いている棚に置いたり、同じ棚に複数のデータを並べたりして対処します。こうした工夫のおかげで、ハッシュテーブルは平均すると、件数にほとんど関係なく素早く値を見つけられます。

もっとも、この速さには代償があります。衝突を減らすには、棚に十分な空きを残しておく必要があります。つまり、ハッシュテーブルは実際に入れるデータより多めのメモリを使います。また、キーから棚番号を計算する以上、後から中身が変わるキーは使えません。Pythonの辞書で、書き換えのできるリストをキーにできないのはこのためです。

### 関連するデータをひとまとめにする

1人のユーザーには、名前、年齢、住んでいる町など、複数の情報があります。これらをばらばらの変数に入れると、どの名前とどの年齢が対応しているのか分からなくなりがちです。関連するデータは、ひとまとめにして扱うのが基本です。

先ほどの辞書もその一例です。C言語には**構造体**（structure）という、複数のデータをまとめた型を自分で作るしくみがあります。Javaなどのオブジェクト指向の言語では、データと、それを扱う処理をセットにした**オブジェクト**（object）を使います。

さらに、こうしたまとまりを組み合わせることもできます。たとえば、SNSの投稿一覧は「投稿を表す辞書が、いくつも並んだリスト」として表せます。

```python
posts = [
    {"user": "さくら", "text": "海に来ました", "likes": 12},
    {"user": "たける", "text": "今日のランチ", "likes": 5},
]
print(posts[1]["text"])   # 2番目の投稿の本文
```

```
今日のランチ
```

リストと辞書を組み合わせれば、現実の複雑なデータもたいてい表現できます。エンジニアの仕事の多くは、扱いたい情報をどのような組み合わせで表すかを考えることから始まるのです。

## 4-4　データの並べ方を工夫する ― 代表的なデータ構造

### 並べ方が使い勝手を決める

本棚の本を、あなたはどう並べていますか。作者順、買った順、よく読む本を手前に、など人によってさまざまでしょう。どの並べ方がよいかは、本をどう探し、どう出し入れするかで決まります。

プログラムのデータも同じです。データをどのような形で並べ、どうつなげておくかの決まりを**データ構造**（data structure）といいます。前の節の配列や連想配列も、データ構造の一種です。この節では、ほかの代表的なデータ構造を5つ紹介します。それぞれ、どんな操作が得意なのかに注目してください。

### スタック：最後に入れたものから取り出す

アプリの「元に戻す」機能を思い出してください。文章を編集していて元に戻すと、直前の操作から順に取り消されます。3つ前の操作だけを、いきなり取り消すことはできません。

この動きを実現するのが**スタック**（stack）です。第3章で積み重ねたお皿のたとえで見たように、スタックはデータを積み重ねていく構造で、取り出せるのは常に一番上のデータだけです。最後に入れたものが最初に出てくるので、**後入れ先出し**（LIFO：Last In, First Out）と呼ばれます。データを積むことを**プッシュ**（push）、取り出すことを**ポップ**（pop）といいます。

```python
history = []                 # 操作の履歴を入れるスタック
history.append("文字を入力")   # プッシュ
history.append("太字にする")
history.append("色を変える")
print(history.pop())          # ポップ：最後の操作が出てくる
print(history)
```

```
色を変える
['文字を入力', '太字にする']
```

ブラウザーの「戻る」ボタンも、見てきたページをスタックに積んでおくことで実現できます。第3章で学んだ、関数の呼び出しを管理するスタック領域も、この構造を使ったものです。

### キュー：先に入れたものから取り出す

オフィスのプリンターに、何人もが同時に印刷を頼んだとしましょう。プリンターは、頼まれた順番に1枚ずつ印刷していきます。後から頼んだ人の印刷が、先に頼んだ人を追い越すことはありません。

この動きを実現するのが**キュー**（queue）です。キューは、お店のレジの行列と同じ構造です。新しいデータは列の最後尾に並び、取り出すときは先頭から取り出します。先に入れたものが先に出てくるので、**先入れ先出し**（FIFO：First In, First Out）と呼ばれます。

```python
from collections import deque   # キューに向いた道具を読み込む
jobs = deque()
jobs.append("見積書.pdf")   # 最後尾に並ぶ
jobs.append("請求書.pdf")
jobs.append("地図.png")
print(jobs.popleft())       # 先頭から取り出す
print(list(jobs))
```

```
見積書.pdf
['請求書.pdf', '地図.png']
```

ここで、なぜ普通のリストではなく deque という道具を使ったのか、気になった人もいるでしょう。リストの先頭から取り出すと、残りの要素をすべて1つずつ前へ詰める必要があります。前の節で見た、配列の弱点そのものです。deque は両端での出し入れが速くなるように作られているので、キューに向いています。同じ「先頭から取り出す」でも、裏側の構造によって手間が大きく変わるのです。

キューは、順番を守って処理したい場面のあらゆるところで使われています。キーボードから入力された文字の処理や、Webサーバーに次々と届く要求の処理などです。スタックとキューは、どちらも「出し入れの順番」に決まりをもたせた構造です。違いは、取り出す側が新しいほうか古いほうかの1点だけです（図4-2）。

![図4-2　スタックとキューの違い](../figures/fig-4-2.svg)

どちらも出し入れの順番が決まっていますが、取り出されるのが「最新」か「最古」かが逆になっています。

### 連結リスト：数珠つなぎで並べる

前の節で、配列は途中への挿入が苦手だと説明しました。この弱点を補うのが**連結リスト**（linked list）です。

連結リストでは、それぞれのデータが「次のデータはどこにあるか」という情報を持っています。データはメモリ上のばらばらの場所に置かれ、目印をたどってつながっています。宝探しゲームで、1つ目のヒントに2つ目の隠し場所が書いてある様子に似ています。

途中にデータを挿入するときは、つなぎ目の情報を書き換えるだけです。配列のように、後ろのデータを全部ずらす必要はありません。その代わり、何番目かを指定して直接取り出すことはできません。先頭から順に目印をたどっていく必要があります。配列とは長所と短所がちょうど逆になっているのです。

なお、名前がまぎらわしいのですが、Pythonの「リスト」は連結リストではありません。中身は、前の節で見た配列に近い構造です。だからこそ、番号を指定した取り出しが速く、途中への挿入は遅いのです。データ構造の性質を知るには、名前ではなく、裏側で実際にどう並んでいるかを確かめる必要があります。

### 木構造：枝分かれで階層を表す

パソコンのフォルダーを思い浮かべてください。「ドキュメント」フォルダーの中に「仕事」と「趣味」のフォルダーがあり、「仕事」の中にさらにファイルが入っている。このように、1つのものから複数のものが枝分かれしていく構造を**木構造**（tree）と呼びます。木を逆さまにした形に見えるのが名前の由来です。

木構造を作る1つひとつの要素を**節**（node）と呼びます。一番上の節が**根**（root）で、それ以上枝分かれしない端の節が**葉**（leaf）です。根から目的の節までは、必ずただ1つの道筋でたどれます。フォルダーの場所を表すパスは、この道筋を書き表したものです。

Webページを記述するHTMLも木構造です。ページ全体の中に本文があり、本文の中に段落があり、段落の中に強調した語がある、という入れ子になっています。会社の組織図や、トーナメント表も木構造の仲間です。木構造は、階層や包含関係のあるデータを表すのに向いているのです。

木構造は、データを素早く探すためにも使われます。値の大小に従って左右に振り分けながらデータを並べておけば、探すときに枝を1本ずつ選んで下りていくだけで済みます。こうした工夫は、次の節で見る探索の考え方や、第5章で扱うデータベースの検索を速くするしくみにもつながっています。

### グラフ：網の目のつながりを表す

木構造では、枝分かれした先どうしが直接つながることはありません。しかし、現実のつながりはもっと複雑です。鉄道の路線図では、多くの駅が複数の路線でつながり、ぐるりと一周する環状線もあります。

このような網の目状のつながりを表すのが**グラフ**（graph）です。ここでいうグラフは、棒グラフや折れ線グラフとは別のものです。点（**頂点**：vertex、ノードとも呼びます）と、それらを結ぶ線（**辺**：edge、エッジとも呼びます）でできた構造を指します。駅が頂点、駅と駅を結ぶ線路が辺にあたります。

SNSの人間関係もグラフで表せます。ユーザーが頂点、フォローの関係が辺です。フォローには「AさんがBさんをフォローする」という向きがあるので、辺に矢印をつけた**有向グラフ**として表します。「知り合いの知り合い」をおすすめとして表示する機能は、このグラフをたどることで実現されています。乗り換え案内の最短経路の検索も、グラフの上で道を探す計算です。

### 目的に応じて構造を選ぶ

ここまでの構造を、得意なことでまとめてみましょう。

表4-5　代表的なデータ構造の特徴

| データ構造 | 並べ方の特徴 | 得意なこと | 身近な例 |
| --- | --- | --- | --- |
| 配列 | メモリ上に連続して並べる | 番号を指定した取り出し | 写真の一覧 |
| 連想配列 | キーから置き場所を計算する | 名前を指定した取り出し | ユーザー情報 |
| スタック | 上に積み、上から取る | 直前の状態に戻ること | 元に戻す、戻るボタン |
| キュー | 後ろに並び、前から取る | 来た順に処理すること | 印刷待ち、レジの行列 |

表の中には、性質の違うものが混ざっています。スタックやキューは「どの順番で出し入れするか」という使い方の約束です。その中身は、配列でも連結リストでも作れます。前に使った deque も、内部では配列の塊を数珠つなぎにした作りになっています。使う側は約束どおりに出し入れするだけで、中身の作りを気にする必要はありません。こうして、使い方と作り方を分けて考えられることも、データ構造という考え方の強みです。

すべての操作が得意な、万能のデータ構造はありません。番号での取り出しを速くすれば挿入が遅くなり、挿入を速くすれば取り出しが遅くなります。どの構造を選ぶかは、そのデータに対して「どの操作を一番多く行うか」で決めます。

構造の選び方を誤ると、プログラムは正しく動いても、データが増えたとたんに極端に遅くなることがあります。データ構造を学ぶのは、名前を覚えるためではありません。目の前の問題に合った道具を選べるようになるためなのです。

## 4-5　効率よく処理する ― アルゴリズムと計算量

### 同じ答えでも、手順によって手間が違う

紙の国語辞典で「ハッシュ」という言葉を引くとき、最初のページから1ページずつめくる人はいないでしょう。だいたい真ん中あたりを開き、「は」より前か後かを見て、探す範囲を絞り込んでいくはずです。どちらの方法でも、いつかは目的の言葉にたどり着きます。けれども、かかる手間は大違いです。

第3章で見たように、問題を解くための手順をアルゴリズム（algorithm）といいます。第3章では、本棚から1冊を探す例で手順による手間の違いを確かめ、プログラムが順次・分岐・繰り返しの組み合わせで書けることも学びました。アルゴリズムは、それらをどの順番でどう組み合わせるかという「解き方の設計」にあたります。この節では、データを探す手順と並べ替える手順を例に、アルゴリズムによって手間がどれほど変わるのかを見ていきます。

### 先頭から順に探す：線形探索

最も素直な探し方は、先頭から1つずつ順に確かめていく方法です。これを**線形探索**（linear search）と呼びます。

```python
def linear_search(data, target):
    for i in range(len(data)):   # 先頭から順に調べる
        if data[i] == target:    # 見つかったら
            return i             # その位置を返す
    return -1                    # 最後まで見つからなければ -1 を返す

names = ["たける", "さくら", "ひなた", "れん"]
print(linear_search(names, "ひなた"))
```

```
2
```

線形探索の長所は、データがどんな順番に並んでいても使えることです。しかし、データが増えると手間も同じ割合で増えます。100万件のデータなら、運が悪いと100万回の比較が必要です。

### 半分ずつ絞り込む：二分探索

データがあらかじめ小さい順に並んでいれば、もっと賢い方法が使えます。辞書を引くときと同じように、まず真ん中を見るのです。探している値が真ん中より大きければ、前半には絶対にありません。小さければ、後半には絶対にありません。こうして1回比べるごとに、探す範囲を半分に減らしていきます。この方法を**二分探索**（binary search）と呼びます（図4-3）。

```python
def binary_search(data, target):
    low, high = 0, len(data) - 1      # 探す範囲の両端
    while low <= high:
        mid = (low + high) // 2       # 範囲の真ん中
        if data[mid] == target:
            return mid                # 見つかった
        elif data[mid] < target:
            low = mid + 1             # 後半に絞る
        else:
            high = mid - 1            # 前半に絞る
    return -1                         # 見つからなかった

scores = [3, 7, 12, 19, 24, 31, 38, 42, 50, 57, 63, 71, 80, 88, 95]
print(binary_search(scores, 63))
```

```
10
```

15件のデータから63を探すのに、比較は4回で済みました。では、データが100万件ならどうでしょう。100万を半分にする操作を繰り返すと、20回で1件まで絞り込めます。2を20回掛けると1,048,576となり、100万を超えるからです。第2章の数当てゲームと同じ理屈です。線形探索なら最大100万回かかるところが、二分探索なら最大でも20回です。データが10億件に増えても、必要な回数は30回ほどにしかなりません。

![図4-3　二分探索で探す範囲が半分ずつ減るようす](../figures/fig-4-3.svg)

候補は15件、7件、3件、1件と、比べるたびにおよそ半分に減っていきます。

ただし、二分探索には「データが並べ替えられていること」という前提があります。順番がばらばらなら、真ん中を見ても前後のどちらにあるのか判断できません。速さを得るには、事前の準備が必要なのです。

では、1回探すためだけに並べ替えるのは得なのでしょうか。後で見るとおり、並べ替えには探索よりずっと多くの手間がかかります。1回しか探さないなら、線形探索のほうが早く終わります。けれども、同じデータから何千回、何万回と探すなら話は別です。最初に一度だけ並べ替えておけば、その後の探索はすべて速くなります。どちらを選ぶかは、データをどう使うかによって決まるのです。

### 並べ替える：ソート

データを決まった順番に並べ替えることを**ソート**（sort）といいます。二分探索の準備としてだけでなく、「いいねの多い順」「新しい順」のように、ソートはあらゆるところで使われます。

最も分かりやすいソートの1つが**選択ソート**（selection sort）です。トランプの手札を小さい順に並べる場面で考えてみましょう。

1. まだ並べていない札の中から、一番小さい札を探す
2. それを、並べ終えた札の列の最後に置く
3. 札がなくなるまで、1と2を繰り返す

考え方は単純ですが、手間はかかります。1枚選ぶたびに、残りの札をすべて見比べる必要があるからです。札が10枚なら45回、1,000枚なら約50万回の比較になります。札が10倍になると、手間は100倍になるのです。

実際のプログラムでは、もっと速いソートが使われます。たとえば**クイックソート**や**マージソート**は、データを分割して並べ替えることで、比較の回数を大きく減らします。100万件のデータを並べ替える場合、選択ソートでは約5,000億回の比較が必要です。一方、マージソートなら約2,000万回で済みます。PythonやJavaなど多くの言語には、こうした工夫を凝らしたソートが最初から用意されています。普段はそれを使えば十分です。たとえば、投稿を「いいね」の多い順に並べるなら、Pythonでは次のように書けます。

```python
posts = [
    {"text": "海に来ました", "likes": 12},
    {"text": "今日のランチ", "likes": 5},
    {"text": "夕焼け", "likes": 31},
]
# likes の値を基準に、大きい順（reverse=True）に並べ替える
ranking = sorted(posts, key=lambda p: p["likes"], reverse=True)
for p in ranking:
    print(p["likes"], p["text"])
```

```
31 夕焼け
12 海に来ました
5 今日のランチ
```

並べ替えの基準を指定するだけで、手順そのものは言語が引き受けてくれます。自分でソートを一から書く機会は、実務ではほとんどありません。それでも、しくみを知っておけば、件数が増えたときにどのくらい時間がかかるかを見積もれるようになります。

### 計算量：データが増えたらどうなるか

アルゴリズムの速さを比べるとき、「何秒かかったか」は当てになりません。同じプログラムでも、速いコンピューターと遅いコンピューターでは時間が違うからです。そこで、「データの件数が増えたとき、手間がどのくらいの勢いで増えるか」という見方をします。これを**計算量**（computational complexity）といいます。

計算量は、**オーダー記法**（O記法）で表します。データの件数を n として、O(n) のように書き、「オーダー n」と読みます。細かな係数は気にせず、増え方の性質だけをつかむための表し方です。

表4-6　計算量の比較（手間の回数の目安）

| オーダー | 増え方のイメージ | 例 | 10件 | 1,000件 | 100万件 |
| --- | --- | --- | --- | --- | --- |
| O(1) | 件数に関係なく一定 | 配列の番号指定、辞書の検索（平均） | 1 | 1 | 1 |
| O(log n) | 件数が倍になっても1回増えるだけ | 二分探索 | 約3 | 約10 | 約20 |
| O(n) | 件数に比例 | 線形探索 | 10 | 1,000 | 100万 |
| O(n log n) | 比例よりやや多い | 速いソート | 約33 | 約1万 | 約2,000万 |
| O(n²) | 件数の2乗に比例 | 選択ソート | 100 | 100万 | 1兆 |

表の数字は、手間の増え方を比べるための目安です。たとえば選択ソートの実際の比較回数は、n² のおよそ半分です。それでも、件数が10倍になれば手間が100倍になるという増え方の性質は変わりません。10件では、どのアルゴリズムも大差ありません。違いが現れるのは、データが増えたときです。100万件になると、O(log n) の約20回に対して、O(n²) では1兆回にもなります。1回の処理に100万分の1秒かかるとすれば、前者は一瞬です。一方、後者は10日以上かかる計算になります。

### 時間とメモリのかけひき

計算量には、時間だけでなくメモリの使用量についての見方もあります。前者を**時間計算量**、後者を**空間計算量**と呼びます。そして、この2つはしばしば引き換えの関係になります。

たとえば、4-3で見たハッシュテーブルは、多めのメモリを使う代わりに、検索をほぼ一定の時間で済ませます。逆に、メモリを節約するために、毎回データを先頭から調べ直す方法をとることもできます。よく使う計算結果を保存しておき、2回目からは計算を省くのも同じ発想です。速さを買うためにメモリを払うのか、メモリを守るために時間を払うのか。この判断も、アルゴリズムを選ぶうえで欠かせない視点です。

### データが100倍に増えても耐えられるか

開発中のテストデータは、たいてい数十件から数百件です。この規模では、どんなアルゴリズムでも一瞬で終わります。ところが、サービスが成長して利用者が100万人になったとたん、画面が表示されなくなる。こうした事態は、実際の開発現場でしばしば起こります。原因の多くは、繰り返しの中で線形探索をしているなど、O(n²) の処理が紛れ込んでいることです。

ここで、4-3と4-4で学んだデータ構造が効いてきます。リストから線形探索で探していた処理を辞書に置き換えるだけで、O(n) が O(1) になることがあります。アルゴリズムとデータ構造は、セットで考えるものなのです。プログラムを書くときは「今のデータ量で動くか」だけでなく、「100倍に増えても耐えられるか」を考える習慣をつけましょう。

## 4-6　データを保存し、受け渡す ― ファイルとデータ形式

### 電源を切ると、作業台は片付けられる

ここまで見てきた変数やリスト、辞書は、すべてメインメモリという作業台の上に置かれていました。ところが、第1章で見たように、メインメモリには大きな弱点があります。電源を切ると、中身が消えてしまうのです。アプリを終了したときも、そのアプリが使っていたメモリの内容は失われます。

もし保存のしくみがなければ、書きかけの文章も、ゲームの進み具合も、アプリを閉じるたびに消えてしまいます。料理人が営業の終わりに、作業台の上の食材を冷蔵庫や食品庫へしまうのと同じです。プログラムも、残しておきたいデータをストレージ（SSDやHDD）にしまいます。電源を切っても中身が消えないストレージに、データを**ファイル**（file）としてまとめて保存するのです。

ファイルを書き込んだり読み込んだりする実際の作業は、第1章で見たシステムコールを通じて、OSが引き受けます。プログラムは「このファイルにこの内容を書いて」とOSに頼むだけです。厨房全体を取り仕切る店長が、食品庫の管理を一手に担っているのと同じ構図です。

Pythonでは、open という関数でファイルを開き、書き込みや読み込みを頼みます。

```python
with open("memo.txt", "w", encoding="utf-8") as f:   # 書き込み用に開く
    f.write("海に来ました")                            # 文字列を書き込む

with open("memo.txt", "r", encoding="utf-8") as f:   # 読み込み用に開く
    print(f.read())                                   # 中身を読んで表示する
```

```
海に来ました
```

encoding="utf-8" という指定に注目してください。これは、文字をどの文字コードでビット列に変換して保存するかを決めるものです。第2章で見たとおり、同じ文字でも文字コードが違えば、ビット列も違います。書いたときと違う文字コードで読むと、文字化けが起きます。ファイルを扱うときは、どの文字コードで書かれているかを常に意識する必要があります。

### テキストファイルとバイナリファイル

ファイルの中身も、結局はビットの並びです。ただし、その中身の性質によって、ファイルは大きく2種類に分けられます。

1つは**テキストファイル**（text file）です。中身が、文字コードで表された文字だけでできているファイルです。メモ帳のようなテキストエディターで開けば、人間がそのまま読めます。プログラムのソースコードや、後で紹介するCSVやJSONのファイルがこの仲間です。

もう1つは**バイナリファイル**（binary file）です。文字以外の形式でデータを記録したファイルです。写真や音楽、動画、アプリ本体などがこちらに入ります。テキストエディターで開くと、意味の分からない記号の羅列に見えます。文字として解釈するように作られていないからです。

表4-7　テキストファイルとバイナリファイル

| 種類 | 中身 | 人間が直接読めるか | 例 |
| --- | --- | --- | --- |
| テキストファイル | 文字コードで表した文字 | 読める | .txt、.csv、.json、.py |
| バイナリファイル | 文字以外の形式のデータ | 読めない | .jpg、.mp3、.mp4、.exe |

テキストファイルは、読みやすく扱いやすい反面、同じ情報でもサイズが大きくなりがちです。バイナリファイルは、人間には読めない代わりに、コンパクトで素早く読み書きできます。写真や動画のように大きなデータがバイナリで保存されるのは、このためです。

### 拡張子：中身の種類を示す目印

ファイル名の末尾にある「.jpg」や「.csv」の部分を**拡張子**（extension）といいます。拡張子は、そのファイルがどんな形式で書かれているかを示す目印です。OSは拡張子を見て、ダブルクリックしたときにどのアプリで開くかを決めています。

ただし、拡張子はあくまで名前の一部にすぎません。写真のファイル名を「.txt」に変えても、中身は写真のままです。テキストエディターで開いても、文字化けした記号が並ぶだけでしょう。拡張子はファイルの中身を変えるものではなく、中身についての約束事を名前で示しているだけなのです。

そのため、多くのバイナリ形式では、ファイルの先頭の数バイトに「自分はこの形式です」という決まった印を書き込んでいます。たとえばPNG形式の画像は、先頭に「PNG」という文字を含む8バイトの印で始まります。アプリはこの印を確かめることで、拡張子が間違っていても中身の形式を見分けられます。名前を信じすぎず、中身で確かめる。これも、外から来たデータを扱うときの大切な姿勢です。

### 表のデータを保存する：CSV

データをファイルに書き出すとき、決まった書き方に従っておくと、別のプログラムでも読み込めます。このような書き方の決まりを**データ形式**（data format）または**ファイル形式**といいます。

表の形のデータを保存するときによく使われるのが、**CSV**（Comma-Separated Values）です。名前のとおり、値をカンマで区切り、1行に1件のデータを書きます。

```csv
name,age,city
さくら,20,東京
たける,25,大阪
```

1行目は、それぞれの列が何を表すかを示す見出しです。CSVは表計算ソフトでそのまま開けるので、業務の現場で広く使われています。ただし、階層のあるデータは表しにくいという弱点があります。値そのものにカンマが含まれる場合の書き方にも、注意が必要です。

### 構造のあるデータを保存する：JSON

リストや辞書を組み合わせた複雑なデータを表すには、**JSON**（JavaScript Object Notation）がよく使われます。もともとはJavaScriptというプログラミング言語の書き方をもとにした形式です。現在では、言語を問わず広く使われています。SNSに投稿する場面を例にしてみましょう。

```json
{
  "user": "さくら",
  "text": "海に来ました",
  "likes": 12,
  "tags": ["海", "夏"],
  "is_public": true
}
```

4-3で見たPythonの辞書とリストに、とてもよく似ていることが分かります。波括弧はキーと値の組を、角括弧は値の並びを表します。文字列、数値、真偽値の区別もあります。Pythonでは、json という標準の道具を使って、辞書とJSONの文字列を相互に変換できます。

```python
import json

post = {"user": "さくら", "likes": 12, "tags": ["海", "夏"], "is_public": True}
text = json.dumps(post, ensure_ascii=False)   # 辞書をJSONの文字列に変換する
print(text)
data = json.loads(text)                       # JSONの文字列を辞書に戻す
print(data["tags"][0])
```

```
{"user": "さくら", "likes": 12, "tags": ["海", "夏"], "is_public": true}
海
```

Pythonの True が、JSONでは小文字の true になっている点に注目してください。言語ごとの書き方の違いを、変換の道具が吸収してくれているのです。

構造のあるデータの形式は、JSONのほかにもいくつかあります。タグで入れ子を表すXMLや、人が書きやすい形を重視したYAMLなどです。表の形ならCSV、入れ子のあるデータならJSONというように、データの形に合わせて選ぶのが基本です。どの形式も、データを人間とプログラムの双方に分かる形で書き表す工夫だといえます。

### 共通の形式があるから、データを受け渡せる

スマートフォンのアプリで写真を投稿すると、アプリはその投稿の情報をサーバーへ送ります。このとき、本文やタグなどの情報は、JSONのような共通の形式に変換されて送られることがよくあります。スマートフォンのアプリと、サーバーのプログラムは、別々の言語で書かれているかもしれません。それでもデータを正しくやり取りできるのは、両者が同じ形式を使っているからです。

メモリ上のデータを、ファイルに保存したり通信で送ったりできる形に変換することを**シリアライズ**（serialize）といいます。その逆の変換は**デシリアライズ**（deserialize）です。プログラムの内側ではリストや辞書として扱い、外へ出すときは共通の形式に変換する。この切り替えが、プログラムどうし、システムどうしをつなぐ基本のしくみです。データがネットワークの中をどう運ばれるのかは、第6章で詳しく見ます。

### ファイルだけでは足りなくなるとき

ファイルは便利ですが、扱うデータが大量になると問題が出てきます。SNSの投稿が何億件もあると想像してください。

- 特定の条件に合う投稿を探すたびに、大きなファイルを最初から読む必要がある
- 大勢が同時に同じファイルを書き換えると、内容が食い違ったり壊れたりする
- 書き込みの途中で停電が起きると、データが中途半端な状態で残ってしまう

こうした問題を解決するために作られたのが、データベースです。大量のデータを、速く、安全に、大勢で扱うためのしくみについては、第5章で詳しく見ていきます。

## コラム　「値」と「参照」― 同じデータを指す2つの変数

次のプログラムの実行結果を予想してみてください。

```python
a = [1, 2, 3]
b = a            # b に a を代入する
b.append(4)      # b にだけ 4 を追加したつもり
print(a)
```

```
[1, 2, 3, 4]
```

b にだけ追加したはずなのに、a にも4が入っています。これは、プログラミングを学び始めた人の多くが一度は驚く現象です。

なぜこうなるのでしょうか。4-1では、変数を「データの置き場所」と説明しました。これは多くの言語に共通する基本の考え方です。しかしPythonでは、もう一歩踏み込んだ見方が必要です。Pythonの変数は、データそのものを入れた箱ではありません。メモリ上のどこか（第3章で見たヒープ領域）に置かれたデータを「指し示す名札」のようなものです。「b = a」という代入は、リストを複製したのではありません。a が指しているのと同じリストに、b という名札をもう1枚付けただけなのです。2枚の名札が同じ1つのリストに付いているので、どちらから中身を変えても、もう一方から見た中身も変わります。

このように、データのある場所を指し示す情報を**参照**（reference）と呼びます。これに対して、データそのものを複製して渡すやり方を「値を渡す」と表現します。

では、なぜわざわざ参照という方式をとるのでしょうか。理由の1つは効率です。100万件のデータが入ったリストを、代入のたびに丸ごと複製していたら、時間もメモリも大量に消費します。場所を指し示す情報だけを渡せば、データの大きさに関係なく一瞬で済みます。第3章で見た、関数にデータを渡す場面でも同じです。大きなデータを関数に渡すたびに複製が起きないのは、参照を渡しているからです。

一方で、整数や文字列では、このような驚きは起きません。

```python
x = 10
y = x
y = y + 1        # y に新しい値 11 を代入し直す
print(x, y)
```

```
10 11
```

Pythonでは、整数や文字列は作った後に中身を書き換えられない**イミュータブル**（immutable）なデータです。「y = y + 1」は、10を書き換えるのではありません。11という新しい値を作り、y の名札をそちらに付け替えています。x は元の10を指したままです。対して、リストや辞書は中身を書き換えられる**ミュータブル**（mutable）なデータなので、先ほどのようなことが起きます。

本当に別のリストとして扱いたいときは、明示的に複製を作ります。

```python
a = [1, 2, 3]
b = a.copy()     # 中身を複製した、新しいリストを作る
b.append(4)
print(a, b)
```

```
[1, 2, 3] [1, 2, 3, 4]
```

この性質は、関数にリストを渡すときにも現れます。関数の中でリストに要素を追加すると、関数の外にある元のリストも変わります。それが意図したことなら便利ですが、そうでなければ発見しにくいバグになります。関数を作るときは、受け取ったデータを書き換えるのか、書き換えずに新しいデータを返すのかを決めておきましょう。

値と参照の違いは、言語ごとに細かな規則が異なります。しかし、「この変数はデータそのものを持っているのか、それとも場所を指しているだけなのか」という問いは、どの言語にも共通する大切な視点です。思いがけない場所でデータが書き換わるバグに出会ったら、まずこの問いを思い出してください。

## 第4章のまとめ

- 変数は、メモリ上の場所にデータを置き、名前で扱えるようにするしくみです。「=」は等号ではなく、右の値を左の名前に入れる代入を表します。
- データ型は、ビット列をどう解釈し、どんな操作ができるかを決めます。型を実行前に決める静的型付けと、実行中に決まる動的型付けがあります。
- 演算の結果は型によって変わります。文字列の"10"と数値の10は別物で、入力された値は計算の前に型変換が必要です。
- 比較演算と論理演算の結果は真偽値になり、条件分岐の判断材料になります。
- 配列は要素をメモリ上に連続して並べるため、番号で素早く取り出せます。インデックスが0から始まるのは、先頭からのずれを表しているからです。連想配列は、キーから値を素早く引けます。
- スタック、キュー、連結リスト、木構造、グラフなど、データ構造にはそれぞれ得意な操作があります。目的に合わせて選ぶことが大切です。
- 同じ問題でも、アルゴリズムによって手間は大きく変わります。計算量のオーダーは、データが増えたときの手間の増え方を表します。
- メモリの内容は電源を切ると消えるため、ファイルとして保存します。CSVやJSONのような共通の形式が、プログラム間のデータ交換を支えています。

ファイルは便利ですが、大量のデータを大勢で同時に扱うには限界があります。次の第5章では、その限界を乗り越えるために生まれたデータベースのしくみを見ていきましょう。
