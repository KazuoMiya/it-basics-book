# 第5章　大量のデータを速く正しく管理する

ネットショップで買い物をすると、会員の情報や注文の記録がどこかに残ります。大きなショップなら、会員は何百万人、注文は1日に何万件にもなります。しかも同じ瞬間に、大勢の人が商品を選び、注文ボタンを押しています。これほどのデータを、間違えず、失わず、すばやく扱うしくみは、どうなっているのでしょうか。

第4章では、ファイルだけで大量のデータを管理するには限界があることを見ました。この章では、その限界を乗り越えるために生まれたデータベースのしくみを学びます。表でデータを整理する考え方、問い合わせる言語であるSQL、使いやすい表の設計、大勢が同時に使っても壊れない工夫、速さを保つ技術の順に、架空のネットショップを例に見ていきましょう。

## 5-1　なぜデータベースが必要なのか

### 表計算ソフトで管理してみると

小さなネットショップを始めたばかりなら、会員も注文も、表計算ソフトのファイル1つで管理できます。

ところが、ショップが大きくなると困りごとが出てきます。第4章の終わりで見た3つの問題は、ここでもそのまま起こります。何百万行もの注文から目的の1件を探すには、時間がかかります。2人のスタッフが同じファイルを開いて順に保存すれば、先に保存した人の変更は消えます。保存の最中に電源が落ちれば、ファイルが中途半端な状態で壊れることがあります。

表をファイルで管理すると、さらに2つの問題が加わります。1つは、データの重複と食い違いです。同じ会員が何度も注文すると、その人の住所が何行にも書かれます。会員が引っ越したとき、1行でも直し忘れると、同じ人なのに住所が2種類ある状態になります。このように、データ同士が矛盾している状態を**不整合**といいます。

もう1つは、見せる範囲の制御です。アルバイトのスタッフには注文の一覧だけを見せ、会員のメールアドレスは見せない、といった細かな制御は、ファイルでは難しいのです。

### データベースとDBMS

こうした困りごとをまとめて引き受けてくれるのが、データベースです。データベース（database）とは、大量のデータを決まった形式で整理し、蓄えたものです。複数の人やプログラムが共有して使うことを前提にしています。

ただし、データを蓄えておくだけでは足りません。整理された形を保ち、同時に届く読み書きをさばき、障害が起きても壊れないよう見張る役が必要です。この役割を担うソフトウェアを、**データベース管理システム**（DBMS：Database Management System）といいます。

DBMSのおもな仕事を、先ほどの困りごとと対応させてみましょう（表5-1）。

表5-1　ファイルで管理するときの困りごとと、DBMSが用意するしくみ

| ファイルでの困りごと | DBMSが用意するしくみ | 詳しく見る節 |
| --- | --- | --- |
| 重複と不整合 | 表の設計とルール（制約）で矛盾を防ぐ | 5-2、5-3、5-4 |
| 同時更新 | 同時に届く処理を交通整理する | 5-5 |
| 検索の遅さ | 索引（インデックス）で目的のデータへ近道する | 5-6 |
| 障害時の復旧 | 記録（ログ）とバックアップで元に戻す | 5-5 |
| 見せる範囲の制御 | 利用者ごとに、見てよい範囲と操作を決める | 5-3 |

厨房のたとえでいえば、ストレージは冷蔵庫や食品庫でした。DBMSは、その食品庫に専任の管理係を置くようなものです。料理人は「玉ねぎを3個」と頼むだけで、どの棚に何があるかを知らなくても受け取れます。棚の整理も在庫の記録も、管理係の仕事です。利用者も同じで、データがストレージのどこに、どんな形で置かれているかを気にせず、DBMSに頼むだけで済みます。

なお、日常会話では、DBMSのことも含めて単に「データベース」と呼ぶことがよくあります。本書でも、区別が必要な場面以外はそう呼びます。銀行口座の残高、交通系ICカードの利用履歴、序論で見たSNSの投稿など、データベースは生活のあらゆるところで動いています。

### なぜ専用のしくみに任せるのか

重複を防ぐのも同時の更新をさばくのも、理屈の上では、プログラムを工夫すれば自分で作れます。しかし、障害が起きても決して壊れないしくみを正しく作るのは、とても難しい仕事です。そこで、データを守る難しい部分はDBMSにまとめる、という役割分担が生まれました。第1章で見たOSが、ハードウェアの細かな操作を引き受けてくれるのとよく似ています。DBMSの使い方を覚える手間はかかりますが、データと使う人が増えるほど、任せる利点が大きくなります。

## 5-2　表でデータを扱う ― リレーショナルデータベース

### データを表の形で持つ

名簿や時刻表、成績表など、私たちは昔から、情報を表の形で整理してきました。データベースにもいくつかの種類がありますが、現在もっとも広く使われているのは、データを表の形で管理する種類です。これを**リレーショナルデータベース**（RDB：Relational Database）といいます。この考え方は、1970年にIBMの研究者だったエドガー・F・コッドが提案しました。RDBを管理するDBMSは、**RDBMS**（Relational Database Management System）と呼ばれます。

RDBでは、1つの表を**テーブル**（table）と呼びます。架空のネットショップの会員テーブルを見てみましょう（表5-2）。

表5-2　会員テーブル（members）

| member_id | name | prefecture | email |
| --- | --- | --- | --- |
| 1 | 佐藤 花子 | 東京都 | hanako@example.com |
| 2 | 鈴木 一郎 | 大阪府 | ichiro@example.com |
| 3 | 高橋 美咲 | 東京都 | misaki@example.com |
| 4 | 伊藤 直樹 | 福岡県 | NULL |

横1行が会員1人分のデータです。この横の並びを**行**、または**レコード**（record）と呼びます。縦の並びは「氏名」「都道府県」といった項目で、これを**列**、または**カラム**（column）と呼びます。テーブル名や列名には、プログラムから扱いやすいよう英語の名前を付けるのが一般的です。prefectureは都道府県を表しています。

### 列ごとに決まる「データ型」

表計算ソフトでは、価格の欄に「千二百円」と文字で書くこともできます。しかし、これでは合計を計算できません。

RDBでは、テーブルを作るときに、列ごとに入れてよい値の種類を決めます。第4章で見たデータ型を、列ごとに指定するのです。表5-3は、列の型を厳密に検査するDBMSでの代表例です。

表5-3　代表的なデータ型

| データ型の例 | 入る値 | ネットショップでの使い道 |
| --- | --- | --- |
| INTEGER | 整数 | 会員ID、在庫数、数量 |
| VARCHAR | 文字列（長さの上限を決める） | 氏名、メールアドレス |
| DATE | 日付 | 注文日、生年月日 |
| DECIMAL | 桁数を決めた正確な数値 | 金額、割引率 |

たとえば日付型を厳密に検査するDBMSなら、「明日」のような文字列を日付として登録しようとするとエラーになります。テーブルの列、型、制約など、構造の定義を**スキーマ**（schema）と呼びます。

本書のWeb版で使うSQLiteの通常のテーブルでは、列の型は値をどのように変換するかの目安です。たとえばDATE列にも「明日」が入り、VARCHAR(50)と宣言しても51文字の名前を保存できます。日付や文字数を制限したいときは、アプリケーションで検証したり、5-3で見るCHECK制約を付けたりします。金額の例では、円単位の整数を使います。

なお、値がまだ分からない、あるいは存在しないことを表す特別な印として、**NULL**（ヌル）があります。表5-2の会員4は、メールアドレスを登録していません。そこでemailの欄がNULLになっています。NULLは「0」や「空の文字列」という値ではなく、値がないことを示す印です。

### 行を見分ける「主キー」

会員テーブルには、何百万人もの会員が登録されます。その中から特定の1人を確実に指し示すには、名前では足りません。同姓同名の人がいるからです。メールアドレスなら重複はなさそうですが、会員がアドレスを変更することもあります。そこで、会員1人ずつに、重複せず、変わることのない番号を振ります。これが会員テーブルのmember_idです。

このように、テーブルの中で行を1つに特定するための列を**主キー**（primary key）といいます。主キーには、次の2つの決まりがあります。

- 同じ値を持つ行が2つ以上あってはならない
- 値が空（NULL）であってはならない

DBMSはこの決まりを常に見張っていて、主キーが重複する行の登録を拒否します。

### 表と表を結ぶ「外部キー」

次に、注文テーブルを見てみましょう（表5-4）。ここでは話を簡単にするため、1回の注文で買う商品は1種類とします。この点は、5-4で改めて考えます。

表5-4　注文テーブル（orders）

| order_id | member_id | product_id | quantity | unit_price | order_date |
| --- | --- | --- | --- | --- | --- |
| 1001 | 1 | 101 | 2 | 1200 | 2026-10-01 |
| 1002 | 2 | 103 | 5 | 400 | 2026-10-01 |
| 1003 | 1 | 102 | 1 | 2500 | 2026-10-02 |
| 1004 | 3 | 101 | 1 | 1200 | 2026-10-03 |

unit_priceは注文時に確定した1個あたりの販売価格です。現在の商品価格は、商品テーブル（products）に記録します（表5-5）。

表5-5　商品テーブル（products）

| product_id | name | price |
| --- | --- | --- |
| 101 | マグカップ | 1200 |
| 102 | トートバッグ | 2500 |
| 103 | ノート | 400 |

注文テーブルには、会員の名前も住所も書かれていません。代わりにmember_idという列があり、会員の番号だけが入っています。注文1001の会員は「1」なので、会員テーブルをたどれば、佐藤花子さんの注文だと分かります。会員4の伊藤さんは、まだ一度も注文していないので、注文テーブルには登場しません。

このように、ほかのテーブルの主キーを参照する列を**外部キー**（foreign key）といいます。注文テーブルのmember_idは、会員テーブルへの外部キーです（図5-1。図では、注文テーブルと会員テーブルの列を一部省いています）。同じようにproduct_idは、商品テーブルへの外部キーです。

![図5-1　主キーと外部キーで結ばれた表（会員と注文）](../figures/fig-5-1.svg)

注文テーブルのmember_idの値をたどると、会員テーブルの同じ番号の行に行き着きます。

外部キーを設定しておくと、DBMSは「参照先に実在する値かどうか」を確かめてくれます。存在しない会員番号「99」の注文を登録しようとすると、エラーになるのです。注文が残っている会員を削除しようとしたときも、拒否したり、あらかじめ決めた処理をしたりできます。テーブル同士の参照に矛盾がない状態を、**参照整合性**（referential integrity）といいます。外部キーは、この状態を保つためのしくみです。

ただし、SQLiteは、何も設定しないと外部キーの検査をしません。接続するたびに「PRAGMA foreign_keys = ON;」という設定文を実行して、検査を有効にします。本書のWeb版は、この設定を済ませた状態でSQLを実行しています。

### なぜ表を分けて結ぶのか

注文テーブルに会員の名前や住所をそのまま書いておけば、たどる手間は省けます。それでも番号だけを書くのは、同じ情報を1か所にだけ置くためです。会員の住所は会員テーブルに1回だけ書かれているので、引っ越しのときに直すのは、その1行だけで済みます。5-1で見た、直し忘れによる不整合は、こうして防がれます。この考え方は、5-4の正規化で詳しく見ます。

ちなみに、「リレーショナル」の元になった「関係」は数学の用語で、表と表の関係ではなく、テーブルそのものを指しています。

### 代表的なRDBMS

よく名前を聞くRDBMSを表5-6にまとめました。表の「オープンソース」は、ソースコード（第3章）が公開され、決められた条件のもとで誰でも利用や改良ができるソフトウェアのことです。

表5-6　代表的なRDBMS

| 名前 | 提供形態 | 特徴 |
| --- | --- | --- |
| MySQL | オープンソース（商用版もある） | Webサービスで広く使われてきた |
| PostgreSQL | オープンソース | 機能が豊富で、拡張しやすい |
| Oracle Database | 商用 | 大企業の基幹システムで多く使われる |
| Microsoft SQL Server | 商用（無償版もある） | マイクロソフト製品と組み合わせやすい |
| SQLite | パブリックドメインで公開 | アプリに組み込んで使う小型のRDBMS |

SQLiteは、サーバーとして動かすのではなく、アプリケーションの中に部品として組み込んで使います。データベース全体が1つのファイルに収まるため、スマホのアプリやブラウザーの内部で広く使われています。

製品は違っても、テーブル、主キー、外部キーという考え方は共通です。既存のシステムを引き継いだら、まずスキーマを読みましょう。どんなテーブルがあり、どの列がどこを参照しているかが分かると、そのシステムが何を扱っているのかが見えてきます。

## 5-3　データベースと会話する言葉 ― SQL

### データベースへの頼み方

RDBに頼みごとをするときは、決まった「頼み方の言葉」を使います。それが**SQL**です。読み方は「エスキューエル」が一般的です。SQLはもともと、1970年代にIBMでリレーショナルデータベースの研究とともに開発されました。その後、1986年にANSI（米国規格協会）、1987年にISO（国際標準化機構）によって規格として定められました。そのため、5-2で紹介したどのRDBMSでも、基本的な書き方は共通です。

SQLの文は、英語に近い単語の組み合わせでできています。SELECTやFROMのような決まった単語は、小文字でもかまいませんが、読みやすさのために大文字で書く習慣が定着しています。文字列の値は「'東京都'」のようにシングルクォーテーションで囲み、文の終わりにはセミコロンを付けます。

SQLの文は、役割でいくつかの種類に分けられます。中心になるのは次の2つです。テーブルなどの構造を定義する文を**DDL**（Data Definition Language：データ定義言語）、データを取り出したり書き換えたりする文を**DML**（Data Manipulation Language：データ操作言語）といいます。ここからは、5-2の会員・注文・商品の3つのテーブルを使って、両方を順に見ていきます。

### 表をつくる

まず、テーブルそのものを作るDDLです。注文テーブルを作るSQLは、たとえば次のようになります。

```sql tables=members,products
CREATE TABLE orders (
  order_id   INTEGER PRIMARY KEY,
  member_id  INTEGER NOT NULL,
  product_id INTEGER NOT NULL,
  quantity   INTEGER NOT NULL,
  unit_price INTEGER NOT NULL,
  order_date DATE    NOT NULL,
  FOREIGN KEY (member_id)  REFERENCES members (member_id),
  FOREIGN KEY (product_id) REFERENCES products (product_id)
);
```

列の名前とデータ型を並べ、order_idが主キーであることを指定しています。NOT NULLは「この列は空にしてはいけない」という意味です。最後の2行は外部キーの指定で、member_idが会員テーブルの主キーを参照すると宣言しています。

主キーや外部キー、NOT NULLのように、列に入れてよい値を縛る決まりを**制約**（constraint）といいます。制約に反する書き込みは、DBMSがエラーにして受け付けません。アプリケーションに不具合があっても、おかしなデータが入り込まないよう、データベース自身が最後の砦になるのです。おもな制約を表5-7にまとめます。

表5-7　おもな制約

| 制約 | 守らせる決まり | 例 |
| --- | --- | --- |
| PRIMARY KEY | 主キー。重複もNULLも許さない | 注文のorder_id |
| FOREIGN KEY | 参照先のテーブルにある値だけを許す | 注文のmember_id |
| NOT NULL | NULLを許さない | 注文のquantity |
| UNIQUE | ほかの行と同じ値を許さない | 会員のメールアドレスを重複させない |
| CHECK | 書いた条件を満たす値だけを許す | CHECK (quantity >= 1) で0個の注文を防ぐ |

### データを取り出す ― SELECT

ここからはDMLです。いちばんよく使うのが、データを取り出すSELECT文です。東京都に住む会員の氏名を取り出してみましょう。

```sql unordered
SELECT name, prefecture
FROM members
WHERE prefecture = '東京都';
```

| name | prefecture |
| --- | --- |
| 佐藤 花子 | 東京都 |
| 高橋 美咲 | 東京都 |

SELECTのあとに取り出したい列を、FROMのあとにテーブル名を書きます。WHEREのあとには、行を絞り込む条件を書きます。全体は「membersテーブルから、東京都の行の、nameとprefectureを選ぶ」と読めます。すべての列がほしいときは、列名の代わりに「\*」と書きます。

並び順を指定するには、ORDER BYを使います。商品を価格の高い順に並べてみます。

```sql
SELECT name, price
FROM products
ORDER BY price DESC;
```

| name | price |
| --- | --- |
| トートバッグ | 2500 |
| マグカップ | 1200 |
| ノート | 400 |

DESCは降順（大きい順）を表します。昇順（小さい順）ならASCと書くか、何も書きません。

ORDER BYを書かなかった場合、結果がどの順に並ぶかは決まっていません。たまたま登録順に並んで見えても、データが増えたり内部の状態が変わったりすると、順序が変わることがあります。順序が必要なら、必ずORDER BYで指定します。

### 条件を書き分ける ― BETWEEN、IN、LIKE、IS NULL

WHEREの条件には、「=」のほかにもいろいろな書き方があります（表5-8）。

表5-8　WHEREに書ける条件

| 書き方 | 意味 | 例 |
| --- | --- | --- |
| =、<>、<、<=、>、>= | 値の比較。<>は「等しくない」 | price >= 1000 |
| AND、OR、NOT | 条件の組み合わせ（かつ、または、〜でない） | price >= 1000 AND price <= 2000 |
| BETWEEN | 範囲。両端の値を含む | price BETWEEN 1000 AND 2000 |
| IN | 並べた値のどれかに等しい | prefecture IN ('大阪府', '福岡県') |
| LIKE | 文字列のパターン。%は0文字以上の任意の文字列 | name LIKE '%藤%' |
| IS NULL、IS NOT NULL | NULLである、NULLでない | email IS NULL |

LIKEを使って、氏名に「藤」を含む会員を探してみます。

```sql unordered
SELECT name, prefecture
FROM members
WHERE name LIKE '%藤%';
```

| name | prefecture |
| --- | --- |
| 佐藤 花子 | 東京都 |
| 伊藤 直樹 | 福岡県 |

「%」を前後に付けたので、「藤」の前後に何文字あっても当てはまります。「'佐藤%'」と書けば、「佐藤」で始まる氏名だけになります。

NULLの扱いには注意が必要です。メールアドレスを登録していない会員を探すには、「=」ではなくIS NULLを使います。

```sql
SELECT name
FROM members
WHERE email IS NULL;
```

| name |
| --- |
| 伊藤 直樹 |

「email = NULL」と書いても、エラーにはなりませんが、どの行も当てはまりません。NULLは「値が分からない」という印なので、何かと比べた結果も、真でも偽でもない「不明」になるからです。WHEREは、条件が真になった行だけを取り出します。Web版では、IS NULLを「= NULL」に書き換えて実行し、結果が0行になることを確かめてみてください。

### データを追加・変更・削除する

データを書き換える文も見ておきましょう。新しい会員を追加するにはINSERT、既存のデータを変更するにはUPDATE、削除するにはDELETEを使います。

```sql
-- 新しい会員を追加する
INSERT INTO members (member_id, name, prefecture, email)
VALUES (5, '田中 健太', '福岡県', 'kenta@example.com');

-- 会員1の都道府県を変更する
UPDATE members
SET prefecture = '神奈川県'
WHERE member_id = 1;

-- 会員5を削除する
DELETE FROM members
WHERE member_id = 5;
```

「--」から行末までは、人間向けのメモ（コメント）です。UPDATEとDELETEでは、WHEREで対象の行を指定している点に注目してください。もしWHEREを書き忘れると、条件がないので「すべての行」が対象になります。全会員の住所が神奈川県になったり、全会員が消えたりするのです。書き換える前に、同じ条件のSELECTで対象を確かめる習慣をつけましょう。

### 集計する ― 集計関数とGROUP BY

ショップの運営では、「注文は全部で何件か」「会員ごとに何回買っているか」といった集計がよく必要になります。SQLには、こうした計算のための**集計関数**が用意されています。件数を数えるCOUNT、合計を求めるSUM、平均を求めるAVG、最大と最小を求めるMAXとMINなどです。

COUNTには2つの書き方があります。COUNT(\*)は、行の数を数えます。ここでの「\*」は「すべての列」ではなく、「行そのもの」を指しています。COUNT(email)のように列名を書くと、その列がNULLでない行だけを数えます。会員テーブルで比べてみましょう。

```sql
SELECT COUNT(*) AS member_count, COUNT(email) AS email_count
FROM members;
```

| member_count | email_count |
| --- | --- |
| 4 | 3 |

会員は4人ですが、メールアドレスを登録しているのは3人です。ASは、結果の列に分かりやすい名前を付けるための書き方です。SUMやAVGなども、NULLの行を除いて計算します。

さらにGROUP BYを組み合わせると、グループごとに集計できます。会員ごとの注文回数と、買った商品の合計数量を求めてみましょう。

```sql unordered
SELECT member_id, COUNT(*) AS order_count, SUM(quantity) AS total_quantity
FROM orders
GROUP BY member_id;
```

| member_id | order_count | total_quantity |
| --- | --- | --- |
| 1 | 2 | 3 |
| 2 | 1 | 5 |
| 3 | 1 | 1 |

GROUP BY member_idは、「member_idが同じ行を1つのグループにまとめよ」という指示です。会員1の注文は1001と1003の2件なので、回数は2、数量は2＋1で3になります。注文のない会員4は、注文テーブルに行がないので、結果にも現れません。

集計した結果でグループを絞り込みたいときは、HAVINGを使います。2回以上注文した会員だけを取り出してみます。

```sql
SELECT member_id, COUNT(*) AS order_count
FROM orders
GROUP BY member_id
HAVING COUNT(*) >= 2;
```

| member_id | order_count |
| --- | --- |
| 1 | 2 |

WHEREとHAVINGは、働く時点が違います。WHEREは、グループにまとめる前の1行ずつを絞り込みます。HAVINGは、まとめた後のグループを絞り込みます。そのため、COUNTやSUMの結果を使う条件は、WHEREには書けず、HAVINGに書きます。

### 表と表をつなぐ ― JOIN

注文テーブルには会員の番号しかないので、そのままでは誰の注文か読み取りにくいですね。そこで、外部キーをたどって複数のテーブルをつなぎ合わせます。これを**結合**（JOIN）といいます。

```sql
SELECT orders.order_id,
       members.name  AS member_name,
       products.name AS product_name,
       orders.quantity
FROM orders
JOIN members  ON orders.member_id  = members.member_id
JOIN products ON orders.product_id = products.product_id
ORDER BY orders.order_id;
```

| order_id | member_name | product_name | quantity |
| --- | --- | --- | --- |
| 1001 | 佐藤 花子 | マグカップ | 2 |
| 1002 | 鈴木 一郎 | ノート | 5 |
| 1003 | 佐藤 花子 | トートバッグ | 1 |
| 1004 | 高橋 美咲 | マグカップ | 1 |

ONのあとには、どの列同士を突き合わせるかを書きます。「注文のmember_idと、会員のmember_idが等しい行同士をつなぐ」という意味です。会員テーブルにも商品テーブルにも、nameという列があります。そこで「members.name」のように、テーブル名を付けて区別しています。

結合と集計は組み合わせられます。商品ごとの売上金額を、多い順に求めてみましょう。

```sql
SELECT products.product_id, products.name, SUM(orders.quantity * orders.unit_price) AS sales
FROM orders
JOIN products ON orders.product_id = products.product_id
GROUP BY products.product_id, products.name
ORDER BY sales DESC, products.product_id;
```

| product_id | name | sales |
| --- | --- | --- |
| 101 | マグカップ | 3600 |
| 102 | トートバッグ | 2500 |
| 103 | ノート | 2000 |

マグカップは、注文1001で2個、注文1004で1個売れています。1,200円×3個で3,600円です。同名の商品も商品番号で区別できます。各注文の単価を使うので、値上げしても過去の売上は変わりません。

### 相手のいない行も残す ― 外部結合

ここまでのJOINは、ONの条件に合う相手が見つかった行同士だけをつなぎます。これを**内部結合**（INNER JOIN）といい、単にJOINと書くと内部結合になります。相手が見つからない行は、結果から落ちます。次の例では、会員に注文をつなぐ問い合わせを、まずJOIN、次にLEFT JOINで実行しています。

```sql
SELECT members.name, orders.order_id
FROM members
JOIN orders ON members.member_id = orders.member_id
ORDER BY members.member_id, orders.order_id;

SELECT members.name, orders.order_id
FROM members
LEFT JOIN orders ON members.member_id = orders.member_id
ORDER BY members.member_id, orders.order_id;
```

| name | order_id |
| --- | --- |
| 佐藤 花子 | 1001 |
| 佐藤 花子 | 1003 |
| 鈴木 一郎 | 1002 |
| 高橋 美咲 | 1004 |

1つ目のJOINの結果は上の4行で、注文のない伊藤さんが落ちています。2つ目のLEFT JOINの結果には、次のように5行目が加わります。

| name | order_id |
| --- | --- |
| 佐藤 花子 | 1001 |
| 佐藤 花子 | 1003 |
| 鈴木 一郎 | 1002 |
| 高橋 美咲 | 1004 |
| 伊藤 直樹 | NULL |

LEFT JOINは、左側（FROMに書いたmembers）の行を、相手がいなくてもすべて残します。相手のいない行では、右側（orders）の列がNULLになります。このように、片方の表の行をすべて残す結合を**外部結合**（OUTER JOIN）といいます。LEFT JOINは左外部結合とも呼ばれます。右側をすべて残すRIGHT JOINや、両側を残すFULL JOINもあります。

外部結合は、「一度も注文していない会員」のように「ないもの」を探すときに役立ちます。上のLEFT JOINに「WHERE orders.order_id IS NULL」を足せば、伊藤さんの行だけが残ります。逆に、内部結合で一覧や集計を作ると、相手のいない行が黙って消える点に注意が必要です。

#### 修正問題　注文のない会員も0回として数える

会員ごとの注文回数の一覧に、注文のない会員も0回として載せます。下のSQLでは、伊藤さんが一覧から落ちています。列名と表示順はそのままに、目標の出力になるように修正しましょう。直す場所は2か所あります。


| name | order_count |
| --- | --- |
| 佐藤 花子 | 2 |

| 高橋 美咲 | 1 |
| 伊藤 直樹 | 0 |

### 選択・射影・結合 ― 表から表を作る操作

ここまでのSELECT文は、3つの基本操作の組み合わせとして整理できます。RDBの土台になっている理論では、これらを**関係演算**と呼びます（表5-9）。

表5-9　関係演算とSQLの対応

| 関係演算 | 表に対する操作 | SQLでの書き方 |
| --- | --- | --- |
| 選択 | 条件に合う行だけを取り出す | WHERE |
| 射影 | 必要な列だけを取り出す | SELECTのあとの列の並び |
| 結合 | 共通の列の値を手がかりに、表と表をつなぐ | JOIN … ON |

紛らわしいことに、SQLのSELECTという単語は、関係演算の「選択」ではなく、列を選ぶ「射影」の場所にあります。行を選ぶ「選択」にあたるのはWHEREです。

大切なのは、どの演算も、表を受け取って表を返すことです。結果がまた表になるので、その結果にさらに演算を重ねられます。次に見る副問合せは、この性質を使っています。

### 問い合わせの中に問い合わせを書く ― 副問合せ

「平均より高い商品」を探すには、まず平均価格を求め、その値と各商品の価格を比べる必要があります。SQLでは、SELECT文の中に、かっこで囲んだ別のSELECT文を書けます。これを**副問合せ**（サブクエリ）といいます。

```sql
SELECT name, price
FROM products
WHERE price > (SELECT AVG(price) FROM products);
```

| name | price |
| --- | --- |
| トートバッグ | 2500 |

DBMSは、かっこの中を先に計算したものとして扱います。3つの商品の平均価格は約1,367円なので、それより高いトートバッグだけが残ります。副問合せが複数の行を返すときは、表5-8のINと組み合わせます。たとえば「WHERE member_id IN (SELECT member_id FROM orders WHERE product_id = 101)」と書けば、マグカップを注文したことのある会員に絞り込めます。

### 見せる範囲を決める ― ビューとGRANT

5-1で、見せる範囲の制御という困りごとを挙げました。RDBMSは、これに2つの道具で応えます。

1つ目は**ビュー**（view）です。ビューは、SELECT文に名前を付けて保存したもので、テーブルと同じように問い合わせられる「仮想の表」です。会員テーブルからメールアドレスを除いたビューを作ってみます。

```sql
CREATE VIEW member_list AS
SELECT member_id, name, prefecture
FROM members;

SELECT * FROM member_list
WHERE prefecture = '東京都'
ORDER BY member_id;
```

| member_id | name | prefecture |
| --- | --- | --- |
| 1 | 佐藤 花子 | 東京都 |
| 3 | 高橋 美咲 | 東京都 |

ビューはデータの写しを持たず、問い合わせるたびに元のテーブルから結果を作ります。会員テーブルを書き換えれば、ビューの見え方もすぐに変わります。

2つ目は、利用者ごとの**権限**です。多くのRDBMSでは、接続する利用者ごとに、どのテーブルやビューに、どの操作（SELECT、INSERTなど）を許すかを決められます。権限を与える文がGRANT、取り消す文がREVOKEです。こうした文は、DDLやDMLと並べて**DCL**（Data Control Language：データ制御言語）と呼ばれます。

```sql norun
GRANT SELECT ON member_list TO staff;
```

これは、staffという利用者に、member_listを読む権限だけを与える文です。会員テーブルそのものへの権限を与えなければ、staffはメールアドレスを見ることも、会員を書き換えることもできません。仕事に必要な最小限の権限だけを与えるこの考え方は、第7章で「最小権限の原則」として改めて取り上げます。

なお、SQLiteにはGRANTがありません。アプリケーションに組み込まれてファイルを直接読み書きするので、利用者を区別するしくみを持たないのです。そのため、上の文はWeb版でも実行できません。

### 「どうやって」ではなく「何がほしいか」を書く

ここまでのSQLを振り返ると、ある特徴に気づきます。「先頭の行から順に読み、条件に合えば取り出す」といった手順を、一度も書いていないのです。書いたのは「どのテーブルの、どんな条件の、どの列がほしいか」だけでした。

第3章で見たような多くのプログラミング言語では、処理の手順を1つずつ書きます。このような言語を**手続き型**と呼びます。それに対してSQLは、ほしい結果だけを書く**宣言型**の言語です。

手順はDBMSが考えます。DBMSの中には、**オプティマイザー**（optimizer）と呼ばれる部品があります。データの量や索引の有無を見て、もっとも速そうな手順を選ぶ役目です。選ばれた手順を**実行計画**と呼びます。

データの量や置き方は、時間とともに変わります。手順を利用者が書くと、状況が変わるたびに書き直さなければなりません。何がほしいかだけを書いておけば、同じSQLのまま、手順の工夫をDBMSに任せられるのです。

### SQLを組み立てるときは、入力の埋め込みに注意する

実際の開発では、プログラムの中でSQL文を組み立て、データベースに送ることがよくあります。このとき、利用者が入力した文字をそのままSQL文に埋め込むのは危険です。悪意のある入力によって、意図しないSQLが実行されてしまうおそれがあるからです。この「SQLインジェクション」と呼ばれる攻撃については、第7章で詳しく見ます。

## 5-4　使いやすい表をつくる ― 正規化とデータ設計

### 1つの表に全部入れると何が起きるか

5-2では、話を簡単にするため、1回の注文で買う商品を1種類としていました。しかし実際のネットショップでは、1回の注文でいくつもの商品をまとめて買えます。こうした現実のデータを、どんな表に分けて持てばよいのでしょうか。

まずは、紙の注文伝票をそのまま写したような表を考えてみます（表5-10）。ここでは分かりやすさのため、列名を日本語で書きます。

表5-10　注文伝票をそのまま写した表

| 注文番号 | 注文日 | 会員番号 | 氏名 | 都道府県 | 購入商品 |
| --- | --- | --- | --- | --- | --- |
| 1005 | 2026-10-04 | 1 | 佐藤 花子 | 東京都 | 101 マグカップ 1,200円×1、103 ノート 400円×3 |
| 1006 | 2026-10-05 | 2 | 鈴木 一郎 | 大阪府 | 102 トートバッグ 2,500円×1 |
| 1007 | 2026-10-05 | 1 | 佐藤 花子 | 東京都 | 103 ノート 400円×2 |

人間が見る伝票としては分かりやすい表ですが、データベースで扱うには問題があります。

たとえば、佐藤花子さんの都道府県が何度も書かれています。佐藤さんが引っ越したら、すべての行を漏れなく直さなければなりません。1行でも直し忘れると、5-1で見た不整合が起きます。これを**更新時異常**と呼びます。

まだ一度も売れていない新商品を登録したいときも困ります。注文がなければ、商品を書く場所がないのです。これを**挿入時異常**と呼びます。

逆に、トートバッグの注文1006を取り消して行を削除したとします。すると、商品番号102がトートバッグだという情報まで一緒に消えてしまいます。これを**削除時異常**と呼びます。

どの問題も、性質の違う情報が1つの表に混ざり、同じ事実が何か所にも書かれていることから起きています。

### 正規化で表を分ける

こうした異常を防ぐために、表を決まった手順で分けていく作業を**正規化**（normalization）といいます。正規化にはいくつかの段階があり、それぞれ「第1正規形」「第2正規形」のように呼ばれます。ここでは、実務でよく目標とされる第3正規形までを見ます。

### 第1正規形 ― 1つのマスには1つの値

表5-10の「購入商品」の列には、複数の商品が詰め込まれています。これでは「ノートを買った注文」を探すのも、売れた数量を合計するのも面倒です。

そこで、1つのマスには1つの値だけを入れるように直します。商品ごとに行を分け、商品番号、商品名、単価、数量をそれぞれ別の列にします（表5-11）。このように、繰り返しの項目をなくし、どのマスにも値が1つだけ入った形を**第1正規形**といいます。

表5-11　第1正規形にした表

| 注文番号 | 商品番号 | 注文日 | 会員番号 | 氏名 | 都道府県 | 商品名 | 注文時の単価 | 数量 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1005 | 101 | 2026-10-04 | 1 | 佐藤 花子 | 東京都 | マグカップ | 1200 | 1 |
| 1005 | 103 | 2026-10-04 | 1 | 佐藤 花子 | 東京都 | ノート | 400 | 3 |
| 1006 | 102 | 2026-10-05 | 2 | 鈴木 一郎 | 大阪府 | トートバッグ | 2500 | 1 |
| 1007 | 103 | 2026-10-05 | 1 | 佐藤 花子 | 東京都 | ノート | 400 | 2 |

伝票に書かれた単価は、その注文で実際に支払われた1個あたりの価格です。そこで列名を「注文時の単価」としました。

この表では、注文番号だけでは行を1つに決められません。注文1005が2行あるからです。注文番号と商品番号を組み合わせれば、行が1つに決まります。このように、複数の列を組み合わせた主キーを**複合キー**と呼びます。

ただし、第1正規形にしただけでは、重複はむしろ増えています。佐藤さんの氏名や都道府県は3行に、ノートという商品名は2行に書かれています。

### 第2正規形 ― キーの一部だけで決まる列を分ける

ここからは、列と列の間の「決まり方」に注目します。ある列Aの値が決まると、別の列Bの値がただ1つに決まるとき、BはAに**関数従属**しているといいます。商品番号が決まれば商品名は1つに決まるので、商品名は商品番号に関数従属しています。

表5-11の主キーは、注文番号と商品番号の組でした。主キー以外の列が、主キーのどの部分で決まるのかを調べてみます。

注文日、会員番号、氏名、都道府県は、注文番号さえ分かれば決まります。商品番号には関係ありません。商品名は、商品番号だけで決まります。このように、複合キーの一部だけに関数従属していることを**部分関数従属**といいます。

一方、数量は、注文番号と商品番号の両方がそろって初めて決まります。キーの一部だけでは決まらず、キー全体によって決まることを**完全関数従属**といいます。

注文時の単価は、どちらでしょうか。商品番号だけで決まるように見えますが、そうではありません。マグカップをあとで1,500円に値上げしても、注文1005で支払われたのは1,200円だという事実は変わらないからです。注文時の単価は「どの注文の、どの商品か」によって決まります。つまり、数量と同じく、主キー全体に完全関数従属する列です。

第1正規形の表から部分関数従属をなくし、主キー以外のすべての列が主キーに完全関数従属するようにした形を、**第2正規形**といいます。部分関数従属している列を、決め手になる列と一緒に別の表へ移します。表5-11は、次の3つの表に分かれます。

- 注文：注文番号、注文日、会員番号、氏名、都道府県
- 商品：商品番号、商品名、現在の価格
- 注文明細：注文番号、商品番号、数量、注文時の単価

商品の表の「現在の価格」は、伝票にはなかった列です。いま売っている価格は、商品番号だけで決まる別の事実なので、商品の表に置きます。5-2で、注文テーブルがunit_priceを、商品テーブルがpriceを持っていたのは、この区別のためです。

これで、まだ売れていない商品も登録できます。注文を取り消しても、商品の情報は消えません。なお、主キーが1列だけの表にはキーの「一部」がないので、第1正規形であれば、そのまま第2正規形でもあります。

### 第3正規形 ― キー以外の列で決まる列を分ける

まだ問題が残っています。注文の表には、氏名と都道府県が注文のたびに書かれます。佐藤さんが引っ越せば、やはり何行も直す必要があります。

よく見ると、氏名と都道府県は、注文番号から直接決まるわけではありません。注文番号から会員番号が決まり、その会員番号から氏名と都道府県が決まっています。このように、主キー以外の列をはさんで間接的に決まることを**推移関数従属**といいます。

第2正規形の表から推移関数従属をなくした形を、**第3正規形**といいます。氏名と都道府県を会員の表に移し、注文の表には会員番号だけを残します。最終的に、表は次の4つになります（表5-12）。

表5-12　第3正規形まで進めた結果

| テーブル | 主キー | そのほかの列 |
| --- | --- | --- |
| 会員 | 会員番号 | 氏名、都道府県 |
| 商品 | 商品番号 | 商品名、現在の価格 |
| 注文 | 注文番号 | 注文日、会員番号（外部キー） |
| 注文明細 | 注文番号＋商品番号 | 数量、注文時の単価 |

注文明細の注文番号と商品番号は、それぞれ注文と商品への外部キーでもあります。佐藤さんの都道府県も、ノートという商品名も、それぞれ1か所にしか書かれていません。

商品の「現在の価格」と注文明細の「注文時の単価」は、同じ値が入ることも多いので、重複に見えるかもしれません。しかし、この2つは別の事実です。正規化の本質は、似た値をなくすことではなく、1つの事実を1か所に置くことです。

ここでは主キーを使って説明しましたが、厳密な定義では、主キーになりうる列の組（候補キー）のすべてについて同じことを考えます。第3正規形の先にも、ボイス・コッド正規形などがあります。ただ、一般的な業務データの多くは、第3正規形まで進めれば十分に扱いやすくなります。

### あえて重複を持たせる ― 非正規化

正規化は万能ではありません。表を細かく分けるほど、データを取り出すときには5-3のJOINでつなぎ直す必要があります。JOINが増えれば、そのぶん処理に時間がかかります。そこで、読み出しの速さを優先して、あえて重複を持たせる設計をすることもあります。これを**非正規化**といいます。

たとえば、注文の表に「合計金額」の列を持たせる設計です。合計金額は注文明細から計算できるので、同じ事実を2か所に置くことになります。その代わり、注文の一覧を表示するたびに明細を集計せずに済みます。引き換えに、明細を変えたら合計も必ず直すという責任が、アプリケーションの側に生じます。まず正規化した設計を作り、速さが足りないと分かった箇所にだけ非正規化を検討するのが基本です。

### ER図でデータの関係を描く

テーブルが増えてくると、全体の関係を文章だけで把握するのは難しくなります。そこで設計の場面では、**ER図**（Entity-Relationship Diagram）と呼ばれる図がよく使われます。

ER図では、会員や注文のように、データとして管理したい対象を**エンティティ**（entity）と呼びます。エンティティを箱で描き、その中に氏名や注文日といった**属性**を書き込みます。そして、エンティティ同士の関係（リレーションシップ）を線で結びます。表5-12の4つの表をER図にすると、図5-2のようになります。

![図5-2　ネットショップのER図（会員・注文・注文明細・商品）](../figures/fig-5-2.svg)

線の両端の記号は、相手が「1つ」なのか「複数」なのかを表します。この数の対応を**カーディナリティ**（多重度）と呼びます。図5-2は、複数の側を鳥の足のような三つ又で描く記法（IE記法）で描いています。縦線は「1」、丸は「0」、三つ又は「多」を表し、箱に近い記号が最大の数、箱から遠い側の記号が最小の数です。

会員と注文を結ぶ線を読んでみましょう。会員の側は縦線が2本なので、1件の注文から見た会員は「ちょうど1人」です。注文の側は丸と三つ又なので、1人の会員から見た注文は「0件以上」です。まだ注文していない会員がいてもよいことまで読み取れます。このような関係を「1対多」といいます。注文と注文明細、商品と注文明細も1対多です。1件の注文には明細が少なくとも1行あるので、注文と結ぶ線の注文明細の側は、縦線と三つ又（1以上）です。まだ一度も売れていない商品もあるので、商品と結ぶ線の注文明細の側は、丸と三つ又（0以上）です。

注文と商品の関係は、もともと「多対多」です。1件の注文に複数の商品が含まれ、1つの商品は多くの注文で買われるからです。RDBでは、多対多の関係をそのまま表せません。そこで、間に注文明細という表をはさみ、2つの「1対多」に分けています。これはRDBの設計でよく使われる定石です。

### コードより先にデータを設計する

プログラムは何度も書き直されますが、データは何年も使われ続け、蓄積されてから構造を変えるのは大きな手間を伴います。新しい機能を作るときは、コードを書く前に、どんなエンティティがあり、どう関係するかをER図に描いてみましょう。

## 5-5　データを正しく守る ― トランザクションと同時実行制御

### 振込の途中で止まったら

銀行で、Aさんの口座からBさんの口座へ1万円を振り込むとします。口座のデータは、次の口座テーブル（accounts）に入っているとしましょう。

```sql norun
CREATE TABLE accounts (
  account_id VARCHAR(10) PRIMARY KEY NOT NULL,
  holder     VARCHAR(20) NOT NULL,
  balance    INTEGER     NOT NULL CHECK (balance >= 0)
);
```

balanceが残高です。CHECK (balance >= 0)は表5-7で見たCHECK制約で、残高がマイナスになる書き込みを拒みます。主キーにNOT NULLも書いているのは、SQLiteの通常のテーブルが歴史的な事情で、「INTEGER PRIMARY KEY」と宣言した列以外の主キーにNULLを許してしまうためです。最初の残高は表5-13のとおりです。

表5-13　口座テーブル（accounts）の最初の状態

| account_id | holder | balance |
| --- | --- | --- |
| A | Aさん | 50000 |
| B | Bさん | 30000 |

振込では、少なくとも次の2つの書き換えが必要です。

1. Aさんの口座の残高を1万円減らす
2. Bさんの口座の残高を1万円増やす

もし、1つ目が終わったところでサーバーの電源が落ちたら、Aさんの残高は減ったのに、Bさんの残高は増えていません。1万円がどこかへ消えてしまいます。

### トランザクション ― 「全部やる」か「何もしない」か

この問題を解決するのが**トランザクション**（transaction）です。トランザクションとは、ひとまとまりで扱うべき一連の処理のことです。DBMSは、その処理を「全部成功させる」か「全部なかったことにする」かのどちらかにし、途中までという状態は残しません。

SQLでは、3つの文でトランザクションを操作します。

- BEGIN：トランザクションを始める。ここから先の変更は、仮の状態に置かれる
- COMMIT：仮の状態だった変更を、まとめて確定する。これを**コミット**（commit）という
- ROLLBACK：仮の状態だった変更をすべて取り消し、BEGINの時点に戻す。これを**ロールバック**（rollback）という

始め方は製品によって少し異なり、START TRANSACTIONと書くものもあります。BEGINを書かずに実行した文は、SQLiteやPostgreSQLなど多くのDBMSで、1文ごとにすぐ確定します。5-3のINSERTやUPDATEは、この形で実行していました。

振込を、トランザクションとして実行してみましょう。

```sql
BEGIN;
UPDATE accounts SET balance = balance - 10000 WHERE account_id = 'A';
UPDATE accounts SET balance = balance + 10000 WHERE account_id = 'B';
COMMIT;

SELECT account_id, balance FROM accounts ORDER BY account_id;
```

| account_id | balance |
| --- | --- |
| A | 40000 |
| B | 40000 |

2つのUPDATEがそろって確定し、どちらの残高も4万円になりました。合計は振込の前と同じ8万円です。

次に、COMMITの代わりにROLLBACKを実行します。取り消す前と後を見比べられるよう、SELECTを2回実行しています。

```sql
BEGIN;
UPDATE accounts SET balance = balance - 10000 WHERE account_id = 'A';
UPDATE accounts SET balance = balance + 10000 WHERE account_id = 'B';

-- 1回目：トランザクションの途中の残高
SELECT account_id, balance FROM accounts ORDER BY account_id;

ROLLBACK;

-- 2回目：取り消したあとの残高
SELECT account_id, balance FROM accounts ORDER BY account_id;
```

| account_id | balance |
| --- | --- |
| A | 40000 |
| B | 40000 |

1回目のSELECTの結果は上のとおりで、振込が済んだように見えます。トランザクションの中からは、自分がまだ確定していない変更も見えるからです。しかし、これは仮の状態です。ROLLBACKのあとの2回目のSELECTでは、次のように最初の残高に戻っています。

| account_id | balance |
| --- | --- |
| A | 50000 |
| B | 30000 |

コミットする前にサーバーが止まった場合も、同じです。DBMSは再起動したときに、確定していない変更を自動で取り消します（図5-3）。

![図5-3　トランザクションのコミットとロールバック（振込の例）](../figures/fig-5-3.svg)

最後まで成功すればコミットで確定し、途中で失敗すればロールバックで開始前の状態に戻ります。

### 失敗に気づいて取り消すのは、アプリケーションの仕事

DBMSは、ROLLBACKと言われれば確実に元へ戻します。しかし、ROLLBACKすべきかどうかを判断するのは、SQLを送るアプリケーションの仕事です。気をつける場面が2つあります。

1つ目は、UPDATEが「正常に終わったのに、1行も書き換えていない」場合です。たとえば振込先の口座番号を間違えて、存在しない「Z」を指定したとします。WHEREに合う行がないだけなので、UPDATEはエラーになりません。このままCOMMITすると、Aさんの残高だけが減ります。そこでアプリケーションは、UPDATEのたびにDBMSから返される「書き換えた行数」を確かめます。Web版の実行欄に「1行を変更しました」のように表示される数です。

2つ目は、文がエラーになった場合です。Aさんの残高は5万円なので、次のように6万円を引き落とそうとすると、CHECK制約に反します。

```sql norun
UPDATE accounts SET balance = balance - 60000 WHERE account_id = 'A';
```

DBMSはこの文をエラーにして、残高を5万円のまま変えません。Web版では、上の振込の実行欄をこの1文に書き換えて実行すると、エラーを確かめられます。ただし、エラーのあとのトランザクションの扱いは、DBMSによって違います。SQLiteやMySQLでは、制約違反で取りやめになるのはエラーになった1文だけで、トランザクションは続いています。エラーを無視して残りの文とCOMMITを実行すると、成功した文の変更だけが確定し、入金だけが行われる、といった事故になります。PostgreSQLは、トランザクションの途中でエラーが起きると、ROLLBACKするまで以降の文を受け付けず、COMMITを送っても取り消しになります。どのDBMSでも、アプリケーションはエラーに気づいた時点でROLLBACKして、処理を打ち切ります。SQLを並べたファイルをまとめて実行する道具には、エラーが起きても次の文へ進むものがあるので、注意が必要です。

アプリケーションが行う振込の流れをまとめると、次のようになります。

```text
BEGIN を実行する
引き落としの UPDATE を実行する
  → エラーになった、または書き換えた行数が1でないなら、ROLLBACK して終了
入金の UPDATE を実行する
  → エラーになった、または書き換えた行数が1でないなら、ROLLBACK して終了
COMMIT を実行する
```

行数を確かめて分岐する処理は、SQLを送るプログラム（たとえばPython）の側に書きます。

### ACID特性

トランザクションが守るべき性質は、4つの英単語の頭文字をとって**ACID特性**と呼ばれます（表5-14）。

表5-14　ACID特性

| 性質 | 英語 | 意味 | 振込の例では |
| --- | --- | --- | --- |
| 原子性 | Atomicity | 全部実行されるか、まったく実行されないかのどちらか | 引き落としの直後に停電しても、引き落としだけが残ることはない |
| 一貫性 | Consistency | データベースの決まりごとが、処理の前後で常に守られる | 残高がマイナスになる書き換えは、CHECK制約によって拒まれる |
| 独立性 | Isolation | 同時に動く複数のトランザクションが、互いに干渉しない | Aさんの残高だけが減った途中の状態は、ほかの処理から見えない |
| 永続性 | Durability | コミットした結果は、障害が起きても失われない | 振込完了の直後に停電しても、振込は取り消されない |

「原子性」の原子は、それ以上分けられないものという意味です。トランザクションは、外からは分割できない1つの操作に見えます。

ACID特性は、DBMSが引き受けてくれる約束です。この約束があるからこそ、アプリケーションの開発者は、「どこからどこまでを1つのトランザクションにするか」と「失敗したらROLLBACKする」ことに集中できます。

### 同時に書き換えるとどうなるか

次に、5-1で見た同時更新の問題を考えます。ネットショップで、残り1個のマグカップを、2人のお客さんがほぼ同時に注文したとします。

1. 1人目の処理が在庫を読む（残り1個）
2. 2人目の処理が在庫を読む（残り1個）
3. 1人目の処理が「在庫あり」と判断し、在庫を0にする
4. 2人目の処理も「在庫あり」と判断し、在庫を0にする

1個しかない商品が2人に売れてしまいました。2人目は、1人目の書き換えを知らないまま上書きしています。このように、ある処理の更新が別の処理に上書きされて失われる現象を**更新の喪失**（ロストアップデート）といいます。

### ロックで順番を守らせる

これを防ぐ代表的な方法が**ロック**（lock）です。トランザクションがデータを使うとき、そのデータに「使用中」の札を掛け、ほかのトランザクションを必要に応じて待たせます。このような制御を**排他制御**といいます。

ロックには、大きく2種類あります。読むときに掛ける**共有ロック**は、ほかの共有ロックと同時に掛けられます。読むだけなら、何人が同時に見ても困らないからです。書き換えるときに掛ける**専有ロック**（排他ロック）は、ほかのどのロックとも同時には掛けられません（表5-15）。

表5-15　ロックの組み合わせ（同じデータに対して）

| 掛けたいロック | すでに共有ロックがある | すでに専有ロックがある |
| --- | --- | --- |
| 共有ロック | 掛けられる | 待つ |
| 専有ロック | 待つ | 待つ |

在庫の例では、「あとで書き換えるつもりで読む」ときに、読む時点で専有ロックを掛けます。多くのDBMSでは「SELECT … FOR UPDATE」と書きます（SQLiteにはない書き方です）。1人目がこの方法で在庫の行を読むと、同じ方法で読もうとした2人目は、1人目のトランザクションが終わるまで待たされます。待ったあとに読む在庫は0なので、「在庫切れ」と正しく判断できます。

実際のDBMSは、表5-15より工夫を重ねています。たとえばPostgreSQLは、既定の設定では、普通のSELECTを待たせず、書き換え中の行については確定済みの値を見せます。そのため、普通に読んだだけでは、在庫を確保したことにはなりません。条件付きのUPDATEを使う方法もあります。商品テーブルに在庫数の列stockがあるとすれば、「UPDATE products SET stock = stock - 1 WHERE product_id = 101 AND stock > 0」と書き、書き換えた行数が1のときだけ注文を受け付けるのです。

ロックには代償もあります。待たされる処理が増えるほど、全体の処理は遅くなります。そこで多くのDBMSは、ロックを掛ける範囲を表全体ではなく行単位に絞ります。また、トランザクション同士をどこまで厳密に隔離するかを、**分離レベル**として選べるようにしています。ACID特性の独立性は、実際には「完全に守るか、守らないか」ではなく、安全性と速さの釣り合いを見て段階的に調整する性質なのです。

### デッドロック ― お互いに待ち続ける

ロックを使うと、困った状況が起きることがあります。トランザクションXが商品Aにロックを掛け、次に商品Bを使おうとしているとします。同時に、トランザクションYは商品Bにロックを掛け、次に商品Aを使おうとしています。XはYがBを放すのを待ち、YはXがAを放すのを待ちます。どちらも相手を待ち続けるので、永遠に先へ進めません。この状態を**デッドロック**（deadlock）といいます。

多くのDBMSは、デッドロックを自動で見つけ出します。そして片方のトランザクションをロールバックさせて、もう片方を先に進めます。

アプリケーションの側では、ロックを掛ける順番をそろえておくと、デッドロックを起こりにくくできます。全員が「商品Aのあとに商品B」の順で使えば、互いに待ち合う形にはなりません。

### ログとバックアップで障害から立ち直る

ACID特性の原子性と永続性は、どのように実現されているのでしょうか。

DBMSは、データを書き換えるとき、ストレージ上のデータ本体をその場で書き換えるわけではありません。まず、メインメモリに読み込んだ写しを書き換えます。第1章のたとえでいえば、食品庫の中で作業するのではなく、作業台に出してきた分を書き換え、あとでまとめて食品庫へ戻すのです。ストレージへの書き込みは遅いので、変更のたびに書き戻していては間に合いません。

しかし、作業台の上のものは、電源が切れると消えます。コミットした変更が作業台の上にしかなければ、永続性を守れません。そこでDBMSは、「どのデータを、何から何に変えたか」を**ログ**（log）と呼ばれる記録に書きます。ジャーナルとも呼ばれます。そして、コミットの時点で、ログだけは確実にストレージへ書き込みます。データ本体より先にログを書くこの方式を、**ログ先行書き込み**（WAL：Write-Ahead Logging）といいます。ログは末尾に追記するだけなので、データ本体を書き換えるよりずっと速く書けます。

メモリ上の変更は、あとでまとめてデータ本体に書き出されます。この書き出しを行い、「ここまではデータ本体に反映済み」という区切りを付ける処理を、**チェックポイント**（checkpoint）といいます。

障害のあとで再起動したDBMSは、最後のチェックポイントより後のログを読み返します。コミット済みなのにデータ本体へ反映されていなかった変更は、ログにある「変更後」の値を使ってやり直します。これを**ロールフォワード**（roll forward）といいます。コミットしていなかったトランザクションの変更が残っていれば、ログにある「変更前」の値を使って取り消します。こちらは、先ほどと同じロールバックです。

ストレージそのものが壊れた場合は、データ本体が失われます。ログを同じストレージに置いていれば、ログも一緒に失われます。そこで、データベースの複製を定期的に別の場所へ保存する**バックアップ**が欠かせません。ログも別の場所に保管しておけば、バックアップを戻したうえで、それ以降のログを使ってロールフォワードし、障害の直前の状態まで復元できます。

### トランザクションの範囲を決め、バックアップは戻して試す

お金、在庫、予約など、つじつまが合わないと困る処理には、必ずトランザクションを使います。ネットショップの注文なら、注文の記録と在庫の引き当てを1つのトランザクションにまとめます。その範囲を決めるのは、アプリケーションを作るエンジニアの仕事です。

バックアップは、「取っている」だけでは不十分です。実際に元に戻せるかを、定期的に試しておきます。戻せないバックアップは、ないのと同じだからです。

## 5-6　速く、大量に扱うための工夫

### 本の索引に学ぶ ― インデックス

分厚い専門書で「デッドロック」という言葉が出てくるページを探すとき、1ページ目から順にめくる人はいません。巻末の索引を開き、五十音順に並んだ項目からページ番号を確かめるでしょう。

データベースも同じです。何百万行もある会員テーブルから、特定のメールアドレスの会員を探すとします。何の工夫もなければ、DBMSは先頭の行から最後の行まで、1行ずつ調べるしかありません。これを**全件走査**（フルスキャン）といいます。第4章で見た線形探索と同じやり方です。

そこで、本の索引にあたるしくみを用意します。これを**インデックス**（index）といいます。第4章で見た配列のインデックス（添字）とは別物で、こちらは「索引」の意味です。インデックスは、特定の列の値を並べ替えて整理し、それぞれの値が表のどこにあるかを記録したものです。メールアドレスの列にインデックスを作っておけば、DBMSは索引をたどって、目的の行へ一気にたどり着けます。

インデックスは、SQLで次のように作ります。

```sql
CREATE INDEX idx_members_email ON members (email);
```

一度作れば、SELECT文を書き換える必要はありません。5-3で見たオプティマイザーが、インデックスを使ったほうが速いと判断したときに、自動で使います。なお、主キーには、多くのRDBMSが自動でインデックスを作ります。

### B木 ― 枝分かれをたどって目的地へ

多くのRDBMSでは、インデックスの中身として**B木**（ビーき：B-tree）と呼ばれるデータ構造を使います。実際にはB木を改良した構造であることが多いのですが、基本の考え方は同じです。

B木は、第4章で見た木構造の一種で、根から枝分かれをたどって目的の値を探します。いちばん上の節（根）には、たとえば「あ〜こ」「さ〜と」「な〜ほ」のような大まかな区切りが書かれています。目的の値が入る範囲の枝を選んで下の節へ進むことを繰り返すと、最後に目的の行の場所にたどり着きます。

B木の特徴は、1つの節から非常に多くの枝が出ていることです。仮に1つの節から100本の枝が出ているとすると、3段たどるだけで100×100×100＝100万通りを区別できます。データが100倍に増えても、たどる段数は1段増えるだけです。だからこそ、データが何百万件、何億件に増えても、検索の速さを保てるのです。

また、B木は値の順に整理されているため、「価格が1,000円以上2,000円以下」のような範囲の検索にも向いています。

### インデックスは作りすぎない

それなら、すべての列にインデックスを作ればよいのでしょうか。そう単純ではありません。本の内容を書き換えたら、索引も直す必要があります。データベースも同じで、行を追加・変更・削除するたびに、関係するインデックスもすべて更新しなければなりません。インデックスが多いほど、書き込みは遅くなります。インデックス自体もストレージの容量を使います。

つまり、インデックスは「読み出しを速くする代わりに、書き込みを少し遅くする」しくみです。実際によく検索に使われる列を見極めて、必要なものだけに作るのが基本です。

「画面の表示が遅い」という問題を調べると、原因がデータベースへの問い合わせにあることは珍しくありません。インデックスがない列で検索していた、必要以上に多くの行を取り出していた、といった具合です。DBMSには、実行計画を表示する機能があります。遅い問い合わせを見つけたら、全件走査になっていないかを実行計画で確かめてみましょう。

### NoSQL ― 表にこだわらないデータベース

RDBは優れたしくみですが、2000年代に入り、世界中から膨大なアクセスが集まるWebサービスが増えると、別の要求も出てきました。

たとえば、データが1台のサーバーに収まりきらず、何台も並べて分担させたい場合です。サーバー1台の性能を上げることを**スケールアップ**、台数を増やすことを**スケールアウト**といいます。従来のRDBは、表同士の結合や厳密なトランザクションを守る必要があるため、スケールアウトがあまり得意ではありません。

また、商品ごとに持つ項目がばらばらだったり、項目が頻繁に増えたりするデータもあります。事前にスキーマを決めるRDBでは、こうしたデータを扱いにくいことがあります。

こうした要求に応えるために広まったRDB以外のデータベースは、まとめて**NoSQL**と呼ばれます。現在では「Not only SQL（SQLだけではない）」の略だと説明されることが多い言葉です。NoSQLには、データの持ち方によっていくつかの種類があります（表5-16）。

表5-16　NoSQLのおもな種類

| 種類 | データの持ち方 | 向いている用途 | 製品の例 |
| --- | --- | --- | --- |
| キーバリュー型 | キー（名札）と値の組 | ログイン状態の保持、キャッシュ | Redis |
| ドキュメント型 | JSONのような入れ子の文書 | 商品カタログ、項目が変わりやすいデータ | MongoDB |
| ワイドカラム型 | 行ごとに異なる列を持てる大きな表 | 大量の書き込み、時系列のデータ | Apache Cassandra |
| グラフ型 | 頂点（ノード）と辺（エッジ） | SNSのつながり、おすすめ機能 | Neo4j |

キーバリュー型は、ロッカーの番号と中身のような関係です。番号を言えば中身がすぐに出てきますが、「赤い荷物が入ったロッカー」のような探し方は苦手です。

### RDBとNoSQLの使い分け

RDBとNoSQLは、どちらが優れているというものではありません。得意なことが違うのです。

お金や在庫のように、つじつまが厳密に合っていなければならないデータや、表同士を結合してさまざまな角度から集計したい場合には、RDBが向いています。

一方、大量のデータを速く読み書きしたい場合や、データの形が決まっていない場合、サーバーを増やして処理を分担したい場合は、NoSQLが力を発揮します。その代わりNoSQLには、結合や複雑な集計が苦手だったり、整合性の保証が弱めだったりするものが多くあります。どこまで保証するかは製品によって異なり、トランザクションに対応したNoSQLもあります。

大きなサービスでは、両方を組み合わせることがよくあります。注文や決済はRDBで管理し、よく表示される商品情報やログイン状態はキーバリュー型に置いて速く取り出す、といった具合です。

### Webアプリとデータベースの関係 ― 3層構造

ネットショップで注文ボタンを押したとき、ブラウザーは、データベースと直接やりとりするわけではありません。一般的なWebアプリは、次の3つの層に分かれています。これを**3層構造**（3層アーキテクチャ）と呼びます（図5-4）。

- **プレゼンテーション層**：画面を表示し、操作を受け付ける（ブラウザー）
- **アプリケーション層**：処理の中身を担う（アプリケーションサーバー）
- **データ層**：データを保管し、問い合わせに答える（データベースサーバー）

![図5-4　Webアプリの3層構造（ブラウザー→アプリケーションサーバー→データベース）](../figures/fig-5-4.svg)

データベースへの問い合わせは、すべてアプリケーションサーバーが代わりに行います。

注文ボタンを押すと、ブラウザーはアプリケーションサーバーに注文の依頼を送ります（このやりとりは第6章で見ます）。アプリケーションサーバーは、在庫を確かめ、注文を記録するためのSQLを組み立てて、データベースに送ります。返ってきた結果を画面の形に整えて、ブラウザーに返します。

ブラウザーから直接データベースにつながない最大の理由は、安全のためです。データベースをインターネットに直接さらせば、誰でも好きなSQLを送れる状態になりかねません。アプリケーションサーバーを間に置けば、許された操作だけをデータベースに届けられます。データベースサーバーは、外部から直接は届かない内側のネットワークに置くのが一般的です。

### クラウドのデータベースサービス

データベースサーバーを自分たちで運用するのは、手間のかかる仕事です。サーバーを用意し、DBMSを導入し、バックアップを取り、障害に備えて予備のサーバーも用意しなければなりません。

近年は、事業者がデータセンターに用意したサーバーなどを、インターネット経由で必要な分だけ借りて使うクラウドが広まりました。データベースの運用を事業者に任せられる**マネージドサービス**も、広く使われています。たとえばAmazon Web ServicesのAmazon RDSは、MySQLやPostgreSQLなどのRDBMSを、事業者の運用のもとで使えるサービスです。NoSQLにも、同じ事業者のAmazon DynamoDBのようなマネージドサービスがあります。

ただし、任せられるのは「運用」の部分です。どんなテーブルを作り、どの列にインデックスを張り、どこをトランザクションにするかという設計の判断は、利用者の仕事として残ります。それぞれのしくみが何を得意とし、何を引き換えにしているのか。その理解が、適切な選択の土台になります。

## コラム　ビッグデータと分析のためのデータベース

積み上がった注文の記録は、「どの商品が、どの季節に売れているか」を分析すれば、仕入れや広告の判断に役立ちます。ところが、こうした分析を、注文を受け付けているデータベースでそのまま行うのは得策ではありません。データベースの仕事には、性格の異なる2種類があるからです。

1つは、注文の登録や在庫の更新のように、少しのデータを素早く何度も読み書きする仕事です。これを**OLTP**（Online Transaction Processing：オンライン・トランザクション処理）といいます。もう1つは、過去数年分の注文を集計するような、大量のデータをまとめて読む仕事です。こちらは**OLAP**（Online Analytical Processing：オンライン分析処理）と呼ばれます。

重い集計を注文用のデータベースで走らせると、その間、注文処理が遅くなるおそれがあります。そこで、社内のさまざまなシステムからデータを集め、分析しやすい形に整えて別の場所に蓄積します。このためのデータベースを**データウェアハウス**（DWH）といいます。ウェアハウスは「倉庫」という意味です。

量（Volume）が膨大で、発生の速さ（Velocity）が速く、種類（Variety）も多様なデータを、**ビッグデータ**と呼びます。分析向けのデータベースでも、何億行ものデータに対する集計をSQLで書けるものが主流です。5-3で学んだSQLは、分析の現場でも共通の言葉なのです。

## 修正問題の解答

### 商品ごとの注文回数を求める

「SUM(quantity)」を「COUNT(*)」に直します。SUM(quantity)は、注文ごとの個数を合計した「売れた個数」です。マグカップは2個と1個の注文があるので3になり、ノートは1回の注文で5個買われたので5になっていました。注文の回数は行の数なので、COUNT(*)で数えます。

```sql answer=order-count tables=members,products,orders
SELECT product_id, COUNT(*) AS order_count
FROM orders
GROUP BY product_id
ORDER BY product_id;
```

| product_id | order_count |
| --- | --- |
| 101 | 2 |
| 102 | 1 |
| 103 | 1 |

列名をorder_countとしても、中身が注文回数になるとは限りません。集計関数が何を数えているかを確かめるのが大切です。

### 合計で3個以上売れた商品を求める

WHEREの行を消し、GROUP BYのあとに「HAVING SUM(quantity) >= 3」を書きます。元のSQLは、合計する前に「1回で3個以上買った注文」だけを残していました。マグカップの注文は2個と1個なので、どちらもこの時点で落ちていたのです。「合計が3個以上」は、グループにまとめた後で調べる条件なので、HAVINGに書きます。

```sql answer=sold-total tables=members,products,orders
SELECT product_id, SUM(quantity) AS total_quantity
FROM orders
GROUP BY product_id
HAVING SUM(quantity) >= 3
ORDER BY product_id;
```

| product_id | total_quantity |
| --- | --- |
| 101 | 3 |
| 103 | 5 |

HAVINGは、GROUP BYのあと、ORDER BYの前に書きます。

### 注文のない会員も0回として数える

「JOIN」を「LEFT JOIN」に、「COUNT(*)」を「COUNT(orders.order_id)」に直します。内部結合では、注文のない伊藤さんの行が結果から落ちます。LEFT JOINに直すと伊藤さんの行は残りますが、COUNT(*)のままでは回数が1になります。相手のいない行も、1行は1行として数えられるからです。その行ではorders.order_idがNULLなので、NULLを数えないCOUNT(orders.order_id)を使うと、0になります。

```sql answer=member-orders tables=members,products,orders
SELECT members.name, COUNT(orders.order_id) AS order_count
FROM members
LEFT JOIN orders ON members.member_id = orders.member_id
GROUP BY members.member_id, members.name
ORDER BY members.member_id;
```

| name | order_count |
| --- | --- |
| 佐藤 花子 | 2 |
| 鈴木 一郎 | 1 |
| 高橋 美咲 | 1 |
| 伊藤 直樹 | 0 |

## 第5章のまとめ

- 大量のデータを、重複や矛盾なく、同時に、速く、安全に扱うために、データベースとそれを管理するDBMSが使われます。
- リレーショナルデータベースは、データをテーブル（行と列）で管理します。行は主キーで1つに特定し、テーブル同士は外部キーで結びつけます。制約に反する書き込みは、DBMSが拒みます。
- SQLは「何がほしいか」を伝える宣言型の言語で、選択（WHERE）、射影（列の指定）、結合（JOIN）を組み合わせて表から表を作ります。手順はDBMSのオプティマイザーが考えます。
- NULLはIS NULLで調べます。内部結合は相手のいない行を落とし、外部結合は残します。WHEREは集計前の行を、HAVINGは集計後のグループを絞り込みます。
- 正規化は、「1つの事実を1か所に」置くように表を分ける作業です。部分関数従属をなくすと第2正規形、推移関数従属もなくすと第3正規形になります。
- トランザクションは、一連の処理を「全部やる」か「何もしない」かのどちらかにします。コミットで確定し、ロールバックで取り消します。失敗に気づいてロールバックを指示するのは、アプリケーションの仕事です。
- ACID特性は、ロックによる排他制御とログによって支えられています。障害のあとは、ロールフォワードとロールバックで正しい状態に戻します。
- インデックスは検索を速くする代わりに、書き込みを少し遅くします。用途によっては、RDBとNoSQLを使い分けたり組み合わせたりします。
- Webアプリでは、ブラウザー、アプリケーションサーバー、データベースの3層構造が一般的です。

次の第6章では、ブラウザーとサーバーの間を、データがどのようにして届くのかを見ていきます。注文ボタンを押してからデータベースに書き込まれるまでの「通り道」である、インターネットのしくみです。
