# 第6章　メッセージが世界を旅する道のりをたどる

スマホで撮った写真をSNSに投稿すると、数秒後には遠く離れた友人の画面にその写真が表示されます。あなたのスマホは、相手のスマホがどこにあるのかも、途中にどんな機械が何台あるのかも知りません。それでも写真は迷わずに届きます。

インターネットはなぜ世界中につながるのでしょうか。この章では、その答えを「約束ごと」と「役割分担」から解き明かしていきます。データを小さな荷物に分けて送るしくみ、住所にあたる番号で届け先を探すしくみ、届いたかどうかを確かめるしくみ、名前から住所を調べるしくみ。これらが層のように積み重なって、はじめて1枚の写真が届きます。章の最後には、ブラウザーにURLを入力してからページが表示されるまでを、学んだ知識で一通りたどります。そのうえで、「つながらない」というトラブルに出会ったとき、どこから順に調べればよいかを1つの手順にまとめます。

## 6-1　ネットワークとインターネット

### ネットワークとは何か

複数のコンピューターを、互いに通信できるように結んだものを**ネットワーク**（network）と呼びます。つなぐ手段は、ケーブルでも電波でもかまいません。スマホ、パソコン、プリンター、テレビ、ゲーム機、防犯カメラ、エアコンまで、今では多くの機器がネットワークの一員です。

### LANとWAN

ネットワークは、広がり方によって2つに分けて呼ばれます。1つは**LAN**（Local Area Network）です。家庭や1つのオフィス、学校の校舎など、限られた範囲の中に作るネットワークを指します。

もう1つは**WAN**（Wide Area Network）です。離れた場所にあるLAN同士を結ぶ、広い範囲のネットワークを指します。たとえば東京本社と大阪支社のLANをつなぐ回線がWANにあたります。WANには、通信事業者の回線を借りて使います。

### 家庭のネットワークの中身

身近な例として、家庭のネットワークをのぞいてみましょう。光回線を契約している家庭なら、おおむね次のような機器が並んでいます。

- 光回線終端装置（ONU）：光ファイバーを伝わる光の信号と、機器が扱う電気の信号を変換する装置
- Wi-Fiルーター：家の中のLANと外のネットワークの境目に立ち、データの出入りを中継する装置
- パソコン、スマホ、テレビなど：実際にデータを使う機器

**Wi-Fi**は、無線LANの規格（IEEE 802.11）に沿った機器を業界団体が認証するときの名称です。一般に「Wi-Fiルーター」と呼ばれている機器は、実は複数の役割を1台にまとめています。電波で機器をつなぐ役割、ケーブルで機器をつなぐ役割、そして家の外との間でデータを中継する**ルーター**（router）の役割です。ルーターの働きは6-3で詳しく見ます。

家の外のつながる先は、**ISP**（Internet Service Provider）です。日本語では「インターネット接続事業者」、一般には「プロバイダー」と呼ばれます。ISPは自社のネットワークを持ち、契約者のデータをインターネットへ送り出します。

### 無線LANとモバイル回線

スマホは、家や店の中ではWi-Fi、屋外ではモバイル回線と、2通りの電波でネットワークにつながります。

Wi-Fiは、世代が進むごとに速くなってきました。規格の正式な名前は分かりにくいので、今は世代の番号で呼ぶのが普通です（表6-1）。

表6-1　Wi-Fiの世代と規格

| 呼び名 | 規格 | 使う電波の周波数帯 |
| --- | --- | --- |
| Wi-Fi 4 | IEEE 802.11n | 2.4GHz帯、5GHz帯 |
| Wi-Fi 5 | IEEE 802.11ac | 5GHz帯 |
| Wi-Fi 6 | IEEE 802.11ax | 2.4GHz帯、5GHz帯 |
| Wi-Fi 6E | IEEE 802.11ax | 6GHz帯も使えるようにしたWi-Fi 6 |
| Wi-Fi 7 | IEEE 802.11be | 2.4GHz帯、5GHz帯、6GHz帯 |

周波数帯によって電波の性質が違います。2.4GHz帯は障害物があっても遠くまで届きやすい反面、電子レンジやBluetoothも同じ帯域を使うので混み合います。5GHz帯や6GHz帯は混雑が少なく速い代わりに、壁などの障害物に弱くなります。

電波は家の外にも届くので、Wi-Fiでは通信を暗号化し、パスワードを知っている機器だけがつなげるようにします。この方式の名前が**WPA2**や、その後継の**WPA3**です。WPA3は、パスワードを次々に試す攻撃に強く、6GHz帯を使う機器では必須になっています。

一方、**モバイル回線**では、スマホは通信事業者が街中に建てた**基地局**と電波でつながります。基地局から先は、通信事業者の光ファイバーなどの有線のネットワークです。移動してもつながり続けるのは、相手をする基地局が近いものへ次々に切り替わるからです。4G（LTE）や5Gは、この方式の世代を表します。Wi-Fiでもモバイル回線でも、電波で運ぶのは最初の1区間だけで、その先のしくみは変わりません。

### インターネットは「ネットワークのネットワーク」

どこかに「インターネット」という巨大な1つのネットワークがあるわけではありません。**インターネット**（the Internet）とは、世界中の無数のネットワークが互いにつながり合ってできた、ネットワークのネットワークです。家庭のLANはISPのネットワークにつながっています。ISPのネットワークは、ほかのISPや、大学、企業、データセンターのネットワークとつながっています。ISP同士は、直接回線を結んだり、**IX**（Internet Exchange、インターネット相互接続点）と呼ばれる施設に集まって接続したりします。

ここで注目したいのは、インターネットには「中心」がないことです。全体を1か所で管理するコンピューターも、すべての通信が必ず通る本部もありません。それぞれのネットワークは別々の組織が運営し、隣のネットワークと約束を交わしてつながっています。

この分散した形には利点があります。新しいネットワークは、既存のどこかにつなぐだけでインターネットの一員になれます。また、ある経路が使えなくなっても、別の経路を回って届けられるので、一部が壊れても全体は止まりにくくなります。異なる組織の機器同士でも話が通じるよう、共通の約束ごとが決められています。その約束ごとを、次の節で見ていきます。

### クライアントとサーバー

インターネット上の通信の多くは、「頼む側」と「応える側」の組み合わせで行われます。

サービスを頼む側を**クライアント**（client）、頼みに応えてサービスを提供する側を**サーバー**（server）と呼びます。Webページを見るときは、スマホのブラウザーがクライアントです。ページのデータを送り返すのがWebサーバーです。

サーバーは、特別な形の機械とは限りません。依頼を待ち受けて応える役割を持つなら、ソフトウェアも、それを動かすコンピューターも、サーバーと呼ばれます。

この分担には理由があります。データや大事な処理をサーバー側に集めておけば、手元の端末は小さく安くて済み、データの更新も一度で全員に反映されます。一方で、サーバーが止まると全員が影響を受けます。そのため多くのサービスは、サーバーを何台も並べて、1台が止まっても困らないように備えています。

## 6-2　通信の約束ごと ― プロトコルと階層モデル

### プロトコルとは

人と話すとき、私たちは無意識のうちに多くの約束を守っています。同じ言語で話す。聞き取れなければ「もう一度お願いします」と頼む。コンピューター同士の通信も同じです。メーカーもOSも違う機器同士が話をするには、あらかじめ決めておいた約束ごとが欠かせません。この通信のための約束ごとを**プロトコル**（protocol）と呼びます。プロトコルには、データをどんな形式で並べるか、どの順番でやりとりするか、失敗したときにどうするか、といった取り決めが書かれています。

インターネットのプロトコルの多くは、**RFC**（Request for Comments）と呼ばれる公開文書として定められています。仕様が誰でも読める形で公開されているので、どの会社でも同じ約束に従った製品を作れます。これが、インターネットが世界中に広がった大きな理由の1つです。

### なぜ階層に分けるのか

通信のために決めておくべきことは多岐にわたります。信号をどう読み取るか。届け先をどう探すか。データが途中で欠けたらどうするか。これらを1つの巨大な約束にまとめると、どこか1か所を変えたいだけでも全体を作り直すことになります。

そこで、通信の仕事をいくつかの段（階層、layer）に分け、段ごとに別々のプロトコルを決めるという方法がとられています。序論で紹介した「階層」の考え方を、通信に当てはめたものです。

手紙を例に考えてみましょう。あなたは便箋に用件を書き、封筒に入れて宛名を書き、ポストに投函します。そこから先、郵便局がどう運ぶのかを、あなたは知る必要がありません。郵便局のほうも、封筒の中に何が書かれているかを気にしません。宛名さえ読めれば届けられます。

この分担のおかげで、配送の手段が変わっても手紙の書き方は変わりません。それぞれの段は、すぐ上とすぐ下の段との受け渡し方さえ守れば、中身を自由に改良できます。コンピューターの通信でも同じです。スマホが自宅でWi-Fiを使っていても、外でモバイル回線を使っていても、ブラウザーは同じ方法でWebページを読み込めます。下の段が入れ替わっても、上の段には影響しないからです。

### TCP/IPの4階層

インターネットで使われている一連のプロトコルは、代表的な2つのプロトコルの名前から**TCP/IP**と呼ばれます。TCP/IPでは、通信の仕事を次の4つの階層に分けて考えます。上の層ほどアプリに近く、下の層ほど物理的な線や電波に近くなります。

表6-2　TCP/IPの4階層

| 階層 | 主な役割 | 代表的なプロトコル・技術 |
| --- | --- | --- |
| アプリケーション層 | アプリ同士がやりとりする内容と手順を決める | HTTP、DNS、SMTP |
| トランスポート層 | 相手のどのアプリに渡すかを区別し、必要なら確実に届ける | TCP、UDP |
| インターネット層 | 宛先のIPアドレスを手がかりに、ネットワークをまたいで届ける | IP |
| ネットワークインターフェース層 | 同じネットワーク内の隣の機器まで、信号として送り届ける | イーサネット、Wi-Fi |

**アプリケーション層**は、手紙でいえば便箋に書く用件と書き方の作法です。**トランスポート層**は、相手の建物に届いた荷物を、どの部屋（どのアプリ）に渡すかを決めます。届いたかどうかの確認もこの層の仕事です。**インターネット層**は、宛名をもとに、いくつもの配送拠点を経由して目的地まで運ぶ役割です。**ネットワークインターフェース層**は、隣の拠点までの1区間を、実際にケーブルや電波で運ぶ役割です。なお、5-6節の3層構造にも「アプリケーション層」や「プレゼンテーション層」が出てきましたが、あちらはWebアプリの役割分担の名前です。ここで見る通信の階層とは別の分け方です。

### OSI参照モデルとの対応

通信の階層を説明するときには、**OSI参照モデル**という7階層のモデルもよく使われます。これは国際標準化機構（ISO）が定めたもので、通信の機能をより細かく7つに分けています。実際のインターネットはTCP/IPで動いていますが、「レイヤー2」「レイヤー3」（略してL2、L3）のような呼び方はOSI参照モデルの番号から来ています。第1章のL2キャッシュ、L3キャッシュとは関係がありません。現場で耳にする機会が多いので、対応関係を押さえておきましょう（表6-3）。

表6-3　OSI参照モデルとTCP/IPの対応（おおまかな目安）

| OSI参照モデル | TCP/IPの4階層 |
| --- | --- |
| 第7層　アプリケーション層 | アプリケーション層 |
| 第6層　プレゼンテーション層 | アプリケーション層 |
| 第5層　セッション層 | アプリケーション層 |
| 第4層　トランスポート層 | トランスポート層 |
| 第3層　ネットワーク層 | インターネット層 |
| 第2層　データリンク層 | ネットワークインターフェース層 |
| 第1層　物理層 | ネットワークインターフェース層 |

たとえば「L3スイッチ」という機器は、第3層、つまりIPアドレスを見て転送できるスイッチという意味です。スイッチとは、LANの中で複数の機器をケーブルでつなぎ、データを中継する機器のことです（6-3で詳しく見ます）。ネットワークエンジニアが「L2の問題」「L7の話」のように層の番号で話すのは、不具合がどの層にあるかを共有するためです。層の境目は厳密に一対一で対応するわけではないので、目安として覚えておけば十分です。

### カプセル化 ― ヘッダーを付けて包む

送る側では、データが上の層から下の層へと渡されていきます。そのとき各層は、受け取ったデータの先頭に自分の層の情報を書いた札を付けます。この札を**ヘッダー**（header）と呼びます。トランスポート層は「どのアプリ宛てか」を、インターネット層は「どのIPアドレス宛てか」を、ネットワークインターフェース層は「隣のどの機器宛てか」を、それぞれヘッダーに書き込みます。

こうして、データは封筒に入れられ、さらに大きな封筒に入れられるように、何重にも包まれていきます。このように、下の層が上の層のデータを丸ごと中身として包むことを**カプセル化**（encapsulation）と呼びます（図6-1）。

包みには、層ごとに呼び名があります。インターネット層でIPヘッダーを付けた包みが、次の項で見るパケットです。ネットワークインターフェース層でさらにヘッダーを付けた、いちばん外側の包みを**フレーム**（frame）と呼びます。ケーブルや電波の上を実際に流れるのは、このフレームです。

![図6-1　TCP/IPの4階層とカプセル化](../figures/fig-6-1.svg)

受け取る側では、逆のことが起きます。下の層から順に自分宛てのヘッダーを読み、外して、中身を上の層へ渡します。最後にアプリケーション層まで届いたとき、元のデータだけが残ります。各層は、自分のヘッダーだけを読めばよく、中身の意味を知る必要はありません。

### パケット交換と回線交換

インターネットでは、大きなデータを一度にまとめて送ることはしません。データを小さく分け、それぞれにヘッダーを付けて送ります。この小分けにしたデータのまとまりを**パケット**（packet）と呼びます。パケットは、宛名を付けて小分けにした荷物のようなものです。1枚の写真も、数百から数千個のパケットに分かれて運ばれます。

このように、パケット単位で回線を共有しながら送る方式を**パケット交換**といいます。これに対し、昔ながらの固定電話は**回線交換**という方式で作られてきました。電話をかけると、通話している2人の間に専用の通り道が確保されます。

2つの方式には、それぞれ得意不得意があります。回線交換は、通り道を確保してしまえば、遅れや途切れが起きにくいのが長所です。その代わり、話していない時間も回線を独り占めするので、使い方に無駄が出ます。パケット交換では、たくさんの人のパケットが同じ回線に混ざって流れます。回線の空き時間を無駄なく使えるので、限られた設備で多くの通信をさばけます。専用の通り道を確保しないので、ある経路が壊れても、続きのパケットを別の経路へ回せる点も強みです。

一方で、パケット交換には弱点もあります。回線が混み合うと、パケットが待たされて遅れが変動します。行き場を失ったパケットが捨てられることもあります。同じ通信のパケットは、ふつうは同じ経路を通ります。それでも、障害や混雑で途中から経路が切り替わると、送った順番とは違う順番で届くことがあります。インターネットは、この弱点を上の層のしくみで補っています。その代表がトランスポート層のTCPで、6-4で詳しく取り上げます。

### 帯域と遅延 ― 回線の速さを表す2つのものさし

「回線が速い」というとき、実は2つの別々のものさしがあります。

1つは**帯域**です。1秒間に運べるデータの量のことで、**bps**（bits per second、ビット毎秒）という単位で表します。「下り100Mbps」なら、1秒間に100Mビット（1億ビット）を受け取れる太さの回線という意味です。もう1つは**遅延**です。送ったデータが相手に届くまでの時間のことで、ms（ミリ秒、1,000分の1秒）で表します。

道路にたとえると、帯域は車線の数、遅延は目的地までの道のりの長さです。車線を増やしても、道のりが遠ければ、1台目が着くまでの時間は縮まりません。動画のダウンロードでは帯域が効き、ビデオ通話やオンラインゲームでは遅延の小ささが効きます。

帯域が分かれば、データを送り終えるまでの時間（伝送時間）を見積もれます。式は「データの量÷回線の速さ」です。ここで、第2章で見たビットとバイトの違いに注意します。ファイルの大きさはバイトで、回線の速さはビットで表すので、8倍して単位をそろえます。6MBの写真を30Mbpsの回線で送る場合を、Pythonで計算してみましょう。

```python
size_mb = 6        # 写真の大きさ（MB）
speed_mbps = 30    # 回線の速さ（Mbps）

size_megabits = size_mb * 8    # 1バイトは8ビットなので、8倍してMビットにする
print(size_megabits, "Mビット")
print(size_megabits / speed_mbps, "秒")
```

```
48 Mビット
1.6 秒
```

6MBは48Mビットなので、30Mbpsの回線なら1.6秒です。これは回線を丸ごと使えた場合の理想の値です。実際には、ヘッダーの分や再送、ほかの通信との分け合いがあるので、もう少し長くかかります。試験問題などでは、回線の速さのうち実際にデータを運べる割合を「伝送効率」として与えます。伝送効率が80%なら、30Mbps×0.8＝24Mbpsで割って、48÷24＝2秒と見積もります。

## 6-3　届け先を見つける ― IPアドレスとルーティング

### IPアドレス ― ネットワーク上の住所

荷物を送るには、届け先の住所が必要です。インターネットでも同じで、通信に参加する機器には、それぞれを区別するための番号が割り当てられます。この番号を**IPアドレス**（IP address）と呼びます。インターネット層のプロトコルである**IP**（Internet Protocol）は、このIPアドレスを宛名として、パケットを目的地まで運びます。

現在広く使われているIPアドレスには2つの版があります。**IPv4**のアドレスは32ビットの数です。人間が読みやすいように、8ビットずつ4つに区切り、それぞれを0から255までの10進数で書きます。たとえば「192.168.1.10」のような形です。第2章で見たように、32ビットで表せる数はおよそ43億通りです。

しかし、パソコンやスマホ、家電までがつながるようになり、IPv4のアドレスは足りなくなりました。そこで作られたのが**IPv6**です。IPv6のアドレスは128ビットあり、事実上使い切れないほどの数を表せます。表記は16ビットずつ8つに区切り、16進数をコロンでつないで「2001:db8::1」のように書きます（0が続く部分は「::」で省略できます。ただし、どこを省いたか分からなくならないよう、使えるのは1か所だけです）。現在は、IPv4とIPv6が併用されている移行期にあります。

### ネットワーク部とホスト部

住所には「東京都板橋区」のような地域の部分と、「1丁目2番3号」のような個々の家の部分があります。郵便の仕分けでは、まず地域の部分だけを見て大まかな行き先を決めます。

IPアドレスも同じように、前半と後半で意味が分かれています。前半はどのネットワークに属しているかを表す**ネットワーク部**、後半はそのネットワークの中のどの機器かを表す**ホスト部**です。どこまでが前半かを示すのが**サブネットマスク**（subnet mask）です。

家庭のLANでよく見かける設定を例にとります。

```text
IPアドレス      192.168.1.10
サブネットマスク 255.255.255.0
CIDR表記        192.168.1.10/24
```

サブネットマスクは、IPアドレスと同じ32ビットの数です。ネットワーク部にあたるビットを1、ホスト部にあたるビットを0にして、境目を示します。第2章で見たとおり、255は8ビットがすべて1の数でした。Pythonのbin()は、数を2進数の表記（先頭に「0b」が付きます）に直す道具です。これで確かめてみましょう。

```python
print(bin(255))
print(bin(0))
```

```
0b11111111
0b0
```

つまり「255.255.255.0」は、1が24個並び、そのあとに0が8個並んだ数です。先頭の24ビットがネットワーク部、残りの8ビットがホスト部であることを表しています。同じことを、アドレスの後ろに「/24」と付けて短く書く方法を**CIDR表記**（サイダー表記）といいます。「/24」の24を**プレフィックス長**と呼びます。この例では「192.168.1」までがネットワーク部、最後の「10」がホスト部です。192.168.1.20のパソコンは同じネットワークの仲間です。一方、192.168.2.20は別のネットワークにいることになります。

前半と後半に分けるのは、世界中の機器の住所を1つ1つ覚えて道案内するのは無理だからです。ネットワーク単位でまとめておけば、インターネット上の中継機器は「203.0.113で始まる宛先はこちら」と、まとめて覚えるだけで済みます。郵便番号で仕分けるのと同じ発想です。なお、本書でインターネット側の例に使う203.0.113.0/24や198.51.100.0/24は、説明用に予約されたアドレスです。実在のサーバーとぶつからないよう、文書の例にはこの範囲を使う決まりになっています。

### サブネットの計算 ― 何台つなげるか

プレフィックス長が決まると、そのネットワークで使えるアドレスの数も決まります。192.168.1.0/24なら、ホスト部は8ビットなので、2の8乗＝256通りです。ただし、両端の2つは特別な役目に使います。

- ホスト部のビットがすべて0のアドレス（192.168.1.0）：ネットワークそのものを指す**ネットワークアドレス**
- ホスト部のビットがすべて1のアドレス（192.168.1.255）：同じネットワークの全員に宛てて送る**ブロードキャストアドレス**

機器に割り当てられるのは、残りの256−2＝254個です。

ネットワークは、8ビットの区切り以外の場所でも分けられます。192.168.1.100/26という設定を考えてみましょう。ホスト部は32−26＝6ビットなので、1つのネットワークは2の6乗＝64個のアドレスを持ちます。192.168.1.0から64個ずつ区切ると、0〜63、64〜127、128〜191、192〜255の4つに分かれます。100は2番目の区間に入ります。したがって、ネットワークアドレスは192.168.1.64、ブロードキャストアドレスは192.168.1.127、機器に割り当てられるのは64−2＝62個です。2進数で見ると、最後の数字の100は01100100です。/26では、このうち先頭の2ビット「01」までがネットワーク部なので、残りの6ビットを0にした01000000（64）がネットワークアドレスになります。

この計算は、Pythonに付属するipaddressという道具でも確かめられます。Pythonでは、「import 名前」と書くと、付属の道具のまとまり（モジュール）を読み込んで、「名前.機能」の形で呼び出せるようになります。「A in B」は、AがBに含まれていればTrue、含まれていなければFalseになる式です。

```python
import ipaddress

net = ipaddress.ip_network("192.168.1.64/26")
print(net.network_address)      # ネットワークアドレス
print(net.broadcast_address)    # ブロードキャストアドレス
print(net.num_addresses - 2)    # 機器に割り当てられる数

print(ipaddress.ip_address("192.168.1.100") in net)
print(ipaddress.ip_address("192.168.1.130") in net)
```

```
192.168.1.64
192.168.1.127
62
True
False
```

192.168.1.130は、最後の数字が128〜191の区間に入るので、隣の別のネットワークの住人です。最初の3つの数字が同じでも、同じネットワークとは限らないことが分かります。

### グローバルIPアドレスとプライベートIPアドレス

IPアドレスには2種類あります。インターネット全体で重複しないよう、管理団体を通じて割り当てられる**グローバルIPアドレス**と、組織や家庭のLANの中だけで自由に使ってよい**プライベートIPアドレス**です。プライベートIPアドレスに使える範囲は決められています（表6-4）。

表6-4　IPv4のプライベートIPアドレスの範囲

| 範囲（CIDR表記） | 主な使われ方の例 |
| --- | --- |
| 10.0.0.0/8 | 大きな企業のネットワーク |
| 172.16.0.0/12 | 企業や組織のネットワーク |
| 192.168.0.0/16 | 家庭や小さなオフィスのLAN |

プライベートIPアドレスは、別の家庭でまったく同じ番号が使われていてもかまいません。その代わり、プライベートIPアドレスのままではインターネットに出ていけません。

### NAT ― 住所の付け替え

では、プライベートIPアドレスを持つスマホは、どうやってインターネット上のサーバーと通信しているのでしょうか。

ここで活躍するのが、家庭のルーターが持つ**NAT**（Network Address Translation、アドレス変換）という機能です。基本の形では、ルーターにISPからグローバルIPアドレスが1つ割り当てられます。家の中の機器がインターネットへパケットを送ると、ルーターは送信元の住所をプライベートIPアドレスから自分のグローバルIPアドレスに書き換えて送り出します。返事が戻ってきたら、どの機器が送ったものだったかを記録から調べ、宛先を元のプライベートIPアドレスに戻して家の中へ届けます。

実際の家庭用ルーターは、6-4で学ぶポート番号も組み合わせて付け替えを行い、1つのグローバルIPアドレスを家中の機器で共有します。この方式を、正確には**NAPT**（Network Address Port Translation）と呼びます。IPマスカレードとも呼ばれます。家庭用ルーターの「NAT」は、ふつうこのNAPTのことです。

NATには、IPv4アドレスの不足を和らげるという大きな効果がありました。家庭や会社ごとにグローバルIPアドレスを1つ用意すれば済むからです。それでも足りなくなり、今では1つのグローバルIPアドレスを複数の契約者で分け合う方式が広がっています。国内の光回線で使われるMAP-Eは、契約者ごとに使えるポート番号の範囲を割り当てて分け合います。DS-Liteやモバイル回線では、事業者側の設備がまとめて変換します（キャリアグレードNATと呼ばれます）。

NATには、外から家の中の機器へ直接話しかけにくくなるという性質もあります。アドレスが十分にあるIPv6では、原則としてNATは要りません。それぞれの機器が世界で1つだけのアドレスを持てるからです。

### ルーターとルーティングテーブル

宛先の住所が分かっても、そこまでの道順が分からなければ届けられません。パケットの道案内を担当するのが、6-1でも登場したルーターです。ルーターは、複数のネットワークの境目に立ち、届いたパケットを次にどこへ送るかを決める装置です。荷物の中継を担う配送拠点にたとえられます。

ルーターは、行き先ごとの道案内の表を持っています。これを**ルーティングテーブル**（routing table、経路表）と呼びます。そこには「このネットワーク宛てなら、この隣のルーターへ渡す」という対応が並んでいます。どの行にも当てはまらない宛先のために、「それ以外はすべてここへ」という行も用意されています。これを**デフォルトルート**と呼びます。家庭のルーターのデフォルトルートは、ISPのルーターを指しているのが普通です。

パケットを受け取ったルーターは、宛先IPアドレスのネットワーク部を見て、ルーティングテーブルから次の転送先を選び、パケットを送り出します。このように、パケットの転送先を決めて送り出すことを**ルーティング**（routing）と呼びます。

### バケツリレーによる転送

ここで大事なのは、どのルーターも目的地までの全行程を知らないということです。各ルーターが知っているのは、「この宛先なら次はあちら」という、次の1区間だけです。同じ宛先なら同じ渡し先を選ぶので、1つの通信のパケットは、ふつうは同じ道筋をたどります。

あなたのスマホから海外のサーバーへ写真を送るとき、パケットはまず家のルーターへ渡されます。家のルーターはISPのルーターへ、ISPのルーターは次のルーターへと、パケットを順々に手渡していきます。1区間ずつの手渡しを何度も繰り返すことで、最終的に目的地へたどり着きます（図6-2）。まさにバケツリレーです。

![図6-2　ルーターによるパケットのバケツリレー](../figures/fig-6-2.svg)

インターネットはあまりに大きく、日々つながり方が変わるので、全体の地図を1台が持ち続けることはできません。その代わり、ルーター同士は**ルーティングプロトコル**と呼ばれる約束に従って、互いに「この宛先なら自分を通れば届く」という情報を交換しています。どこかの経路が切れると、その情報が伝わり、別の経路が選ばれるようになります。

なお、パケットが迷子になって永遠に回り続けないよう、IPv4のヘッダーには**TTL**（Time To Live）、IPv6では**Hop Limit**という数が入っています。ルーターを1つ通過するたびにこの数が1ずつ減り、0になったパケットは捨てられます。

### MACアドレスとイーサネット

IPアドレスは、最終的な目的地を表す住所でした。しかし、実際にケーブルや電波でパケットを運ぶのは、隣の機器までの1区間ずつです。その1区間の届け先を表すのが**MACアドレス**（Media Access Control address）です。

MACアドレスは、ネットワークにつなぐための部品（ネットワークインターフェース）ごとに割り当てられた48ビットの番号です。「00:1A:2B:3C:4D:5E」のように、16進数を区切って書きます。原則として製造時に割り当てられます。ただし最近のスマホやパソコンでは、プライバシー保護のため、接続先ごとに別のMACアドレスを使う機能も一般的です。

有線のLANで最も広く使われている規格が**イーサネット**（Ethernet）です。イーサネットやWi-Fiは、フレームのヘッダーに宛先と送信元のMACアドレスを書いて、データを届けます。ルーターを通らずにフレームが直接届く範囲を**リンク**と呼びます。家庭のLANは、全体が1つのリンクです。

本書のたとえでいえば、IPアドレスは荷物に書かれた最終的な届け先の住所です。MACアドレスは、次の配送拠点までの1区間だけの宛先です。家のスマホから遠くのサーバーへ送るとき、パケットの宛先IPアドレスはサーバーです。しかし、最初のフレームの宛先MACアドレスは家のルーターです。ルーターは受け取ったフレームの包みを外し、次の区間用のフレームに包み直して送り出します。区間を乗り継ぐたびにフレームのヘッダーは作り直されますが、中のパケットの宛先IPアドレスは変わりません（途中でNATが書き換える場合と、TTLが減る点は別です）。

### スイッチとARP ― 1区間を届けるしくみ

LANの中でフレームを中継するのが、6-2で触れた**スイッチ**（スイッチングハブ）です。スイッチは、届いたフレームの送信元MACアドレスを見て、「このMACアドレスの機器は、この差し込み口の先にいる」と覚えていきます。この対応表をMACアドレステーブルと呼びます。宛先MACアドレスが表にあれば、その差し込み口にだけフレームを送り出します。表にまだない宛先のときは、すべての差し込み口に送り出します。

では、送る側は相手のMACアドレスをどうやって知るのでしょうか。分かっているのは、相手のIPアドレスだけです。IPv4では、**ARP**（Address Resolution Protocol）というプロトコルで調べます。まず、「192.168.1.1を使っている方、MACアドレスを教えてください」という問い合わせを、リンクの全員に宛てて送ります。全員宛てに送ることを**ブロードキャスト**と呼びます。該当する機器だけが、「私です。MACアドレスは00:1A:2B:3C:4D:5Eです」と、尋ねた相手にだけ返事をします。調べた結果はしばらく覚えておき、次からは問い合わせを省きます。IPv6では、同じ役目を**近隣探索**（Neighbor Discovery）というしくみが担います。

ここまでに登場したLANの機器を整理しておきましょう（表6-5）。

表6-5　LANで使われる主な機器

| 機器 | 見ている情報 | 役割 |
| --- | --- | --- |
| ハブ（リピーターハブ） | 何も見ない | 届いた信号を、ほかのすべての差し込み口へ流す。今はほとんど使われない |
| スイッチ（スイッチングハブ、L2スイッチ） | MACアドレス | 宛先の機器がいる差し込み口にだけフレームを送る |
| アクセスポイント | MACアドレス | 電波でつながる機器と、有線のLANとの間でフレームを橋渡しする |
| ルーター | IPアドレス | 別々のネットワークの境目で、パケットの次の渡し先を決める |

家庭のWi-Fiルーターは、スイッチ、アクセスポイント、ルーターを1台にまとめた機器です。

### DHCPとデフォルトゲートウェイ ― 最初の渡し先を決める

スマホをWi-Fiにつなぐと、何も設定しなくても通信できます。IPアドレスを決めているのは**DHCP**（Dynamic Host Configuration Protocol）です。ネットワークにつながった端末は、まだ自分のIPアドレスを持っていません。そこで「設定を貸してください」という依頼をブロードキャストで送ります。これを受け取ったDHCPサーバーが、空いているIPアドレスを選んで貸し出します。家庭では、Wi-Fiルーターがこのサーバーの役目をしています。貸し出しには期限があります。このとき端末は、次の4つをまとめて受け取ります。

- 自分のIPアドレス
- サブネットマスク
- **デフォルトゲートウェイ**のIPアドレス：別のネットワーク宛てのパケットを最初に渡すルーター。家庭ではWi-Fiルーター
- DNSサーバーのIPアドレス：6-5で見る、名前から住所を調べてくれるサーバー

端末は、パケットを送るたびに、宛先が自分と同じネットワークにいるかどうかを判定します。自分のIPアドレスと宛先のIPアドレスのそれぞれから、サブネットマスクでネットワーク部を取り出して比べるのです（図6-3）。

![図6-3　同じネットワークかどうかで変わる最初の渡し先](../figures/fig-6-3.svg)

同じネットワークなら、ARPで相手のMACアドレスを調べて、直接フレームを届けます。別のネットワークなら、ARPでデフォルトゲートウェイのMACアドレスを調べて、ルーターにフレームを渡します。どちらの場合も、パケットの宛先IPアドレスは最終的な届け先のままです。

端末も、「自分のネットワーク宛ては直接。それ以外はデフォルトゲートウェイへ」という小さなルーティングテーブルを持っているわけです。だから、サブネットマスクやデフォルトゲートウェイの設定を誤ると、LANの中とは通信できるのに外へは出られない、といった症状が起きます。

自分の端末がどんな設定を受け取ったかは、簡単に確かめられます。Windowsでは`ipconfig`、Linuxでは`ip addr`、macOSでは`ifconfig`というコマンドで表示できます。スマホでは、設定アプリでWi-Fiの接続先の詳細を開くと表示されます。

```text
IPv4 アドレス . . . . . . . : 192.168.1.10
サブネット マスク . . . . . : 255.255.255.0
デフォルト ゲートウェイ . . : 192.168.1.1
```

※Windowsのipconfigの表示を簡略化した一例です。

#### 修正問題　直接届けるか、ルーターに渡すか

IPアドレスが192.168.1.10、サブネットマスクが255.255.255.0のパソコンが、2つの宛先について最初の渡し先を判定するコードです。実行すると、どちらも「直接届ける」と表示されてしまいます。目標の出力になるように、1か所を直しましょう。

ヒント：255.255.255.0は、プレフィックス長でいうといくつでしょうか。そのとき、このパソコンのネットワークアドレスはどうなるでしょうか。解答は、この章のまとめの前にあります。

```python exercise=same-network
import ipaddress

my_network = ipaddress.ip_network("192.168.0.0/16")

for dest in ["192.168.1.20", "192.168.2.20"]:
    if ipaddress.ip_address(dest) in my_network:
        print(dest, "直接届ける")
    else:
        print(dest, "デフォルトゲートウェイへ渡す")
```

目標の出力（修正後）

```text

192.168.2.20 デフォルトゲートウェイへ渡す
```

### ICMP ― pingとtracerouteを支える通知のしくみ

IPには、相棒となるプロトコルがあります。届けられなかった理由を送り主に知らせたり、相手に届くかを確かめたりするための**ICMP**（Internet Control Message Protocol）です。

ICMPを使う代表的な道具が`ping`です。pingは、相手に「聞こえたら返事をください」というICMPのメッセージを送ります。返事が戻れば、相手までIPのパケットが届くこと（疎通）が分かります。往復にかかった時間もmsの単位で表示されるので、6-2で見た遅延を測る道具にもなります。

パケットが本当にバケツリレーで運ばれていることも、ICMPのおかげで確かめられます。macOSやLinuxでは`traceroute`、Windowsでは`tracert`というコマンドを使います。

```text
$ traceroute www.example.com
 1  192.168.1.1     1.2 ms
 2  198.51.100.1    4.8 ms
 3  203.0.113.1     6.1 ms
 ...
```

※表示は簡略化した一例です。アドレスや時間は環境によって異なります。

このコマンドは、TTLを1、2、3と増やしながらパケットを送ります。TTLが尽きたルーターから「ここで捨てました」というICMPの通知が返ってくるので、途中で通ったルーターを順番に知ることができます。1行目は多くの場合、家のルーターです。途中で応答しないように設定されたルーターもあるので、「\*」が並ぶ行があっても異常とは限りません。pingとtracerouteは、6-6でまとめる切り分けの手順でも使います。

## 6-4　確実に届ける ― TCPとUDP、ポート番号

### IPは「届けようと努力する」だけ

IPには1つ大きな割り切りがあります。パケットが確実に届くことまでは約束しないのです。

途中のルーターが混み合えば、パケットは捨てられることがあります。途中で経路が切り替わると、順番が入れ替わって届くこともあります。IPはそれを知らせてくれません。このような「最善は尽くすが保証はしない」という性質は、ベストエフォートと呼ばれます。

この問題を引き受けるのが、IPの1つ上にあるトランスポート層です。トランスポート層の代表的なプロトコルは2つあります。確実さを重視する**TCP**（Transmission Control Protocol）と、速さと手軽さを重視する**UDP**（User Datagram Protocol）です。

### TCP ― 確認しながら確実に届ける

TCPは、データを送る前に、まず相手との間に通信の通り道を作ります。この論理的なつながりを**コネクション**（connection）と呼びます。回線交換のように専用の通り道を確保するわけではなく、送る側と受ける側が互いの状態を管理し合う関係を作るということです。

コネクションを作る手順は、**3ウェイハンドシェイク**（3-way handshake）と呼ばれます。

1. クライアントが「つなぎたい」という合図（SYN）を送る
2. サーバーが「了解、こちらもつなぎたい」という合図（SYN＋ACK）を返す
3. クライアントが「了解」という合図（ACK）を返す

電話で「聞こえますか」「聞こえます。そちらは」「聞こえます」と確かめ合ってから本題に入るようなものです。このやりとりを通じて、両者は互いに送受信ができる状態にあることを確認します。同時に、これから使う通し番号の出発点も伝え合います。

### 順番の管理と、確認応答・再送

コネクションができたら、いよいよデータを送ります。TCPは、送るデータの各部分に**シーケンス番号**という通し番号を付けます。受け取った側は、この番号を見てデータを正しい順番に並べ直します。

受け取った側は、「ここまで受け取りました」という返事を送り返します。これを**確認応答**（ACK：Acknowledgment）と呼びます。送った側は、一定の時間が過ぎても確認応答が返ってこなければ、そのデータが途中で失われたと判断して送り直します。これが**再送**です。

さらにTCPは、相手や途中の回線の混み具合に合わせて、送る量を調整する工夫も持っています。こうした機能のおかげで、アプリを作る人は、データが順番どおりに欠けずに届くものとして扱えます。

ただし、確実さには代償があります。コネクションを作る手間や、確認応答を待つ時間がかかります。データが1つ欠けると、それが再送されて届くまで、後ろのデータもアプリに渡せずに待たされます。

### UDP ― 確認を省いて速さを優先する

UDPは、TCPのような確認の手間をほとんど省いたプロトコルです。コネクションを作らず、いきなりデータを送ります。届いたかどうかの確認も、失われたデータの再送も、順番の並べ直しもしません。

それでも、UDPが向いている場面があります。

- 音声通話やビデオ通話、オンラインゲーム：遅れて届いた古い音声や位置はもう役に立たない。再送を待つより、多少欠けても最新の情報を流し続けたい
- DNSの問い合わせ：短い質問と短い答えを1往復するだけなので、コネクションを作る手間のほうが大きくなる（6-5で詳しく見ます）

つまり、TCPとUDPは優劣ではなく、得意分野の違いです。Webページやメールのように正確さが何より大切な通信にはTCPが、多少の欠けよりも遅れのほうが困る通信にはUDPが選ばれます。UDPを使うアプリの中には、必要な分だけの確認や再送を自分で組み込んでいるものもあります。実際、Webの新しい通信方式であるHTTP/3は、QUIC（クイック）というプロトコルを使います。QUICは、UDPの上に独自の確認や再送のしくみを載せて、TCPと同じように確実に届けます。そのうえで、接続の準備と暗号化の準備を一度にまとめて済ませたり、1か所の欠けがほかのデータを待たせにくくしたりしています。

### ポート番号 ― どのアプリ宛てかを区別する

あなたのパソコンでは、ブラウザーもメールアプリもチャットアプリも同時に動いています。IPアドレスはパソコン1台に対して割り当てられているので、届いたパケットをどのアプリに渡せばよいのか、IPアドレスだけでは分かりません。

この区別に使われるのが**ポート番号**（port number）です。ポート番号は0から65,535までの数で、TCPやUDPのヘッダーに書き込まれます。IPアドレスが建物の住所だとすれば、ポート番号はその建物の中の部屋番号です。住所で建物まで届けたあと、部屋番号を見て渡す先を決めます。

サーバー側のよく使われるサービスには、あらかじめ決まったポート番号があります。0から1023までの範囲がそのために使われ、**ウェルノウンポート**（well-known port）と呼ばれます（表6-6）。

表6-6　代表的なウェルノウンポート

| ポート番号 | 主なサービス | 使うプロトコル |
| --- | --- | --- |
| 22 | SSH（サーバーへの遠隔ログイン） | TCP |
| 25 | SMTP（メールサーバー間の転送。利用者のメールアプリからの送信は587番） | TCP |
| 53 | DNS（名前解決） | 主にUDP（TCPも使う） |
| 80 | HTTP（Webページ） | TCP |
| 443 | HTTPS（暗号化されたWebページ） | TCP（HTTP/3ではUDP） |

一方、クライアント側のアプリには、通信のたびにOSが空いている番号を一時的に割り当てます。サーバーからの返事は、その番号を宛先にして戻ってきます。

通信の相手は、「送信元IPアドレス・送信元ポート番号・宛先IPアドレス・宛先ポート番号」に、TCPかUDPかの種別を加えた組み合わせで区別されます。ブラウザーとメールアプリが同時に通信しても、データが混ざらないのはこのためです。6-3で見たNATも、この組み合わせを記録して、どの機器宛ての返事かを判断しています。

### ポート番号とファイアウォール

開発中のWebアプリを手元で動かすとき、「localhost:3000」のように番号を付けて開くことがよくあります。localhostは「このコンピューター自身」を指す特別な名前です。サーバーを外部に公開するときは、**ファイアウォール**（firewall）で「443番だけを通す」のように、ポート番号を単位に通信を許可したり遮断したりします。ファイアウォールとは、外部とのあいだを流れる通信を調べて、決めた条件に合うものだけを通すしくみです。「つながらない」原因が、実はポートが閉じられていただけ、ということも珍しくありません。

## 6-5　名前から住所を調べる ― DNS

### 人は名前で覚え、機械は番号で運ぶ

ブラウザーに入力するのは、「203.0.113.25」のような数字ではなく、「www.example.co.jp」のような名前です。ところが、パケットを運ぶIPが使うのはIPアドレスです。そこで、通信を始める前に、名前に対応するIPアドレスを調べる必要があります。この「名前から住所を調べる」しくみが**DNS**（Domain Name System）です。名前を引けば番号が分かる、電話帳のようなものです。名前からIPアドレスを調べることを**名前解決**と呼びます。

名前を使う利点は、覚えやすいことだけではありません。サーバーを引っ越してIPアドレスが変わっても、名前とIPアドレスの対応を書き換えるだけで済み、利用者は同じ名前でアクセスし続けられます。

### ドメイン名の階層構造

「www.example.co.jp」のような名前を**ドメイン名**（domain name）と呼びます。ドメイン名は、ドットで区切られた部分ごとに階層を表しています。読むときは、右から左へ向かって範囲が狭くなっていきます。

表6-7　www.example.co.jpの階層

| 部分 | 意味 |
| --- | --- |
| jp | 日本を表すトップレベルドメイン |
| co | 日本の企業向けであることを表す区分 |
| example | 組織が登録した名前 |
| www | その組織の中の、特定のサーバーやサービスの名前 |

いちばん右の部分を**トップレベルドメイン**（TLD：Top Level Domain）と呼びます。「jp」「uk」のような国や地域を表すものと、「com」「org」のような分野を表すものなどがあります。さらにその上には、目には見えない頂点として「ルート」があります。ドメイン名の世界は、ルートを頂点とした大きな木の形をしているのです。

この木の各部分は、それぞれ別の組織が管理しています。ルートはインターネット全体の調整を担う組織のもとで管理され、「jp」は日本のドメイン名を管理する事業者が担当します。「example.co.jp」の中身は、それを登録した組織自身が管理します。上の階層は「下の階層を誰が担当しているか」だけを知っていて、細かい中身は担当者に任せています。こうして、世界中の膨大な名前を、どこか1か所に集めずに扱えます。

### 名前解決の流れ

では、実際の名前解決の流れを追ってみましょう。スマホのブラウザーで「www.example.co.jp」を開く場面です（図6-4）。

まず、スマホは自分では調べ回りません。代わりに調べてくれるサーバーへ「www.example.co.jpのIPアドレスを教えてください」と頼みます。このサーバーを**フルサービスリゾルバー**（キャッシュDNSサーバーとも呼ばれます）と呼びます。多くの場合、契約しているISPが用意したものが使われます。そのIPアドレスは、6-3で見たDHCPで端末に知らされています。

頼まれたフルサービスリゾルバーは、階層の上から順番に問い合わせていきます。

1. **ルートサーバー**に尋ねる。ルートサーバーは答えそのものは知らないが、「jpのことはjpのサーバーに聞いてください」と、担当サーバーを教えてくれる
2. jpを担当する**TLDのサーバー**に尋ねる。ここでも答えは返らないが、「example.co.jpのことは、この組織のサーバーに聞いてください」と教えてくれる
3. example.co.jpを担当する**権威DNSサーバー**に尋ねる。このサーバーは自分の担当範囲の正式な情報を持っているので、「www.example.co.jpのIPアドレスはこれです」と答えてくれる

フルサービスリゾルバーは、こうして得たIPアドレスをスマホに返します。スマホはそのIPアドレスを宛先にして、ようやくWebサーバーとの通信を始められます。

![図6-4　DNSの名前解決の流れ](../figures/fig-6-4.svg)

ルートサーバーは世界中の多数の拠点に複製されているので、どこか1か所が止まっても、名前解決全体が止まることはありません。

### キャッシュとTTL

この流れを毎回繰り返していたら時間がかかり、ルートサーバーにも膨大な問い合わせが押し寄せます。そこでDNSでは、一度調べた結果を一定時間覚えておくキャッシュのしくみが使われています。第1章で見た「よく使うものの写しを速い場所に置いておく」キャッシュと同じ発想です。フルサービスリゾルバーは、調べた答えを手元に保存しておきます。次に誰かが同じ名前を尋ねたら、上の階層へ問い合わせずにすぐ答えを返せます。スマホやパソコンのOS、ブラウザーも、それぞれ小さなキャッシュを持っています。

ただし、覚えた情報が古くなる心配もあります。そこで、DNSの情報には、キャッシュしてよい時間が秒単位で添えられています。これをTTL（Time To Live）と呼びます。IPのヘッダーのTTL（6-3）とは別物ですが、「寿命」という考え方は共通しています。

TTLを長くすれば問い合わせが減って速くなりますが、変更が行き渡るまでに時間がかかります。短くすれば、その逆です。そのためエンジニアは、サーバーの引っ越しを予定しているときには、事前にTTLを短くしておくといった工夫をします。

### DNSに登録されている情報

DNSには、IPアドレス以外の情報も登録できます。登録される情報の1件1件を**リソースレコード**と呼び、種類ごとに名前が付いています。

表6-8　代表的なリソースレコード

| 種類 | 内容 |
| --- | --- |
| A | 名前に対応するIPv4アドレス |
| AAAA | 名前に対応するIPv6アドレス |
| CNAME | 別名（ある名前を、別の名前の別名として登録する） |
| MX | その名前宛てのメールを受け取るサーバー |
| NS | そのドメインを担当する権威DNSサーバー |

### DNSが止まると何が起きるか

DNSは、ふだんは存在を意識されませんが、止まったときの影響は甚大です。止まり方は、どのサーバーが止まるかで変わります。

フルサービスリゾルバーが応答しなくなると、そのリゾルバーを使っている利用者は、どのサイトも開けなくなります。Webサーバーは元気に動いていても、名前からIPアドレスを調べられないので、通信を始めることすらできないからです。

一方、権威DNSサーバーが止まると、そのサーバーに名前を任せていたサービスだけが、世界中の利用者から見つけにくくなります（キャッシュに答えが残っている間は開けます）。実際に2016年10月、多くの企業から権威DNSサーバーの運用を任されていたDynという事業者が、大量の通信を送りつける攻撃（第7章で見るDDoS攻撃）を受けました。Dynに名前を任せていたTwitterやSpotifyなどのサービスが、一時つながりにくくなりました。攻撃の送信元は、Miraiという不正なプログラム（マルウェア）に感染した、多数のIoT機器（インターネットにつながる家電やカメラなど）でした。こうした機器が攻撃に悪用される問題は、7-2で取り上げます。設定ミスで誤ったレコードを登録してしまい、サービスが見えなくなるという事故も、たびたび起きています。

そのためエンジニアは、つながらない原因を探るとき、「名前解決ができているか」を早い段階で確かめます。`nslookup`や`dig`といったコマンドを使うと、ある名前がどのIPアドレスに解決されるかを調べられます。

```text
$ nslookup www.example.co.jp
Name:    www.example.co.jp
Address: 203.0.113.25
```

※説明用に簡略化した架空の例です。実際の表示は環境によって異なります。

## 6-6　Webページが表示されるまで

### URL ― 何を、どこから、どうやって取ってくるか

いよいよ、ここまで学んだしくみを組み合わせる番です。まずは、ブラウザーに入力するURLから見ていきましょう。**URL**（Uniform Resource Locator）は、インターネット上の情報の置き場所を示す書き方です。次のURLを例にします。

```text
https://www.example.co.jp:443/news/index.html?page=2#top
```

URLは、いくつかの部品に分けて読めます（表6-9）。

表6-9　URLの構造

| 部品 | 例 | 意味 |
| --- | --- | --- |
| スキーム | https | どの方式（プロトコル）で取りに行くか |
| ホスト名 | www.example.co.jp | どのサーバーから取ってくるか |
| ポート番号 | 443 | サーバーのどの窓口に頼むか（省略されることが多い） |
| パス | /news/index.html | サーバーの中のどの情報か |
| クエリ | page=2 | サーバーに渡す追加の条件 |
| フラグメント | top | ページの中のどの位置を表示するか（ブラウザーだけが使う） |

つまりURLは、「どの方式で」「どのサーバーの」「どの情報を」取ってくるかを1行で表したものです。ホスト名はDNSでIPアドレスに変換され、ポート番号はトランスポート層の窓口を指します。ポート番号を省略すると、6-4で見たとおり、httpなら80番、httpsなら443番が使われます。

URLの分解は、プログラムにもよく出てくる処理です。Pythonに付属のurllib.parseというモジュールにあるurlsplitを使うと、表6-9と同じ部品に分けられます。「from モジュール名 import 機能名」は、モジュールの中から機能を1つだけ読み込む書き方です。

```python
from urllib.parse import urlsplit

url = urlsplit("https://www.example.co.jp:443/news/index.html?page=2#top")
print(url.scheme)      # スキーム
print(url.hostname)    # ホスト名
print(url.port)        # ポート番号
print(url.path)        # パス
print(url.query)       # クエリ
print(url.fragment)    # フラグメント
```

```
https
www.example.co.jp
443
/news/index.html
page=2
top
```

### HTTP ― リクエストとレスポンス

ブラウザーとWebサーバーの会話に使われるアプリケーション層のプロトコルが**HTTP**（Hypertext Transfer Protocol）です。ブラウザーが「これをください」と頼み、サーバーが「どうぞ」と返す。この1往復が基本です。

ブラウザーが送る頼みごとを**リクエスト**（request）、サーバーが返す答えを**レスポンス**（response）と呼びます。HTTPのメッセージは、もともと人間にも読める文字で書かれていました。リクエストの一例を、簡略化して示します。

```text
GET /news/index.html?page=2 HTTP/1.1
Host: www.example.co.jp
User-Agent: (ブラウザーの種類)
Accept-Language: ja
```

1行目は「/news/index.html?page=2をGETします」という依頼です。URLのうち、パスとクエリがここに入ります。ホスト名は2行目のHostで伝えます。フラグメント（#top）はどこにも入っていません。フラグメントはブラウザーがページ内の表示位置を決めるために使う部分で、サーバーには送られないのです。2行目以降は**HTTPヘッダー**と呼ばれ、宛先のホスト名や、ブラウザーの種類、希望する言語などの付帯情報を伝えます。

これに対し、サーバーは次のようなレスポンスを返します。

```text
HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8
Content-Length: 5120

<!DOCTYPE html>
<html> ...（ページの中身）... </html>
```

1行目の「200 OK」は、依頼がうまく処理できたことを表します。続くヘッダーで中身の種類や大きさを伝え、空行のあとにページの本体が続きます。なお、新しいHTTPの版（HTTP/2やHTTP/3）では、メッセージの区切りやヘッダーを文字ではなくバイナリーの形式で送ります。1本の接続の中で、複数のリクエストとレスポンスを並行してやりとりできるようにするためです。運ばれるHTMLなどの中身や、リクエストとレスポンスという考え方は変わりません。

HTTPには、もう1つ重要な性質があります。基本的に、1回1回のやりとりを独立したものとして扱い、前のやりとりを覚えていないのです。この性質を**ステートレス**（stateless）と呼びます。覚えておく必要がないぶん、サーバーのしくみを単純にでき、大量の利用者をさばきやすくなります。一方、ログインしたままの状態を保つには工夫が必要です。そこで、サーバーが渡した小さな情報をブラウザーが保存し、次のリクエストのたびに送り返す**Cookie**（クッキー）というしくみが使われています。

### メソッド ― 何をしてほしいのか

リクエストの1行目の先頭にある「GET」は、サーバーに何をしてほしいかを表す**メソッド**（method）です。よく使われるのは次の2つです。

- GET：情報を取得する。Webページを表示するときや、検索結果を見るときに使われる
- POST：情報を送信する。フォームの入力内容を送るときや、写真を投稿するときに使われる

このほか、情報の更新を表すPUTや、削除を表すDELETEなどもあり、Webアプリを作るときにはこれらを使い分けます。

#### 修正問題　サーバーに送るリクエスト行を作る

URLから、HTTPのリクエストの1行目を組み立てるコードです。文字列どうしを「+」でつなぐと、1つの文字列になります。このコードは、サーバーに送るべき部品を落とし、送らない部品を入れてしまっています。目標の出力になるように直しましょう。

ヒント：パスの後ろに付けてサーバーに送るのは、クエリとフラグメントのどちらでしょうか。区切りの記号も変わります。解答は、この章のまとめの前にあります。

```python exercise=request-line
from urllib.parse import urlsplit

url = urlsplit("https://www.example.co.jp/search?q=wifi#result")
target = url.path + "#" + url.fragment
print("GET", target, "HTTP/1.1")
print("Host:", url.hostname)
```

目標の出力（修正後）

```text
GET /search?q=wifi HTTP/1.1
Host: www.example.co.jp
```

### ステータスコード ― 結果はどうだったのか

レスポンスの1行目にある「200」のような3桁の数を**ステータスコード**（status code）と呼びます。百の位の数字で、結果がおおまかに分類されています。

表6-10　ステータスコードの分類

| ステータスコード | 意味 | よく見る例 |
| --- | --- | --- |
| 200番台 | 成功 | 200 OK（正常に処理できた） |
| 300番台 | 追加の対応が必要（別の場所への案内など） | 301 Moved Permanently（恒久的に移転した）、304 Not Modified（前回から変わっていないので、手元の写しを使ってよい） |
| 400番台 | クライアント側の問題 | 404 Not Found（指定された情報が見つからない） |
| 500番台 | サーバー側の問題 | 500 Internal Server Error（サーバー内部でエラーが起きた） |

「404 Not Found」は、サーバーには届いたものの、指定されたパスの情報がなかったという意味です。一方、500番台はサーバー側のプログラムや設定に問題があることを示します。304は、ブラウザーが前に受け取って保存しておいた写し（キャッシュ）をそのまま使ってよい、という返事です。同じ画像を何度も送り直さずに済みます。ステータスコードを見れば、問題がクライアント側にあるのかサーバー側にあるのかの見当がつきます。

### HTML・CSS・JavaScript ― ページを形作る3つの言語

サーバーから届いたページの本体は、主に3種類のファイルでできています。

- **HTML**（HyperText Markup Language）：ページの構造と内容を表す。見出し、段落、画像、リンクなどを記述する
- **CSS**（Cascading Style Sheets）：ページの見た目を表す。文字の色や大きさ、配置などを指定する
- **JavaScript**：ページに動きを付けるプログラミング言語。ボタンを押したときの処理などを担う

ブラウザーは、最初に受け取ったHTMLを先頭から読み進めます。その中には、「このCSSファイルを使う」「この画像を表示する」といった指示が書かれています。ブラウザーはそれを見つけるたびに、追加のリクエストを送って必要なファイルを集めます。1つのページを表示するために、数十回以上のリクエストが送られることも珍しくありません。集めた材料から各要素の位置と大きさを計算し、画面に描きます。

### HTTPS ― 通信を暗号化する

ここまでの説明では、HTTPのメッセージは中身がそのまま読める形で運ばれていました。途中のネットワークで誰かがのぞき見れば、入力したパスワードや個人情報が読まれてしまうおそれがあります。

そこで現在のWebでは、通信を暗号化した**HTTPS**（HTTP Secure）が標準になっています。URLが「https://」で始まるサイトでは、ブラウザーとサーバーの間のやりとりが暗号化され、途中で読まれたり書き換えられたりしにくくなっています。また、接続している相手が本物のサーバーかどうかを確かめるしくみも備えています。暗号化と相手の確認を受け持つのはTLSというプロトコルで、HTTPSは「TLSで守ったHTTP」です。TLSや証明書のしくみについては、第7章で詳しく見ます。

### VPN ― 離れた場所を安全につなぐ

HTTPSが守るのは、ブラウザーとサーバーの間の1つの通信です。これに対し、端末やLANから出る通信をまとめて守る技術が**VPN**（Virtual Private Network、仮想専用線）です。

VPNは、6-2で見たカプセル化の応用です。送りたいパケットを丸ごと暗号化し、それを別のパケットの中身として包んで、VPNの装置まで運びます。インターネットという公共の道路の中に、外から中が見えないトンネルを通すようなものです。受け取った装置は、包みを外して元のパケットを取り出し、その先のネットワークへ流します。

自宅や外出先から会社のLANにつなぐときや、離れた拠点のLAN同士をつなぐときに使われます。6-1で見たWANを、専用の回線を借りずにインターネットの上に作れるので、費用を抑えられます。

### メールを運ぶプロトコル

アプリケーション層のプロトコルは、HTTPだけではありません。メールは、役割の違う複数のプロトコルを組み合わせて届けます。

- **SMTP**：メールを送り出し、相手のメールサーバーまで転送する
- **POP3**：メールサーバーに届いたメールを、端末に取り込む。取り込んだメールは端末で管理する
- **IMAP**：メールをサーバーに置いたまま読む。スマホとパソコンのどちらから見ても、同じ状態になる

あなたのメールアプリは、SMTPで自分の側のメールサーバーにメールを渡します。メールサーバーは、宛先のドメイン名のMXレコード（6-5）をDNSで調べ、相手のメールサーバーへSMTPで転送します。相手は、POP3やIMAPで自分のメールサーバーからメールを受け取ります。送るしくみと受け取るしくみが分かれているのは、相手の端末の電源が入っていなくても、サーバーが預かっておけるようにするためです。

### URLを入力してから表示されるまでのおさらい

最後に、ブラウザーに「https://www.example.co.jp/」と入力してから、ページが表示されるまでの流れをまとめてみましょう。

1. DNSで名前解決をする：フルサービスリゾルバーに問い合わせ、www.example.co.jpのIPアドレスを得る（6-5）
2. TCPのコネクションを作る：得たIPアドレスと443番ポートに向けて、3ウェイハンドシェイクを行う（6-4）
3. 暗号化の準備をする（TLS）：鍵の材料を交換して双方で同じ鍵を作り、続いてサーバーの証明書と署名を検証して、相手が本物のサーバーかを確かめる（7-4）
4. HTTPのリクエストを送る：GETメソッドで、ページのHTMLを要求する
5. HTTPのレスポンスを受け取る：ステータスコード200とともに、HTMLが返ってくる
6. 必要なファイルを集めて組み立てる：CSSや画像、JavaScriptを追加で取得し、ページを組み立てて画面に描く

HTTP/3を使う場合は、手順2と3が変わります。UDPの443番ポートに向けて、QUICが接続の準備と暗号化の準備をまとめて行います。

この間、すべてのデータはパケットに分けられ、ヘッダーで何重にも包まれて送られています（6-2）。スマホは最初のフレームをデフォルトゲートウェイに渡し、各パケットはルーターのバケツリレーで目的地まで運ばれています（6-3）。そして、欠けたパケットはTCPが再送して補っています（6-4）。たった1秒ほどの出来事の中で、これだけの仕事が分担されているのです。

### つながらないときの切り分け手順

この流れを知っていると、「ページが表示されない」というときに、どこで止まっているのかを順に確かめられます。コツは、下の層から、そして手元に近いところから順に調べることです。1つ確かめるごとに、「ここまでは届いている」という範囲が広がっていきます（表6-11）。

表6-11　つながらないときに確かめる順番

| 順番 | 確かめること | 使う道具 | だめなときに疑う場所 |
| --- | --- | --- | --- |
| 1 | 自分の端末がIPアドレスなどの設定を受け取っているか | ipconfig、ip addr、スマホの設定画面 | Wi-Fiやケーブルの接続、DHCP |
| 2 | デフォルトゲートウェイまで届くか | ping 192.168.1.1（自分のゲートウェイのアドレス） | LANの中（電波、ケーブル、スイッチ） |
| 3 | インターネット上のIPアドレスまで届くか | IPアドレスを指定したping | ルーターから先（回線、ISP） |
| 4 | 名前解決ができるか | nslookup 名前 | DNS |
| 5 | どこまで届いているか | traceroute（Windowsではtracert） | 応答が途切れたあたりの経路 |
| 6 | サーバーは何と答えているか | ブラウザーの開発者ツール | ポートの遮断、サーバーやアプリ |

手順3では、名前ではなくIPアドレスを指定するのが要点です。名前を使うと、DNSの問題なのか経路の問題なのかを区別できないからです。ただし、pingに返事をしない設定のサーバーもあるので、複数の相手で試します。なお、HTTPSのサイトを、ブラウザーにIPアドレスを直接入力して開こうとしてはいけません。証明書の名前と一致しないので、DNSとは関係なく警告が出てしまいます。

手順6で使う開発者ツールは、ブラウザーに組み込まれた調査用の画面です。リクエストごとのステータスコードや、名前解決、接続、応答待ちのそれぞれに何msかかったかを確認できます。この章で学んだ層の知識は、そのまま調査の手順になるのです。

## コラム　インターネットの「物理的な姿」― 海底ケーブルとデータセンター

「クラウド」という言葉のせいか、インターネットは空中のどこかに浮かんでいるもののように感じられるかもしれません。しかし実際のインターネットは、ケーブルと機械でできた、きわめて物理的な存在です。

その代表が、海の底に敷かれた**海底ケーブル**です。国をまたぐデータ通信のほとんどは、衛星ではなく、海底を這う光ファイバーのケーブルが担っています。

深い海の底に置かれるケーブルは、意外なほど細く、太さは家庭の水まきホースほどです。長い距離を進むうちに光の信号は弱まるため、途中には数十kmごとに信号を増幅する中継器が組み込まれています。

ケーブルが切れる原因として多いのは、錨や漁具による損傷や、地震などの自然災害です。修理の間も、6-3で見たように、データは別のケーブルを経由する経路に切り替えられます。

ケーブルの先には、**データセンター**があります。データセンターは、大量のサーバーを安全に動かし続けるために作られた専用の建物です。停電に備えた自家発電設備や、サーバーの熱を逃がす大規模な冷却設備を備えています。SNSの写真も動画配信の映像も、最終的にはどこかのデータセンターのサーバーに保存されています。

物理的な距離は、通信の速さにも影響します。光ファイバーの中の光は、1秒間におよそ20万km進みます。とても速いようですが、地球の裏側までは地表に沿っておよそ2万kmあります。往復で4万kmなので、4万km÷20万km/秒＝約0.2秒が、光が進むだけでかかります。これが、6-2で見た遅延の下限になります。そのため、大きなWebサービスは世界各地にデータセンターを置き、利用者の近くから応答できるようにしています。よく見られる画像や動画を利用者の近くに置いておく**CDN**（Content Delivery Network）というしくみも広く使われています。

画面の向こうには、こうした目に見えない設備と、それを守る人たちの仕事が広がっているのです。

## 修正問題の解答

### 動画のダウンロードは何秒かかる？

動画の大きさを8倍して、ビットにそろえてから割ります。300MBは2,400Mビットなので、100Mbpsの回線では24秒かかります。元のコードは、バイトで数えた大きさを、ビットで数えた速さでそのまま割っていました。

```python answer=transfer-time
size_mb = 300       # 動画の大きさ（MB）
speed_mbps = 100    # 回線の速さ（Mbps）

seconds = size_mb * 8 / speed_mbps
print(seconds, "秒")
```

実行結果は次のとおりです。

```text
24.0 秒
```

### 直接届けるか、ルーターに渡すか

ネットワークを「192.168.1.0/24」に直します。255.255.255.0は、1が24個並んだマスクなので、プレフィックス長は24です。192.168.1.10の先頭24ビットを残し、ホスト部を0にすると、ネットワークアドレスは192.168.1.0になります。元のコードの「/16」では、192.168で始まるアドレスがすべて同じネットワークの仲間と判定されていました。実際の端末でマスクの設定を誤ると、同じことが起きます。ルーターに渡すべきパケットを直接届けようとして、相手が見つからずに通信できなくなります。

```python answer=same-network
import ipaddress

my_network = ipaddress.ip_network("192.168.1.0/24")

for dest in ["192.168.1.20", "192.168.2.20"]:
    if ipaddress.ip_address(dest) in my_network:
        print(dest, "直接届ける")
    else:
        print(dest, "デフォルトゲートウェイへ渡す")
```

実行結果は次のとおりです。

```text
192.168.1.20 直接届ける
192.168.2.20 デフォルトゲートウェイへ渡す
```

### サーバーに送るリクエスト行を作る

パスの後ろには、「?」で区切ってクエリを付けます。フラグメントはブラウザーの中だけで使う部品なので、リクエストには入れません。

```python answer=request-line
from urllib.parse import urlsplit

url = urlsplit("https://www.example.co.jp/search?q=wifi#result")
target = url.path + "?" + url.query
print("GET", target, "HTTP/1.1")
print("Host:", url.hostname)
```

実行結果は次のとおりです。

```text
GET /search?q=wifi HTTP/1.1
Host: www.example.co.jp
```

## 第6章のまとめ

- インターネットは、世界中のネットワークが互いにつながり合った「ネットワークのネットワーク」であり、全体を管理する中心を持たない
- 通信の約束ごとをプロトコルと呼ぶ。TCP/IPでは通信の仕事を4つの階層に分け、各層がヘッダーを付けてデータを包む（カプセル化）
- インターネットは、データをパケットに分けて回線を共有するパケット交換で動いている
- 回線の速さには帯域（bps）と遅延（ms）の2つのものさしがある。伝送時間は、ビットとバイトの単位をそろえて「データの量÷回線の速さ」で見積もる
- IPアドレスは通信相手の住所であり、ルーターがルーティングテーブルを頼りにバケツリレーでパケットを目的地まで運ぶ
- 端末はDHCPで設定を受け取る。宛先が同じネットワークなら直接、別のネットワークならデフォルトゲートウェイへ、MACアドレスを宛先にしたフレームで渡す
- TCPは確認応答と再送で確実さを、UDPは手間を省いて速さを優先する。ポート番号で相手のどのアプリ宛てかを区別する
- DNSは、ドメイン名の階層をたどってIPアドレスを調べるしくみであり、キャッシュとTTLで効率よく動いている
- Webページは、DNSでの名前解決、TCPの接続、暗号化の準備（TLS）、HTTPのリクエストとレスポンスを経て、ブラウザーが組み立てて表示する
- つながらないときは、自分の設定、ゲートウェイへのping、IPアドレスへのping、名前解決、経路、サーバーの応答の順に確かめる

この章では、データが世界中のどこへでも届くしくみを見てきました。しかし、つながるということは、悪意を持つ相手ともつながりうるということでもあります。次の第7章では、のぞき見やなりすましから身を守り、インターネットを安全に使うためのしくみを学びます。
